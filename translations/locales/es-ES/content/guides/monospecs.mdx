## Descripción general

MonoSpecs es la solución de gestión de múltiples repositorios que ofrece HagiCode: rastrea y gestiona varios subrepositorios mediante `.hagicode/monospecs.yaml`. Se puede usar en cualquier proyecto que necesite gestionar de forma unificada varios repositorios independientes.

> **Aviso de migración**: `monospecs.yaml` se ha migrado del directorio raíz del proyecto a `.hagicode/monospecs.yaml`. El `monospecs.yaml` del directorio raíz ya no se detecta ni se admite como alternativa; los proyectos existentes deben crear manualmente el directorio `.hagicode/` y mover el archivo.

> 💡 **Primeros pasos**: consulte el repositorio [monospecs-demo](https://github.com/HagiCode-org/monospecs-demo) para conocer la estructura completa de un proyecto MonoSpecs, que incluye el archivo de configuración, el script de descarga y la documentación README.

### Conceptos básicos

**Archivo de configuración**

`.hagicode/monospecs.yaml` es el núcleo de toda la solución de gestión. Este archivo define:

- La lista y la ubicación de los subrepositorios
- La URL de Git de cada repositorio
- El nombre y el icono que se muestran
- El comportamiento de la integración con OpenSpec

**Diferencias con el uso de OpenSpec en un repositorio normal**

Tanto los proyectos gestionados con MonoSpecs como los repositorios únicos normales pueden usar el flujo de OpenSpec de HagiCode para gestionar los cambios. La diferencia entre ambos es la siguiente:

| Característica | Repositorio normal | Proyecto gestionado con MonoSpecs |
|------|---------|---------------------|
| **Ubicación de OpenSpec** | `openspec/` en la raíz del repositorio | `openspec/` en la raíz del repositorio principal |
| **Alcance de los cambios** | Limitado al repositorio actual | Puede abarcar varios subrepositorios |
| **Limpieza de los subrepositorios** | Las specs se mezclan con el código | Las specs viven por separado en el repositorio principal y los subrepositorios quedan más limpios |
| **Confirmación automática al archivar** | Hay que confirmar a mano los cambios de las specs | `commit_when_archive` confirma automáticamente las specs en el repositorio principal |

En resumen, la solución MonoSpecs separa las specs del código de los subrepositorios, mantiene limpios los subrepositorios y simplifica la gestión de las specs mediante la confirmación automática.

### Por qué usar MonoSpecs

- **Gestión unificada**: rastree todos los subrepositorios en un único archivo de configuración
- **Compatibilidad con la automatización**: proporciona metadatos de los repositorios a scripts y herramientas
- **Apto para IA**: la configuración estructurada facilita que los AI Agent comprendan las relaciones entre repositorios
- **Integración con OpenSpec**: se integra sin fricciones con el flujo de trabajo de gestión de cambios

### Cuándo conviene usar MonoSpecs

En los siguientes escenarios conviene considerar MonoSpecs en primer lugar:

**1. Desarrollo colaborativo en varios repositorios**

Cuando un proyecto se divide en varios repositorios independientes y es necesario gestionarlos de forma unificada:
- La aplicación de frontend, el servicio de backend y el cliente de escritorio se desarrollan por separado
- Proyectos auxiliares como la documentación, el sitio web oficial y las herramientas de compilación
- Los repositorios tienen dependencias entre sí y es necesario coordinar versiones y cambios

**2. Desarrollo de funciones que abarcan varios repositorios**

Al usar OpenSpec para gestionar cambios:
- Un cambio de función puede afectar a varios repositorios
- Es necesario rastrear en qué repositorios se aplica el cambio
- Los cambios se confirman automáticamente en el repositorio de destino correcto

**3. Desarrollo asistido por IA**

Proporcione a los AI Agent información sobre la estructura del proyecto:
- Describa la pila tecnológica y las normas de cada repositorio mediante `AGENTS.md`
- La IA puede comprender las relaciones entre repositorios a partir de la configuración
- Permite la generación y refactorización de código entre repositorios

**4. Integración y despliegue continuos**

Los flujos de CI/CD necesitan:
- Procesar por lotes varios repositorios
- Compilar y desplegar automáticamente según la configuración
- Rastrear las versiones y las dependencias de cada repositorio

### Diferencias entre MonoSpecs y los repositorios normales

| Característica | Proyecto normal de varios repositorios | Proyecto gestionado con MonoSpecs |
|------|---------------|---------------------|
| **Descubrimiento de repositorios** | Búsqueda y registro manuales | Lectura automática desde `.hagicode/monospecs.yaml` |
| **Operaciones por lotes** | Hay que escribir los scripts a mano | Scripts unificados dirigidos por la configuración |
| **Compatibilidad con IA** | Depende de la documentación | Configuración estructurada + `AGENTS.md` |
| **Metadatos de los repositorios** | Dispersos por todas partes | Gestión centralizada (iconos, nombres, URL) |
| **Incorporación de nuevas personas** | Hay que leer varios documentos | Basta con ejecutar un script |

### Descripción de la estructura del proyecto

Al usar la solución MonoSpecs se necesita un repositorio principal que gestione la configuración. El propio repositorio principal también es un repositorio Git y sirve para:

- Almacenar el archivo de configuración `.hagicode/monospecs.yaml`
- Gestionar la configuración y los scripts que abarcan varios repositorios
- Rastrear las relaciones de metadatos de los subrepositorios

Tomando como ejemplo el proyecto HagiCode Mono, la estructura típica de un proyecto MonoSpecs es la siguiente:

<FileTree>
- your-project/         # Repositorio principal (repositorio Git)
  - .git/              # Historial de Git del repositorio principal
  - .gitignore         # Excluye el directorio repos/
  - .hagicode/         # Directorio de datos del proyecto HagiCode
    - monospecs.yaml   # Archivo de configuración de repositorios
  - openspec/          # Directorio de cambios de OpenSpec (opcional)
  - repos/             # Directorio de subrepositorios (fuera de Git)
    - frontend/        # Subrepositorio (repositorio Git independiente)
    - backend/         # Subrepositorio (repositorio Git independiente)
    - ...              # Otros subrepositorios
</FileTree>

Todos los subrepositorios deben colocarse en el directorio `repos/`, y este directorio **debe excluirse del control de versiones Git del repositorio principal**. Para ello, añada lo siguiente al archivo `.gitignore` del repositorio principal:

```plaintext
# 排除所有子仓库
repos/
```

De este modo se evita que el repositorio principal rastree el contenido de los subrepositorios, y cada subrepositorio gestiona su propio control de versiones de forma independiente.

## Inicio rápido

Esta sección le guiará por la configuración inicial de MonoSpecs para que pueda empezar enseguida a usar la gestión de múltiples repositorios.

### Inicialización

Siga estos pasos para completar la configuración inicial de MonoSpecs:

#### 1. Crear una carpeta git vacía

Cree una carpeta `git` vacía en su repositorio principal (nota: es `git` y no `repos`; esta es una convención de MonoSpecs):

```bash
mkdir git
cd git
git init
cd ..
```

#### 2. Configurar el archivo de MonoSpecs

Cree el archivo de configuración `.hagicode/monospecs.yaml` en la raíz del repositorio principal y añada los subrepositorios que desea gestionar:

```bash
mkdir -p .hagicode
```

```yaml
version: "1.0"
commit_when_archive: true

repositories:
  - path: "repos/frontend"
    url: "https://github.com/your-org/frontend.git"
    displayName: "前端应用"
    icon: "🌐"
  - path: "repos/backend"
    url: "https://github.com/your-org/backend.git"
    displayName: "后端服务"
    icon: "⚙️"
```

#### 3. Añadir la configuración de .gitignore

Añada lo siguiente al archivo `.gitignore` del repositorio principal para excluir el directorio de los subrepositorios:

```plaintext
# 排除所有子仓库
repos/
```

#### 4. Descargar todos los subrepositorios (repo)

Use el script de clonación para descargar los subrepositorios configurados.

Esto clonará todos los subrepositorios en el directorio `repos/` según la configuración de `.hagicode/monospecs.yaml`.

#### 5. Añadir el repositorio principal a HagiCode

Si usa la aplicación de escritorio de HagiCode, una vez abierta añada el repositorio principal como proyecto desde la interfaz. Haga clic en el botón «Añadir proyecto» o «+» y seleccione la carpeta de su repositorio principal.

Si todo está bien configurado, verá la lista de todos los subrepositorios y la información de su estado.

## Configuración de .hagicode/monospecs.yaml

### Ubicación del archivo de configuración

El archivo de configuración se encuentra en el directorio raíz del proyecto:

<FileTree>
  - your-project/
    - .hagicode/
      - monospecs.yaml
</FileTree>

### Descripción de las opciones de configuración

```yaml
# 版本号
version: "1.0"

# 归档时自动提交（OpenSpec 使用）
commit_when_archive: true

# 仓库列表
repositories:
  # 仓库路径（相对于项目根目录）
  - path: "repos/frontend"
    # Git 仓库 URL
    url: "https://github.com/your-org/frontend.git"
    # 显示名称
    displayName: "前端应用"
    # 图标（emoji）
    icon: "🌐"
```

| Opción | Tipo | Obligatoria | Descripción |
|--------|------|------|------|
| `version` | string | Sí | Versión del archivo de configuración |
| `commit_when_archive` | boolean | No | Si al archivar se confirman automáticamente las specs en el repositorio principal (no se confirma el código de los subrepositorios) |
| `repositories` | array | Sí | Lista de configuración de repositorios |
| `repositories[].path` | string | Sí | Ruta relativa del repositorio |
| `repositories[].url` | string | Sí | URL del repositorio Git |
| `repositories[].displayName` | string | Sí | Nombre del repositorio que se muestra |
| `repositories[].icon` | string | No | Icono del repositorio (emoji) |

## Operaciones de gestión de repositorios

### Añadir un repositorio nuevo

Añada una nueva entrada a la lista `repositories` de `.hagicode/monospecs.yaml`:

```yaml
repositories:
  # ... 现有仓库
  - path: "repos/new-service"
    url: "https://github.com/HagiCode-org/new-service.git"
    displayName: "新服务"
    icon: "🆕"
```

### Actualizar la configuración de un repositorio

Cuando cambie la URL o los metadatos de un repositorio:

1. Edite `.hagicode/monospecs.yaml` para actualizar la entrada correspondiente
2. Compruebe que la sintaxis YAML es correcta
3. Si necesita sincronizar el cambio, actualice a mano la configuración del repositorio local

## Integración con OpenSpec

Tanto los proyectos gestionados con MonoSpecs como los repositorios normales pueden usar el flujo de OpenSpec de HagiCode. La diferencia principal está en la ubicación de la carpeta de OpenSpec y en la forma de distribuir los cambios.

### Ubicación de la carpeta de OpenSpec

**Repositorio normal**:
```
my-repo/
  - openspec/          # OpenSpec 变更目录（与代码混在一起）
  - src/
```

**Proyecto gestionado con MonoSpecs**:
```
your-project/          # 主仓库
  - openspec/          # OpenSpec 变更目录（独立管理）
  - .hagicode/
    - monospecs.yaml
  - repos/
    - frontend/        # 子仓库（更干净，无 openspec/）
    - backend/         # 子仓库（更干净，无 openspec/）
```

**Ventaja**: las specs viven por separado en el repositorio principal y los subrepositorios se mantienen limpios, con solo el código real, sin mezclar documentos normativos.

### Mecanismo de distribución de los cambios

**Repositorio normal**:
- Los cambios solo afectan al repositorio actual
- Las specs y el código están en el mismo repositorio
- Tras archivar, hay que confirmar a mano los cambios relacionados con las specs

**Proyecto gestionado con MonoSpecs**:
- OpenSpec lee `.hagicode/monospecs.yaml` para identificar el alcance de los repositorios
- Hace coincidir automáticamente el repositorio de destino según la ruta de los archivos modificados
- Con `commit_when_archive: true`, al archivar se confirman automáticamente las specs en el repositorio principal, sin intervención manual
- Los cambios reales de código de los subrepositorios deben confirmarse a mano

### Descripción de commit_when_archive

Cuando se establece `commit_when_archive: true`:

```yaml
version: "1.0"
commit_when_archive: true  # 归档时自动提交 specs 到主仓库
```

**Comportamiento al archivar**:
- OpenSpec confirma automáticamente en el repositorio principal los cambios de las specs (proposal, design, tasks, etc.)
- No confirma los cambios reales de código de los subrepositorios (el código debe confirmarse a mano)
- Se evita la molestia de gestionar a mano el control de versiones de las specs

**Flujo de ejemplo**:
1. Cree el cambio `openspec/changes/add-user-auth/`
2. Complete el diseño y las tareas e implemente la función en el código
3. Ejecute la operación de archivado
4. OpenSpec confirma automáticamente las specs en el repositorio principal
5. Confirme a mano los cambios de código de los subrepositorios

### Ejemplo

Cree un cambio en un proyecto gestionado con MonoSpecs:

```
openspec/changes/add-user-auth/
  - proposal.md
  - design.md
  - tasks.md
```

Cuando este cambio implica modificar `repos/frontend/src/components/Login.tsx`:

1. OpenSpec lee `.hagicode/monospecs.yaml`
2. Identifica la configuración del repositorio correspondiente a `repos/frontend`
3. El desarrollador implementa el cambio de código
4. Al archivar, OpenSpec confirma automáticamente las specs en el repositorio principal
5. El desarrollador confirma a mano los cambios de código del subrepositorio frontend

### Compatibilidad con la configuración de AI Agent

Los proyectos que usan la solución MonoSpecs permiten ofrecer a los AI Agent orientaciones específicas del proyecto mediante `AGENTS.md`:

<FileTree>
- your-project/
  - AGENTS.md           # Configuración de Agent a nivel del repositorio principal
  - repos/
    - frontend/
      - AGENTS.md       # Configuración de Agent específica del repositorio (hereda la configuración principal)
    - backend/
      - AGENTS.md       # Configuración de Agent del repositorio de backend
</FileTree>

El `AGENTS.md` de cada repositorio puede incluir:

- **Descripción de la pila tecnológica**: frameworks, herramientas de compilación, gestión de estado, etc.
- **Normas de código**: convenciones de nomenclatura, estructura de archivos y buenas prácticas
- **Comportamiento específico del proyecto**: extensiones o diferencias respecto a la configuración del repositorio principal
- **Integración con OpenSpec**: cómo participar en el flujo de trabajo de gestión de cambios

Esta configuración por capas permite a los AI Agent:
1. Comprender las normas globales del repositorio principal
2. Identificar los requisitos particulares de cada repositorio
3. Mantener la coherencia en las operaciones que abarcan varios repositorios

## Buenas prácticas

### Convenciones de nomenclatura

- **Ruta del repositorio**: use el prefijo `repos/` para mantener la coherencia
- **Nombre del repositorio**: use kebab-case (letras minúsculas y guiones)
- **Nombre para mostrar**: use un nombre en chino conciso
- **Elección del icono**: use un emoji relacionado con la función del repositorio

### Mantenimiento de la configuración

1. **Sincronizar la configuración con el estado real**: asegúrese periódicamente de que `.hagicode/monospecs.yaml` refleja la estructura real de los repositorios

## Migración desde monospecs.yaml en el directorio raíz

Si el proyecto sigue usando `monospecs.yaml` en el directorio raíz, migre manualmente al nuevo directorio de datos del proyecto de HagiCode:

```bash
mkdir -p .hagicode
mv monospecs.yaml .hagicode/monospecs.yaml
git add .hagicode/monospecs.yaml
git rm monospecs.yaml
git commit -m "Move MonoSpecs config to .hagicode"
```

Tras la migración, HagiCode solo leerá `.hagicode/monospecs.yaml`. Si solo se conserva el `monospecs.yaml` del directorio raíz, el proyecto se considerará sin MonoSpecs configurado y los scripts relacionados tampoco lo leerán como ruta de compatibilidad.
2. **Control de versiones**: todos los cambios de configuración deben confirmarse en el control de versiones
3. **Actualización de la documentación**: al añadir o quitar repositorios, actualice la documentación relacionada

### Métodos de verificación

- Confirme que la ruta del repositorio no contiene caracteres especiales
- Compruebe que la sintaxis YAML es correcta
