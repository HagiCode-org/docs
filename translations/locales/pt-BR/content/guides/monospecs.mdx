## Visão geral

O MonoSpecs é a solução de gerenciamento de vários repositórios oferecida pelo HagiCode, que acompanha e gerencia vários sub-repositórios por meio do arquivo `.hagicode/monospecs.yaml`. Ele pode ser usado em qualquer projeto que precise gerenciar de forma unificada vários repositórios independentes.

> **Aviso de migração**: o arquivo `monospecs.yaml` foi migrado do diretório raiz do projeto para `.hagicode/monospecs.yaml`. O `monospecs.yaml` na raiz não é mais detectado nem aceito como alternativa; projetos existentes precisam criar manualmente o diretório `.hagicode/` e mover o arquivo.

> 💡 **Comece rápido**: consulte o repositório [monospecs-demo](https://github.com/HagiCode-org/monospecs-demo) para conhecer a estrutura completa de um projeto MonoSpecs, que inclui o arquivo de configuração, scripts de clonagem e a documentação do README.

### Conceitos principais

**Arquivo de configuração**

O `.hagicode/monospecs.yaml` é o núcleo de toda a solução de gerenciamento. Esse arquivo define:

- A lista e a localização dos sub-repositórios
- A URL Git de cada repositório
- O nome de exibição e o ícone
- O comportamento da integração com o OpenSpec

**Diferença no uso do OpenSpec em relação a um repositório comum**

Tanto um projeto gerenciado pelo MonoSpecs quanto um repositório único comum podem usar o fluxo do OpenSpec do HagiCode para gerenciar mudanças. A diferença entre os dois é a seguinte:

| Característica | Repositório comum | Projeto gerenciado pelo MonoSpecs |
|------|---------|---------------------|
| **Localização do OpenSpec** | `openspec/` na raiz do repositório | `openspec/` na raiz do repositório principal |
| **Escopo da mudança** | Restrito ao repositório atual | Pode envolver vários sub-repositórios |
| **Limpeza dos sub-repositórios** | Specs e código ficam misturados | As specs ficam separadas no repositório principal, e os sub-repositórios ficam mais limpos |
| **Commit automático no arquivamento** | É preciso fazer commit manual das mudanças nas specs | `commit_when_archive` faz o commit automático das specs no repositório principal |

Em resumo, a solução MonoSpecs separa as specs do código dos sub-repositórios, mantendo-os limpos, e ainda simplifica o gerenciamento das specs com o commit automático.

### Por que usar o MonoSpecs

- **Gerenciamento unificado**: acompanhe todos os sub-repositórios em um único arquivo de configuração
- **Suporte à automação**: fornece metadados dos repositórios para scripts e ferramentas
- **Amigável para IA**: a configuração estruturada facilita a compreensão das relações entre repositórios pelo AI Agent
- **Integração com o OpenSpec**: integra-se perfeitamente ao fluxo de gerenciamento de mudanças

### Quando usar o MonoSpecs

Considere o MonoSpecs em primeiro lugar nos seguintes cenários:

**1. Desenvolvimento colaborativo com vários repositórios**

Quando um projeto é dividido em vários repositórios independentes, é preciso gerenciá-los de forma unificada:
- Aplicativo de front-end, serviço de back-end e cliente desktop desenvolvidos de forma independente
- Projetos auxiliares, como documentação, site oficial e ferramentas de build
- Os repositórios têm dependências entre si, e é preciso coordenar versões e mudanças

**2. Desenvolvimento de funcionalidades entre repositórios**

Ao usar o OpenSpec para gerenciar mudanças:
- Uma mudança de funcionalidade pode envolver vários repositórios
- É preciso acompanhar em quais repositórios a mudança é aplicada
- O commit das mudanças é feito automaticamente no repositório de destino correto

**3. Desenvolvimento assistido por IA**

Fornece informações sobre a estrutura do projeto ao AI Agent:
- Descreva a pilha tecnológica e as convenções de cada repositório por meio do `AGENTS.md`
- A IA pode entender a relação entre os repositórios com base na configuração
- Oferece suporte à geração de código e à refatoração entre repositórios

**4. Integração/implantação contínua**

Os pipelines de CI/CD precisam:
- Processar vários repositórios em lote
- Compilar e implantar automaticamente com base na configuração
- Acompanhar as versões e as dependências de cada repositório

### Diferença entre o MonoSpecs e um repositório comum

| Característica | Projeto comum com vários repositórios | Projeto gerenciado pelo MonoSpecs |
|------|---------------|---------------------|
| **Descoberta de repositórios** | Busca e registro manuais | Leitura automática a partir de `.hagicode/monospecs.yaml` |
| **Operações em lote** | É preciso escrever scripts manualmente | Scripts unificados orientados por configuração |
| **Suporte à IA** | Depende de documentação explicativa | Configuração estruturada + `AGENTS.md` |
| **Metadados dos repositórios** | Espalhados por vários lugares | Gerenciados de forma centralizada (ícone, nome, URL) |
| **Integração de novos membros** | É preciso ler vários documentos | Basta executar um script |

### Estrutura do projeto

Ao usar a solução MonoSpecs, é preciso um repositório principal para gerenciar a configuração. O próprio repositório principal também é um repositório Git e serve para:

- Armazenar o arquivo de configuração `.hagicode/monospecs.yaml`
- Gerenciar configurações e scripts entre repositórios
- Acompanhar as relações de metadados dos sub-repositórios

Tomando o projeto HagiCode Mono como exemplo, a estrutura típica de um projeto MonoSpecs é a seguinte:

<FileTree>
- your-project/         # Repositório principal (repositório Git)
  - .git/              # Histórico Git do repositório principal
  - .gitignore         # Exclui o diretório repos/
  - .hagicode/         # Diretório de dados do projeto HagiCode
    - monospecs.yaml   # Arquivo de configuração dos repositórios
  - openspec/          # Diretório de mudanças do OpenSpec (opcional)
  - repos/             # Diretório dos sub-repositórios (fora do Git)
    - frontend/        # Sub-repositório (repositório Git independente)
    - backend/         # Sub-repositório (repositório Git independente)
    - ...              # Outros sub-repositórios
</FileTree>

Todos os sub-repositórios devem ficar no diretório `repos/`, e esse diretório **precisa ser excluído do controle de versão Git do repositório principal**. Isso pode ser feito adicionando o conteúdo a seguir ao arquivo `.gitignore` do repositório principal:

```plaintext
# 排除所有子仓库
repos/
```

Assim, o repositório principal não acompanha o conteúdo dos sub-repositórios, e cada sub-repositório gerencia de forma independente o próprio controle de versão.

## Início rápido

Esta seção guia você pela configuração inicial do MonoSpecs, para que você possa começar rapidamente a usar o gerenciamento de vários repositórios.

### Inicialização

Siga as etapas abaixo para concluir a configuração inicial do MonoSpecs:

#### 1. Criar uma pasta git vazia

No seu repositório principal, crie uma pasta `git` vazia (atenção: é `git`, e não `repos`; essa é uma convenção do MonoSpecs):

```bash
mkdir git
cd git
git init
cd ..
```

#### 2. Configurar o arquivo do MonoSpecs

Crie o arquivo de configuração `.hagicode/monospecs.yaml` na raiz do repositório principal e adicione os sub-repositórios que você quer gerenciar:

```bash
mkdir -p .hagicode
```

```yaml
version: "1.0"
commit_when_archive: true

repositories:
  - path: "repos/frontend"
    url: "https://github.com/your-org/frontend.git"
    displayName: "前端应用"
    icon: "🌐"
  - path: "repos/backend"
    url: "https://github.com/your-org/backend.git"
    displayName: "后端服务"
    icon: "⚙️"
```

#### 3. Adicionar a configuração do .gitignore

Adicione o conteúdo a seguir ao arquivo `.gitignore` do repositório principal para excluir o diretório dos sub-repositórios:

```plaintext
# 排除所有子仓库
repos/
```

#### 4. Baixar todos os sub-repositórios (repo)

Use o script de clonagem para baixar os sub-repositórios configurados.

Ele clona todos os sub-repositórios para o diretório `repos/`, de acordo com a configuração em `.hagicode/monospecs.yaml`.

#### 5. Adicionar o repositório principal ao HagiCode

Se você usa o aplicativo desktop do HagiCode, abra o aplicativo e adicione o repositório principal como projeto pela interface. Clique em "Adicionar projeto" ou no botão "+" e selecione a pasta do seu repositório principal.

Se tudo estiver configurado corretamente, você verá a lista de todos os sub-repositórios e as informações de status.

## Configuração do .hagicode/monospecs.yaml

### Localização do arquivo de configuração

O arquivo de configuração fica na raiz do projeto:

<FileTree>
  - your-project/
    - .hagicode/
      - monospecs.yaml
</FileTree>

### Descrição dos itens de configuração

```yaml
# 版本号
version: "1.0"

# 归档时自动提交（OpenSpec 使用）
commit_when_archive: true

# 仓库列表
repositories:
  # 仓库路径（相对于项目根目录）
  - path: "repos/frontend"
    # Git 仓库 URL
    url: "https://github.com/your-org/frontend.git"
    # 显示名称
    displayName: "前端应用"
    # 图标（emoji）
    icon: "🌐"
```

| Opção de configuração | Tipo | Obrigatório | Descrição |
|--------|------|------|------|
| `version` | string | Sim | Versão do arquivo de configuração |
| `commit_when_archive` | boolean | Não | Define se é feito commit automático das specs no repositório principal no arquivamento (o código dos sub-repositórios não entra no commit) |
| `repositories` | array | Sim | Lista de configurações dos repositórios |
| `repositories[].path` | string | Sim | Caminho relativo do repositório |
| `repositories[].url` | string | Sim | URL do repositório Git |
| `repositories[].displayName` | string | Sim | Nome de exibição do repositório |
| `repositories[].icon` | string | Não | Ícone do repositório (emoji) |

## Operações de gerenciamento de repositórios

### Adicionar um novo repositório

Adicione uma nova entrada ao array `repositories` de `.hagicode/monospecs.yaml`:

```yaml
repositories:
  # ... 现有仓库
  - path: "repos/new-service"
    url: "https://github.com/HagiCode-org/new-service.git"
    displayName: "新服务"
    icon: "🆕"
```

### Atualizar a configuração de um repositório

Quando a URL ou os metadados de um repositório mudarem:

1. Edite `.hagicode/monospecs.yaml` para atualizar a entrada correspondente
2. Verifique se a sintaxe do YAML está correta
3. Se for preciso sincronizar a mudança, atualize manualmente a configuração do repositório local

## Funcionalidades principais

Esta seção apresenta as principais funcionalidades visuais da integração do MonoSpecs com o OpenSpec, para ajudar você a entendê-las e usá-las de forma mais intuitiva.

> **Observação**: as capturas de tela a seguir mostram o resultado com o MonoSpecs ativado.

### Seleção de sub-repositórios

Ao criar uma nova proposta, você pode escolher os sub-repositórios de destino a consultar e editar. O sistema detecta automaticamente e exibe a lista de sub-repositórios disponíveis.

![Seleção de sub-repositórios ao criar uma proposta](../img/screenshots/product/create-proposal/original.png)

Ao criar uma mudança, o OpenSpec lê a configuração de `.hagicode/monospecs.yaml` e lista todos os sub-repositórios disponíveis para você escolher. Você pode selecionar os sub-repositórios que precisam ser modificados, e o sistema acompanha automaticamente o escopo envolvido na mudança.

### Prévia dos detalhes do repositório

No painel do projeto, ao passar o mouse sobre um repositório, aparecem as informações detalhadas desse repositório e as ações rápidas.

![Passar o mouse para ver os detalhes do repositório](../img/screenshots/guides/repository-hover-actions/original.png)

Com essa prévia interativa, você pode conhecer rapidamente:
- O nome, o caminho e o branch atual do repositório
- O estado atual do repositório (se há alterações sem commit e quantos commits ele está à frente ou atrás do remoto)
- As ações rápidas para esse repositório: abrir o Code Server, abrir o gerenciamento do Git, Super Commit, gerenciar o DESIGN.md e ir para o repositório

### Seleção de sub-repositórios no Super Commit

Ao usar o Super Commit para enviar mudanças, você pode escolher sub-repositórios específicos como destino.

![Seleção de sub-repositórios no Super Commit](../img/screenshots/product/git-super-commit/original.png)

A funcionalidade Super Commit:
1. Lê a configuração de `.hagicode/monospecs.yaml`
2. Analisa o conteúdo das suas mudanças
3. Sugere em quais sub-repositórios você deve fazer o commit
4. Você pode aceitar a sugestão ou indicar manualmente os repositórios de destino

## Integração com o OpenSpec

Tanto um projeto gerenciado pelo MonoSpecs quanto um repositório comum podem usar o fluxo do OpenSpec do HagiCode. A principal diferença está na localização da pasta do OpenSpec e na forma de distribuição das mudanças.

### Localização da pasta do OpenSpec

**Repositório comum**:
```
my-repo/
  - openspec/          # OpenSpec 变更目录（与代码混在一起）
  - src/
```

**Projeto gerenciado pelo MonoSpecs**:
```
your-project/          # 主仓库
  - openspec/          # OpenSpec 变更目录（独立管理）
  - .hagicode/
    - monospecs.yaml
  - repos/
    - frontend/        # 子仓库（更干净，无 openspec/）
    - backend/         # 子仓库（更干净，无 openspec/）
```

**Vantagem**: as specs ficam separadas no repositório principal, e os sub-repositórios permanecem limpos, contendo apenas o código real, sem documentos de especificação misturados.

### Mecanismo de distribuição das mudanças

**Repositório comum**:
- A mudança afeta apenas o repositório atual
- As specs e o código ficam no mesmo repositório
- Após o arquivamento, é preciso fazer commit manual das mudanças relacionadas às specs

**Projeto gerenciado pelo MonoSpecs**:
- O OpenSpec lê `.hagicode/monospecs.yaml` para identificar o escopo dos repositórios
- O repositório de destino é encontrado automaticamente com base no caminho dos arquivos alterados
- Com `commit_when_archive: true`, o arquivamento faz o commit automático das specs no repositório principal, sem operação manual
- As mudanças reais no código dos sub-repositórios precisam receber commit manualmente

### Descrição do commit_when_archive

Quando `commit_when_archive: true` está definido:

```yaml
version: "1.0"
commit_when_archive: true  # 归档时自动提交 specs 到主仓库
```

**Comportamento no arquivamento**:
- O OpenSpec faz automaticamente o commit das mudanças das specs (proposal, design, tasks etc.) no repositório principal
- As mudanças reais no código dos sub-repositórios não entram no commit (o código precisa receber commit manualmente)
- Poupa o trabalho de gerenciar manualmente o controle de versão das specs

**Exemplo de fluxo**:
1. Crie a mudança `openspec/changes/add-user-auth/`
2. Conclua o design e as tarefas e implemente a funcionalidade no código
3. Execute a operação de arquivamento
4. O OpenSpec faz automaticamente o commit das specs no repositório principal
5. Faça manualmente o commit das mudanças de código dos sub-repositórios

### Exemplo

Crie uma mudança em um projeto gerenciado pelo MonoSpecs:

```
openspec/changes/add-user-auth/
  - proposal.md
  - design.md
  - tasks.md
```

Quando essa mudança envolve modificar `repos/frontend/src/components/Login.tsx`:

1. O OpenSpec lê `.hagicode/monospecs.yaml`
2. Identifica a configuração de repositório correspondente a `repos/frontend`
3. A pessoa desenvolvedora implementa a mudança no código
4. No arquivamento, o OpenSpec faz automaticamente o commit das specs no repositório principal
5. A pessoa desenvolvedora faz manualmente o commit das mudanças de código do sub-repositório frontend

### Suporte à configuração do AI Agent

Projetos que usam a solução MonoSpecs podem fornecer orientações específicas do projeto ao AI Agent por meio do `AGENTS.md`:

<FileTree>
- your-project/
  - AGENTS.md           # Configuração do Agent no nível do repositório principal
  - repos/
    - frontend/
      - AGENTS.md       # Configuração do Agent específica do repositório (herda a configuração principal)
    - backend/
      - AGENTS.md       # Configuração do Agent do repositório de back-end
</FileTree>

O `AGENTS.md` de cada repositório pode conter:

- **Descrição da pilha tecnológica**: framework, ferramentas de build, gerenciamento de estado etc.
- **Convenções de código**: convenções de nomenclatura, estrutura de arquivos, boas práticas
- **Comportamento específico do projeto**: extensões ou diferenças em relação à configuração do repositório principal
- **Integração com o OpenSpec**: como participar do fluxo de gerenciamento de mudanças

Essa configuração em camadas permite que o AI Agent:
1. Entenda as convenções globais do repositório principal
2. Identifique os requisitos especiais de cada repositório
3. Mantenha a consistência em operações entre repositórios

## Boas práticas

### Convenções de nomenclatura

- **Caminho do repositório**: use o prefixo `repos/`, mantendo a consistência
- **Nome do repositório**: use kebab-case (letras minúsculas e hífens)
- **Nome de exibição**: use um nome conciso em chinês
- **Escolha do ícone**: use um emoji relacionado à função do repositório

### Manutenção da configuração

1. **Sincronize a configuração com o estado real**: confira periodicamente se o `.hagicode/monospecs.yaml` reflete a estrutura real dos repositórios

## Migração do monospecs.yaml da raiz

Se o projeto ainda usa o `monospecs.yaml` na raiz, migre-o manualmente para o novo diretório de dados de projeto do HagiCode:

```bash
mkdir -p .hagicode
mv monospecs.yaml .hagicode/monospecs.yaml
git add .hagicode/monospecs.yaml
git rm monospecs.yaml
git commit -m "Move MonoSpecs config to .hagicode"
```

Após a migração, o HagiCode lê apenas `.hagicode/monospecs.yaml`. Se apenas o `monospecs.yaml` da raiz for mantido, o projeto será considerado sem MonoSpecs configurado, e os scripts relacionados também não o lerão como caminho alternativo.
2. **Controle de versão**: todas as mudanças de configuração devem ser enviadas ao controle de versão
3. **Atualização da documentação**: atualize a documentação relacionada ao adicionar ou remover repositórios

### Métodos de verificação

- Confirme que o caminho do repositório não contém caracteres especiais
- Verifique se a sintaxe do YAML está correta
