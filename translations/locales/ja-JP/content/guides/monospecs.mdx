## 概要

MonoSpecs は、HagiCode が提供するマルチリポジトリ管理方式で、`.hagicode/monospecs.yaml` を通じて複数のサブリポジトリを追跡・管理します。複数の独立したリポジトリをまとめて管理したいプロジェクトであれば、どれでも利用できます。

> **移行のお知らせ**：`monospecs.yaml` はプロジェクトのルートディレクトリから `.hagicode/monospecs.yaml` に移行されました。ルートディレクトリの `monospecs.yaml` は、検出も互換フォールバックもされなくなりました。既存のプロジェクトでは、`.hagicode/` ディレクトリを手動で作成し、ファイルを移動する必要があります。

> 💡 **クイックスタート**：設定ファイル、取得スクリプト、README ドキュメントを含む MonoSpecs プロジェクトの完全な構成は、[monospecs-demo](https://github.com/HagiCode-org/monospecs-demo) リポジトリを参照してください。

### 基本概念

**設定ファイル**

`.hagicode/monospecs.yaml` はこの管理方式の中核となるファイルで、次の内容を定義します。

- サブリポジトリの一覧と配置場所
- 各リポジトリの Git URL
- 表示名とアイコン
- OpenSpec との連携時の動作

**通常のリポジトリとの OpenSpec の使い方の違い**

MonoSpecs で管理されるプロジェクトでも、通常の単一リポジトリでも、HagiCode の OpenSpec フローで変更を管理できます。両者の違いは次のとおりです。

| 特性 | 通常のリポジトリ | MonoSpecs で管理されるプロジェクト |
|------|---------|---------------------|
| **OpenSpec の場所** | リポジトリのルートディレクトリの `openspec/` | メインリポジトリのルートディレクトリの `openspec/` |
| **変更の範囲** | 現在のリポジトリのみ | 複数のサブリポジトリにまたがれる |
| **サブリポジトリのクリーンさ** | specs とコードが混在する | specs はメインリポジトリに独立し、サブリポジトリはよりクリーンになる |
| **アーカイブ時の自動コミット** | specs の変更を手動でコミットする必要がある | `commit_when_archive` により specs が自動的にメインリポジトリへコミットされる |

要するに、MonoSpecs 方式では specs とサブリポジトリのコードを分離してサブリポジトリをクリーンに保ち、さらに自動コミットによって specs の管理手順を簡単にします。

### MonoSpecs を使う理由

- **一元管理**：一つの設定ファイルですべてのサブリポジトリを追跡します
- **自動化のサポート**：スクリプトやツールにリポジトリのメタデータを提供します
- **AI にやさしい**：構造化された設定により、AI Agent がリポジトリ間の関係を理解しやすくなります
- **OpenSpec との連携**：変更管理のワークフローとシームレスに連携します

### MonoSpecs が必要になる場面

次のような場面では、MonoSpecs を優先して検討してください。

**1. マルチリポジトリでの共同開発**

一つのプロジェクトが複数の独立したリポジトリに分割されていて、統一的に管理する必要がある場合：
- フロントエンドアプリ、バックエンドサービス、デスクトップ版をそれぞれ独立して開発している
- ドキュメント、公式サイト、ビルドツールなどの補助的なプロジェクトがある
- リポジトリ間に依存関係があり、バージョンと変更を調整する必要がある

**2. リポジトリをまたぐ機能開発**

OpenSpec で変更を管理する場合：
- 一つの機能変更が複数のリポジトリに及ぶことがある
- 変更がどのリポジトリで実施されるかを追跡する必要がある
- 変更を正しい対象リポジトリへ自動的にコミットする

**3. AI 支援による開発**

AI Agent にプロジェクト構成の情報を提供します：
- `AGENTS.md` で各リポジトリの技術スタックと規約を説明する
- AI が設定をもとにリポジトリ間の関係を理解できる
- リポジトリをまたぐコード生成とリファクタリングに対応する

**4. 継続的インテグレーション／デプロイ**

CI/CD パイプラインでは、次のことが必要です：
- 複数のリポジトリを一括で処理する
- 設定に基づいて自動的にビルドとデプロイを行う
- 各リポジトリのバージョンと依存関係を追跡する

### MonoSpecs と通常のリポジトリの違い

| 特性 | 通常のマルチリポジトリプロジェクト | MonoSpecs で管理されるプロジェクト |
|------|---------------|---------------------|
| **リポジトリの検出** | 手動で探して記録する | `.hagicode/monospecs.yaml` から自動で読み取る |
| **一括操作** | スクリプトを手動で書く必要がある | 設定駆動の統一されたスクリプト |
| **AI のサポート** | ドキュメントの説明に依存する | 構造化された設定 + `AGENTS.md` |
| **リポジトリのメタデータ** | あちこちに分散している | 一元管理（アイコン、名前、URL） |
| **新メンバーの立ち上がり** | 複数のドキュメントを読む必要がある | スクリプトを一つ実行するだけ |

### プロジェクト構成の説明

MonoSpecs 方式を使うには、設定を管理するメインリポジトリが必要です。メインリポジトリ自体も Git リポジトリで、次の用途に使います。

- `.hagicode/monospecs.yaml` 設定ファイルを保存する
- リポジトリをまたぐ設定とスクリプトを管理する
- サブリポジトリのメタデータの関係を追跡する

HagiCode Mono プロジェクトを例にすると、典型的な MonoSpecs プロジェクトの構成は次のとおりです。

<FileTree>
- your-project/         # メインリポジトリ（Git リポジトリ）
  - .git/              # メインリポジトリの Git 履歴
  - .gitignore         # repos/ ディレクトリを除外
  - .hagicode/         # HagiCode のプロジェクトデータディレクトリ
    - monospecs.yaml   # リポジトリ設定ファイル
  - openspec/          # OpenSpec の変更ディレクトリ（任意）
  - repos/             # サブリポジトリのディレクトリ（Git の管理対象外）
    - frontend/        # サブリポジトリ（独立した Git リポジトリ）
    - backend/         # サブリポジトリ（独立した Git リポジトリ）
    - ...              # その他のサブリポジトリ
</FileTree>

すべてのサブリポジトリは `repos/` ディレクトリの下に置き、このディレクトリは**メインリポジトリの Git バージョン管理から必ず除外**する必要があります。メインリポジトリの `.gitignore` ファイルに次の内容を追加することで実現できます。

```plaintext
# 排除所有子仓库
repos/
```

こうすることで、メインリポジトリがサブリポジトリの内容を追跡することを避けられ、各サブリポジトリが自分のバージョン管理を独立して行えます。

## クイックスタート

このセクションでは、MonoSpecs の初期設定を一通り行い、マルチリポジトリ管理機能をすぐに使い始められるようにします。

### 初期化

次の手順で、MonoSpecs の初期設定を完了します。

#### 1. 空の git フォルダーを作成する

メインリポジトリの中に、空の `git` フォルダーを作成します（注意：`repos` ではなく `git` です。これは MonoSpecs の規約です）。

```bash
mkdir git
cd git
git init
cd ..
```

#### 2. MonoSpecs ファイルを設定する

メインリポジトリのルートディレクトリに `.hagicode/monospecs.yaml` 設定ファイルを作成し、管理したいサブリポジトリを追加します。

```bash
mkdir -p .hagicode
```

```yaml
version: "1.0"
commit_when_archive: true

repositories:
  - path: "repos/frontend"
    url: "https://github.com/your-org/frontend.git"
    displayName: "前端应用"
    icon: "🌐"
  - path: "repos/backend"
    url: "https://github.com/your-org/backend.git"
    displayName: "后端服务"
    icon: "⚙️"
```

#### 3. .gitignore の設定を追加する

メインリポジトリの `.gitignore` ファイルに次の内容を追加して、サブリポジトリのディレクトリを除外します。

```plaintext
# 排除所有子仓库
repos/
```

#### 4. すべてのサブリポジトリ（repo）を取得する

clone スクリプトを使って、設定済みのサブリポジトリを取得します。

これにより、`.hagicode/monospecs.yaml` の設定に従って、すべてのサブリポジトリが `repos/` ディレクトリにクローンされます。

#### 5. メインリポジトリを HagiCode に追加する

HagiCode デスクトップアプリを使っている場合は、アプリを開いたあと、画面からメインリポジトリをプロジェクトとして追加します。「プロジェクトを追加」または「+」ボタンをクリックし、メインリポジトリのフォルダーを選択してください。

すべての設定が正しければ、すべてのサブリポジトリの一覧と状態の情報が表示されます。

## .hagicode/monospecs.yaml の設定

### 設定ファイルの場所

設定ファイルは、プロジェクトのルートディレクトリにあります。

<FileTree>
  - your-project/
    - .hagicode/
      - monospecs.yaml
</FileTree>

### 設定項目の説明

```yaml
# 版本号
version: "1.0"

# 归档时自动提交（OpenSpec 使用）
commit_when_archive: true

# 仓库列表
repositories:
  # 仓库路径（相对于项目根目录）
  - path: "repos/frontend"
    # Git 仓库 URL
    url: "https://github.com/your-org/frontend.git"
    # 显示名称
    displayName: "前端应用"
    # 图标（emoji）
    icon: "🌐"
```

| 設定項目 | 型 | 必須 | 説明 |
|--------|------|------|------|
| `version` | string | はい | 設定ファイルのバージョン |
| `commit_when_archive` | boolean | いいえ | アーカイブ時に specs をメインリポジトリへ自動コミットするかどうか（サブリポジトリのコードはコミットしません） |
| `repositories` | array | はい | リポジトリ設定の一覧 |
| `repositories[].path` | string | はい | リポジトリの相対パス |
| `repositories[].url` | string | はい | Git リポジトリの URL |
| `repositories[].displayName` | string | はい | リポジトリの表示名 |
| `repositories[].icon` | string | いいえ | リポジトリのアイコン（emoji） |

## リポジトリの管理操作

### 新しいリポジトリを追加する

`.hagicode/monospecs.yaml` の `repositories` 配列に、新しいエントリを追加します。

```yaml
repositories:
  # ... 现有仓库
  - path: "repos/new-service"
    url: "https://github.com/HagiCode-org/new-service.git"
    displayName: "新服务"
    icon: "🆕"
```

### リポジトリ設定を更新する

リポジトリの URL やメタデータが変更されたときは、次の手順で更新します。

1. `.hagicode/monospecs.yaml` を編集して、該当するエントリを更新する
2. YAML の構文が正しいことを検証する
3. 変更を同期する必要がある場合は、ローカルのリポジトリ設定を手動で更新する

## 主な機能

このセクションでは、MonoSpecs と OpenSpec を連携させたときの主な可視化機能を紹介し、これらの機能をより直感的に理解して使えるようにします。

> **注意**：以下のスクリーンショットは、MonoSpecs を有効にした場合の表示です。

### サブリポジトリの選択

新しい提案を作成するときに、参照・編集の対象とするサブリポジトリを選択できます。システムが利用可能なサブリポジトリの一覧を自動的に検出して表示します。

![新規提案の作成時にサブリポジトリを選択する](../img/screenshots/product/create-proposal/original.png)

変更を作成する際、OpenSpec は `.hagicode/monospecs.yaml` の設定を読み取り、選択可能なすべてのサブリポジトリを一覧表示します。変更したいサブリポジトリを選択すると、システムが変更の及ぶ範囲を自動的に追跡します。

### リポジトリ詳細のプレビュー

プロジェクトパネルでリポジトリにマウスカーソルを重ねると、そのリポジトリの詳細情報とクイック操作が表示されます。

![マウスカーソルを重ねてリポジトリの詳細を表示する](../img/screenshots/guides/repository-hover-actions/original.png)

このインタラクティブなプレビューによって、次のことをすばやく把握できます：
- リポジトリ名、パス、現在のブランチ
- リポジトリの現在の状態（未コミットの変更があるかどうか、およびリモートより進んでいる、または遅れているコミット数）
- そのリポジトリ向けのクイック操作：Code Server を開く、Git 管理を開く、Super Commit、DESIGN.md の管理、リポジトリへ移動

### Super Commit のサブリポジトリ選択

Super Commit で変更をコミットするときは、対象となるサブリポジトリを指定できます。

![Super Commit 時にサブリポジトリを選択する](../img/screenshots/product/git-super-commit/original.png)

Super Commit 機能は次のように動作します：
1. `.hagicode/monospecs.yaml` の設定を読み取る
2. 変更内容を分析する
3. どのサブリポジトリへコミットすべきかを提案する
4. 提案を受け入れるか、対象リポジトリを手動で指定するかを選べる

## OpenSpec との連携

MonoSpecs で管理されるプロジェクトでも通常のリポジトリでも、HagiCode の OpenSpec フローを利用できます。主な違いは、OpenSpec フォルダーの場所と、変更の振り分け方にあります。

### OpenSpec フォルダーの場所

**通常のリポジトリ**：
```
my-repo/
  - openspec/          # OpenSpec 变更目录（与代码混在一起）
  - src/
```

**MonoSpecs で管理されるプロジェクト**：
```
your-project/          # 主仓库
  - openspec/          # OpenSpec 变更目录（独立管理）
  - .hagicode/
    - monospecs.yaml
  - repos/
    - frontend/        # 子仓库（更干净，无 openspec/）
    - backend/         # 子仓库（更干净，无 openspec/）
```

**利点**：specs をメインリポジトリに独立させることで、サブリポジトリには実際のコードだけが残り、仕様ドキュメントが混ざらずにクリーンに保たれます。

### 変更の振り分けの仕組み

**通常のリポジトリ**：
- 変更は現在のリポジトリにのみ作用します
- specs とコードが同じリポジトリにあります
- アーカイブ後に、specs に関する変更を手動でコミットする必要があります

**MonoSpecs で管理されるプロジェクト**：
- OpenSpec が `.hagicode/monospecs.yaml` を読み取って、リポジトリの範囲を識別します
- 変更されたファイルのパスに基づいて、対象リポジトリを自動的に照合します
- `commit_when_archive: true` の場合、アーカイブ時に specs がメインリポジトリへ自動的にコミットされ、手動の操作は不要です
- サブリポジトリの実際のコード変更は、手動でコミットする必要があります

### commit_when_archive の説明

`commit_when_archive: true` を設定すると、次のようになります。

```yaml
version: "1.0"
commit_when_archive: true  # 归档时自动提交 specs 到主仓库
```

**アーカイブ時の動作**：
- OpenSpec が specs の変更（proposal、design、tasks など）を自動的にメインリポジトリへコミットします
- サブリポジトリの実際のコード変更はコミットされません（コードは手動でコミットする必要があります）
- specs のバージョン管理を手動で行う手間が省けます

**フローの例**：
1. 変更 `openspec/changes/add-user-auth/` を作成する
2. 設計とタスクを完了させ、コードの機能を実装する
3. アーカイブ操作を実行する
4. OpenSpec が specs をメインリポジトリへ自動的にコミットする
5. サブリポジトリのコード変更を手動でコミットする

### 例

MonoSpecs で管理されるプロジェクトで変更を一つ作成します。

```
openspec/changes/add-user-auth/
  - proposal.md
  - design.md
  - tasks.md
```

この変更で `repos/frontend/src/components/Login.tsx` を修正する場合は、次のように進みます。

1. OpenSpec が `.hagicode/monospecs.yaml` を読み取る
2. `repos/frontend` に対応するリポジトリ設定を識別する
3. 開発者がコードの変更を実装する
4. アーカイブ時に、OpenSpec が specs をメインリポジトリへ自動的にコミットする
5. 開発者が frontend サブリポジトリのコード変更を手動でコミットする

### AI Agent 設定のサポート

MonoSpecs 方式を使うプロジェクトでは、`AGENTS.md` を通じて、AI Agent にプロジェクト固有のガイダンスを提供できます。

<FileTree>
- your-project/
  - AGENTS.md           # メインリポジトリレベルの Agent 設定
  - repos/
    - frontend/
      - AGENTS.md       # リポジトリ固有の Agent 設定（メイン設定を継承）
    - backend/
      - AGENTS.md       # バックエンドリポジトリの Agent 設定
</FileTree>

各リポジトリの `AGENTS.md` には、次の内容を含められます。

- **技術スタックの説明**：フレームワーク、ビルドツール、状態管理など
- **コード規約**：命名規則、ファイル構成、ベストプラクティス
- **プロジェクト固有の動作**：メインリポジトリの設定に対する拡張や差分
- **OpenSpec との連携**：変更管理のワークフローにどう参加するか

この階層的な設定により、AI Agent は次のことができます：
1. メインリポジトリ全体の規約を理解する
2. 各リポジトリ固有の要件を識別する
3. リポジトリをまたぐ操作でも一貫性を保つ

## ベストプラクティス

### 命名規則

- **リポジトリのパス**：`repos/` プレフィックスを使い、一貫性を保ちます
- **リポジトリ名**：kebab-case（小文字とハイフン）を使います
- **表示名**：簡潔な中国語の名前を使います
- **アイコンの選択**：リポジトリの機能に関連した emoji を使います

### 設定のメンテナンス

1. **設定と実際の状態を同期する**：`.hagicode/monospecs.yaml` が実際のリポジトリ構成を反映していることを、定期的に確認します

## ルートディレクトリの monospecs.yaml からの移行

プロジェクトがまだルートディレクトリの `monospecs.yaml` を使っている場合は、新しい HagiCode のプロジェクトデータディレクトリへ手動で移行してください。

```bash
mkdir -p .hagicode
mv monospecs.yaml .hagicode/monospecs.yaml
git add .hagicode/monospecs.yaml
git rm monospecs.yaml
git commit -m "Move MonoSpecs config to .hagicode"
```

移行後、HagiCode は `.hagicode/monospecs.yaml` だけを読み取ります。ルートディレクトリの `monospecs.yaml` しか残していない場合、そのプロジェクトは MonoSpecs が未設定のものとして扱われ、関連するスクリプトも、それを互換パスとして読み取ることはありません。
2. **バージョン管理**：すべての設定変更をバージョン管理にコミットしてください
3. **ドキュメントの更新**：リポジトリを追加または削除したときに、関連ドキュメントを更新します

### 検証方法

- リポジトリのパスに特殊文字が含まれていないことを確認します
- YAML の構文が正しいことを検証します
