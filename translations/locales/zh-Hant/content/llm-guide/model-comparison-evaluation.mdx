## 評測範圍與方法

- **評測目標**：基於 HagiCode 專案中的真實整合經驗，提供模型選型參考。
- **測試任務類型**：前端元件實作、後端 API 重構、測試案例補全、文件生成。
- **評價維度**：效率完成度（是否能穩定完成任務）與性價比（成本 + 中國大陸可用性）。

- **最近測試時間**：2026-03-08
- **測試週期**：2026-03-01 至 2026-03-08
- **樣本說明**：基於 HagiCode 團隊真實研發任務的感性評估，不代表廠商官方 benchmark。
- **適用邊界**：結論主要適用於本專案目前的工作流程與工程限制，不等同於通用結論。

### 關鍵結論

- 除千問外，其他模型在我們的專案任務中都能在一定程度上達成目標。
- GLM 4.7 及以上（GLM 4.7、GLM 5）整體可以比較順利完成我們的要求。
- GPT 5.3 Codex 與 GPT 5.4 不僅能完成要求，通常還能給出更好的工程實務與實作效果。
- Minimax M2.5 的主要問題是更容易出現程式碼閉合錯誤（例如括號、結構區塊收尾不完整），需要額外複核。

## 性價比評價（經濟成本 + 中國大陸可用性）

按「成本效益比 + 在中國大陸是否能順利使用」優先排序：

1. Minimax M2.5
2. GLM 4.7
3. GLM 5
4. 千問 3.5 / Code Next
5. GPT 5.3 Codex
6. GPT 5.4

> 說明：此排序與效率完成度排序不同，主要反映經濟成本與可取得性的現實限制。

## 選型建議

- **品質優先**：優先 GPT 5.4 / GPT 5.3 Codex。
- **均衡優先**：優先 GLM 5 / GLM 4.7。
- **成本優先**：優先 Minimax M2.5（但要加強程式碼閉合檢查）。
- **落地策略**：建議採用「高品質模型處理關鍵任務 + 高性價比模型處理一般任務」的分層路由。
