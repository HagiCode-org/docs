In the [previous guide](/en-US/blog/2026-11-23-mac-astro-site-claude-github-cloudflare/) you took a clean Mac to a live Astro site on GitHub Pages and Cloudflare. A live site is only half the job: you also need to know whether anyone visits it, what they do, and whether Google can find it.

This guide adds that layer. You will register Google Analytics and Google Search Console, then let Claude wire up tracking, a sitemap, social tags and favicons. Each step ends with a result you can check before you move on.

Here is the whole flow:

1. Create a Google Analytics property and copy its measurement ID.
2. Ask Claude to add Google Analytics to the site, push it, wait for the deployment and prove the tag is live.
3. Confirm in Google Analytics that your visit shows up in real time.
4. Register the site in Google Search Console.
5. Link Search Console to Google Analytics.
6. Ask Claude to design and add event tracking that fits your site, then publish and verify it.
7. Ask Claude to add the basic SEO layer: sitemap, `robots.txt`, canonical links, Open Graph and Twitter tags.
8. Submit the sitemap in Search Console.
9. Ask Claude to polish every page's title, description and keywords, and to generate multi-size favicons with the command-line tools on your Mac.

## Who this guide is for

It is for the person who finished the previous guide: you have an Astro project in a GitHub repository, it deploys on every push to `main`, and it has a public domain. You do not need prior experience with analytics. You do need to be comfortable pasting short prompts into Claude Code and clicking through a few Google pages.

## Prerequisites

- The live Astro site from the previous guide, with its custom domain working. This guide calls the repository `my-astro-site` and the domain `example.com`; replace both with yours.
- A Google account.
- Claude Code installed and logged in, and `gh` logged in (`gh auth status`).
- Access to your domain's DNS. If the domain is on Cloudflare, you already have it.

## Step 1: Create a Google Analytics property and get the measurement ID

Google Analytics 4 (GA4) is organised as an account, which holds one or more properties, which hold data streams. A web site is one web data stream, and the stream has a measurement ID that starts with `G-`.

1. Open [analytics.google.com](https://analytics.google.com) and sign in with your Google account.
2. Click **Start measuring** (or **Admin → Create → Account** if you already use Analytics). Give the account a name such as `My sites`.
3. Create a property. Name it after the site, pick your reporting time zone and currency, and continue through the business questions.
4. When asked for a platform, choose **Web**.
5. Enter your site address (`https://example.com`) and a stream name, and leave **Enhanced measurement** switched on. It records page views, scrolls, outbound clicks and file downloads without any code.
6. Create the stream. Google shows the stream details, including the **Measurement ID**.

Copy the measurement ID. It looks like `G-ABCD123456`. You can find it again later under **Admin → Data collection and modification → Data streams → your stream**.

A measurement ID is not a secret. It is printed in the page source of every site that uses it, so it is safe to commit it to the repository.

Check: you have a measurement ID that starts with `G-`.

## Step 2: Ask Claude to add Google Analytics

Start Claude in the project folder:

```bash
cd ~/Sites/my-astro-site
claude
```

Then give it one request that contains the whole job, including pushing and verifying. The more precisely you describe the end state, the less you need to correct afterwards.

```text
Add Google Analytics 4 to this Astro site. The measurement ID is G-ABCD123456.

Requirements:
- Put the gtag.js loader and the config call in the shared layout's <head>, so every page has it exactly once.
- Use plain inline scripts (is:inline) so that window.gtag is a real global function. Astro bundles ordinary <script> tags into modules, which would hide gtag from later code.
- Only render the tag in production builds, not in `npm run dev`.
- Read the measurement ID from one constant or an environment variable, not from scattered copies.
- Run `npm run build` and check that dist/index.html contains the tag.

When the build passes, commit with a clear message and push to main. Then wait for both deployments, the GitHub Pages workflow and the Cloudflare build, to finish. Finally fetch https://example.com/ with curl and confirm that the live HTML contains the measurement ID. Report what you checked.
```

Claude should produce a snippet close to this in your layout:

```astro
---
const GA_ID = 'G-ABCD123456';
const isProd = import.meta.env.PROD;
---
<head>
  {isProd && (
    <>
      <script is:inline async src={`https://www.googletagmanager.com/gtag/js?id=${GA_ID}`}></script>
      <script is:inline define:vars={{ GA_ID }}>
        window.dataLayer = window.dataLayer || [];
        window.gtag = function () { dataLayer.push(arguments); };
        gtag('js', new Date());
        gtag('config', GA_ID);
      </script>
    </>
  )}
</head>
```

Two details are worth understanding, because they are the most common reasons for "I added the tag but nothing happens".

- **`window.gtag` must be a global.** A tag that works for page views can still leave `window.gtag` undefined if the script is wrapped in a closure. Page views would still arrive, but every custom event you add in step 6 would silently fail. Assigning to `window.gtag` explicitly avoids this.
- **Production only.** If the tag also runs on `localhost`, your own development clicks pollute the data.

While Claude waits for the deployment, it will use commands like these:

```bash
gh run watch
curl -s https://example.com/ | grep -o 'googletagmanager.com/gtag/js?id=G-[A-Z0-9]*'
```

`gh run watch` follows the GitHub Actions run until it finishes. The `curl` line prints the loader URL only if the live page really contains it.

Check: Claude's report shows a successful run on both hosts and the measurement ID found in the live HTML. If the `curl` output is empty, the deployment has not finished or a cache is serving the old page; ask Claude to retry after a minute, and to purge the Cloudflare cache if the old page persists.

## Step 3: Verify in Google Analytics that the site is online

Now confirm from Google's side, not just yours.

1. Open `https://example.com` in a browser. If you use an ad blocker or a privacy browser, turn it off for this check; they block Google Analytics.
2. In Google Analytics, open **Reports → Realtime**.
3. Within about a minute, you should see **1 user in the last 30 minutes** and a `page_view` event in the event list.
4. Click through two or three pages. The page titles appear in the Realtime view.

You can also open **Admin → Data streams → your stream**. A green check and the message that data is flowing means the stream is receiving traffic.

Check: your own visit appears in **Realtime**. Standard reports such as **Acquisition** lag by several hours up to a day, so do not worry if they are still empty.

## Step 4: Register the site in Google Search Console

Google Analytics tells you what visitors do after they arrive. Google Search Console tells you how Google sees your site: which queries bring people, which pages are indexed, and what errors Google found.

1. Open [search.google.com/search-console](https://search.google.com/search-console) and sign in with the same Google account you use for Analytics. Using the same account makes linking easy later.
2. Click **Add property**. You see two types.
   - **Domain** covers `example.com` and every subdomain and protocol. It needs a DNS record.
   - **URL prefix** covers one exact address such as `https://example.com/`. It offers several verification methods.
3. Choose **Domain** if your DNS is on Cloudflare. Enter `example.com`.
4. Search Console shows a `TXT` record. Copy the value, which starts with `google-site-verification=`.
5. In the Cloudflare dashboard, open your domain, go to **DNS → Records → Add record**. Choose type `TXT`, name `@`, paste the value as the content, and save.
6. Return to Search Console and click **Verify**. DNS changes usually apply within minutes, but can take longer. If verification fails, wait and click **Verify** again.

If you chose the **URL prefix** type instead, the easiest method is the Google Analytics one: Search Console can accept the tag you installed in step 2 as proof of ownership, as long as you use the same Google account.

Check: Search Console shows "Ownership verified" and opens the property's overview page. It will show "No data yet" for a while; that is expected.

## Step 5: Link Search Console to Google Analytics

Linking brings search queries and landing-page performance into Analytics reports, so you can see traffic from search next to what those visitors did.

1. In Google Analytics, open **Admin**.
2. Under **Product links**, choose **Search Console links**.
3. Click **Link**, then **Choose accounts**, and select your Search Console property. You need to be an owner of the Search Console property and an editor of the Analytics property.
4. Click **Next**, choose the web data stream, then **Submit**.

Search Console data takes a few days to start flowing, and it arrives with a delay of about two days. There is nothing to wait for here, so continue with the next step.

After the link is created, find the reports in **Reports → Library**. Search Console reports are not added to the left menu automatically. Publish the **Search Console** collection from the library when you want them in the menu.

Check: **Admin → Product links → Search Console links** lists your property.

## Step 6: Add event tracking that matches your site

Enhanced measurement already records page views, scrolls, outbound link clicks, site search and file downloads. Do not rebuild these. Events are for things that are specific to your business: a click on your main call to action, a newsletter sign-up, a contact form, a pricing-page view.

The most useful instruction is not "add some events". It is "look at my site, propose an event plan, and let me approve it". That keeps you in control of what you measure.

```text
Look at the structure of this Astro site: its pages, layouts, components, calls to action, forms and outbound links.

Step 1. Propose an event plan before changing any code. Give me a table with: event name, when it fires, parameters, and the business question it answers. Prefer GA4's recommended event names where one fits (for example generate_lead, sign_up, select_content), and use snake_case custom names otherwise. Do not duplicate what Enhanced measurement already tracks: page views, scrolls, outbound clicks, file downloads. Keep it to 10 events or fewer.

Step 2. After I approve, implement the plan:
- Mark elements with data-ga-event, data-ga-label and data-ga-location attributes.
- Use one delegated click listener on the document that reads those attributes and calls gtag('event', ...). Do not add inline onclick handlers.
- Send only stable ids and locations as parameters. Never send link text, form input, e-mail addresses or anything that identifies a visitor.
- Do not delay or cancel navigation.

Step 3. Run the build, commit, push, wait for both deployments, and verify with curl that the live site contains the listener script. Then tell me exactly which clicks I should try so I can verify them in GA4 DebugView.
```

Claude will first answer with a table. A plausible plan for a small site looks like this:

| Event | Fires when | Parameters | Question it answers |
| --- | --- | --- | --- |
| `cta_click` | A visitor clicks a main call-to-action button | `label`, `location` | Which buttons and which page areas bring action? |
| `generate_lead` | A contact form is submitted successfully | `form_id` | How many visitors become contacts? |
| `nav_click` | A header or footer link is clicked | `label`, `location` | Which navigation items are used? |
| `theme_toggle` | The theme switch is used | `value` | Is the dark mode switch worth keeping? |

Read the table critically. Remove events nobody will look at, and rename anything that names a feature instead of a decision. Then reply "Approved, but drop `theme_toggle`" and let it implement.

The listener Claude writes will look roughly like this:

```js
document.addEventListener(
  'click',
  (event) => {
    const el = event.target.closest('[data-ga-event]');
    if (!el || typeof window.gtag !== 'function') return;
    window.gtag('event', el.dataset.gaEvent, {
      label: el.dataset.gaLabel,
      location: el.dataset.gaLocation,
      transport_type: 'beacon',
    });
  },
  true,
);
```

And a tagged button:

```astro
<a href="/contact" data-ga-event="cta_click" data-ga-label="hero_contact" data-ga-location="home_hero">
  Contact us
</a>
```

### Verify the events

1. In Google Analytics, open **Admin → Data display → DebugView**. DebugView shows events as they arrive, within seconds.
2. To get your browser into debug mode, install the Chrome extension **Google Analytics Debugger**, or ask Claude to add `debug_mode: true` to the `config` call temporarily.
3. Visit the live site and perform the clicks Claude listed.
4. Each click should appear as an event in the DebugView timeline, with the parameters you expect.

After the events have arrived once, they also show up in **Admin → Data display → Events**. If you want to use `label` or `location` in standard reports, register them under **Admin → Data display → Custom definitions → Create custom dimension** with the scope **Event**. Only parameters registered this way appear in standard reports.

Remove any temporary `debug_mode` setting, then ask Claude to push the clean version.

Check: each tracked click appears in DebugView with the right event name and parameters, and the final code is on `main`.

## Step 7: Add the basic SEO layer

Search engines need a map of your pages, instructions about what to crawl, and descriptions that people see when a page is shared. Astro has an official integration for the first, and the rest is a few lines in the layout. Claude is allowed to add Astro components and integrations to do this quickly.

```text
Add the basic SEO foundation to this Astro site.

1. Sitemap: install the official @astrojs/sitemap integration with `npx astro add sitemap`. Make sure `site` in astro.config.mjs is the production origin https://example.com, and remove any `base` left over from GitHub Pages project hosting.
2. robots.txt: create src/pages/robots.txt.ts that returns "User-agent: *", "Allow: /" and a Sitemap line pointing to https://example.com/sitemap-index.xml, built from the `site` setting rather than hard-coded.
3. A reusable SEO component, used by the shared layout, that renders: the <title>; the meta description; a canonical link built from the current URL and `site`; Open Graph tags (og:type, og:title, og:description, og:url, og:image, og:site_name, og:locale); Twitter card tags (twitter:card summary_large_image, twitter:title, twitter:description, twitter:image); and a theme-color meta tag. Every page passes its own title and description as props.
4. A default 1200x630 social image at public/og-default.png, used when a page does not provide one.
5. JSON-LD structured data for the site as a WebSite object, plus an Article object on blog posts if the site has any.
6. Run `npm run build`, then list dist/sitemap-index.xml, show dist/robots.txt, and confirm that the built HTML for the home page contains all the tags above.

When all of that is correct, commit, push, wait for both deployments, and use curl to confirm https://example.com/sitemap-index.xml and https://example.com/robots.txt both return 200 with the right content.
```

Why each part matters:

- **Sitemap.** `@astrojs/sitemap` writes `sitemap-index.xml` and one or more `sitemap-0.xml` files at build time, and it needs the `site` setting to build absolute URLs.
- **`robots.txt`.** It tells crawlers what they may fetch and where the sitemap is. A page that you want out of the index belongs under `noindex`, not only in `robots.txt`.
- **Canonical link.** It tells Google which URL is the official one when the same page is reachable in several ways.
- **Open Graph and Twitter tags.** They control the title, description and image when a link is shared on social networks or chat apps.
- **JSON-LD.** Structured data helps search engines understand what a page is. It does not guarantee rich results, but it is cheap to add.

Check: the live `sitemap-index.xml` lists your pages, `robots.txt` contains the `Sitemap:` line, and a page's source shows the canonical, Open Graph and Twitter tags. You can also paste a URL into a social card validator, or share it in a chat app, to see the preview.

## Step 8: Submit the sitemap in Search Console

Search Console does not know your sitemap exists until you tell it.

1. In Search Console, open your property and choose **Sitemaps** in the left menu.
2. Under **Add a new sitemap**, enter `sitemap-index.xml`.
3. Click **Submit**.
4. The status should change to **Success** with the number of discovered pages. If it says **Couldn't fetch**, open the sitemap URL in a browser first; if it loads, wait a few minutes and refresh, because the first fetch can lag.

Next, ask Google to look at your most important page right away:

1. Paste your home page URL into the search bar at the top of Search Console.
2. Click **Request indexing** if the page is not indexed yet.

Indexing still takes days, and Search Console reports lag too. Check back in a week.

Check: **Sitemaps** lists `sitemap-index.xml` with status **Success**.

## Step 9: Polish every page's metadata and add multi-size favicons

The basic layer gives every page generic metadata. Titles and descriptions are the text people read in search results, so they deserve per-page attention. Favicons need several sizes because browsers, phones and bookmarks each ask for a different one.

### Titles, descriptions and keywords

```text
Review every page of this site and improve its search metadata.

For each page, give me a before/after table with the title, meta description and keywords, then apply it. Rules:
- Title: unique per page, under about 60 characters, the primary topic first, the site name last.
- Description: unique per page, 120 to 160 characters, a plain sentence that says what the visitor gets and invites a click. No keyword stuffing, no copied text between pages.
- Keywords: a short list of 5 to 8 terms taken from the real page content. Keep the keywords meta tag only if the layout already supports it; do not invent topics the page does not cover.
- Check that each page has exactly one <h1> that matches its title in meaning, and that every image has an alt attribute.

Then run the build and write a short report listing any two pages that still share a title or a description.
```

Keep one expectation straight: search engines largely ignore the keywords meta tag. Keywords help you, because writing them forces you to name what each page is about. The title and the description are what appear in results.

### Favicons for every size

A single `favicon.svg` is a good start, but several places want specific files: `favicon.ico` for older browsers and bookmarks, an `apple-touch-icon` for iOS home screens, and 192 and 512 pixel PNGs for Android and web app manifests.

macOS has `sips` for resizing PNGs, built in. For `.ico` you need ImageMagick, which Homebrew installs. Ask Claude to use them directly on your Mac:

```text
Generate a complete favicon set from my source image public/logo-source.png (a square PNG of at least 512x512).

1. Use the macOS `sips` command to create public/icon-192.png, public/icon-512.png and public/apple-touch-icon.png (180x180).
2. If ImageMagick is missing, install it with `brew install imagemagick`. Use `magick` to build public/favicon.ico containing 16x16, 32x32 and 48x48 images.
3. If I have a public/favicon.svg already, keep it. If I do not, create a simple one that matches the logo.
4. Add public/site.webmanifest that lists icon-192.png and icon-512.png.
5. Update the layout <head> with the matching <link> tags: the SVG icon, the .ico fallback, the apple-touch-icon and the manifest.
6. Run `file` on every generated image to confirm its real dimensions, run the build, and make sure the files end up in dist/.
```

The commands Claude runs are close to these:

```bash
sips -z 192 192 public/logo-source.png --out public/icon-192.png
sips -z 512 512 public/logo-source.png --out public/icon-512.png
sips -z 180 180 public/logo-source.png --out public/apple-touch-icon.png
brew install imagemagick
magick public/logo-source.png -define icon:auto-resize=48,32,16 public/favicon.ico
file public/*.png public/favicon.ico
```

and the head links look like this:

```html
<link rel="icon" href="/favicon.svg" type="image/svg+xml" />
<link rel="icon" href="/favicon.ico" sizes="48x48" />
<link rel="apple-touch-icon" href="/apple-touch-icon.png" />
<link rel="manifest" href="/site.webmanifest" />
```

Finally, close the loop in the same way as every other step:

```text
Commit everything with a clear message, push to main, wait for both deployments, and verify with curl that /favicon.ico, /apple-touch-icon.png and /site.webmanifest return 200 on the live site.
```

Check in a browser: the tab shows your icon, and a bookmark or an iOS "Add to Home Screen" uses the large one. Browsers cache favicons aggressively, so open the site in a private window if you still see the old one.

## What to check after a week

- **Search Console → Pages** shows how many of your pages are indexed and why others are not.
- **Search Console → Performance** shows queries, clicks and average position. Use the queries to improve titles and descriptions.
- **Analytics → Reports → Engagement → Events** shows how often your custom events fire.
- **Analytics → Reports → Library** is where the Search Console collection appears once data has arrived.

## Troubleshooting

- **Realtime shows nothing.** An ad blocker or a privacy browser is blocking the tag. Test in a private window with extensions off, and confirm the measurement ID in the live HTML.
- **Page views work but custom events do not.** Open the browser console on the live site and run `typeof window.gtag`. It must print `function`. If it prints `undefined`, the tag script is bundled as a module; ask Claude to use `is:inline` and to assign `window.gtag` explicitly.
- **Events appear in DebugView but not in reports.** Standard reports lag by up to a day, and custom parameters only show up in reports after you register them as custom dimensions.
- **Search Console cannot verify the domain.** Check that the `TXT` record is on the root (`@`), that the value is copied whole, and that Cloudflare's proxy is not involved (TXT records are not proxied). Then wait and retry.
- **Sitemap says "Couldn't fetch".** Open `https://example.com/sitemap-index.xml` yourself. If it returns 404, check that `site` in `astro.config.mjs` is the production origin and that the sitemap integration is listed in `integrations`.
- **Social previews are stale.** Platforms cache previews. Use their debugger tools to refresh the cache after you change tags.

## Privacy and consent

Analytics collects data about visitors. Depending on where your visitors live, you may need to ask for consent before loading Google Analytics, for example under the EU's GDPR and the ePrivacy rules, and you may need to state it in a privacy policy. This guide installs the tag unconditionally to keep the steps short. If your site has visitors from regions that require consent, ask Claude to add a consent banner that loads the tag only after the visitor agrees. This is general information, not legal advice.

## The loop to keep

Every step here followed the same pattern, and it is the habit worth keeping: describe the end state to Claude, let it make the change, make it push and wait for the deployment, make it prove the result on the live site with `curl`, and then confirm from the external tool, such as Google Analytics or Search Console. Whenever you add a feature, repeat the same cycle.
