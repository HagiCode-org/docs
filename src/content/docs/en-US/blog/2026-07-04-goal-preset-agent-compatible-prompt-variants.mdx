## How We Use impeccable to Improve Frontend Interface Design and Implementation Stability

## Introduction

Many teams share the same pain point when building UI: design language depends on experience, interaction details depend on memory, and the result is often "works, but isn't stable."

In the HagiCode monorepo, `impeccable` is not used as an "inspiration tool." Instead, it is placed inside an executable, verifiable, and regression-testable engineering pipeline:

- Task entry points have structured constraints (commands, scenes, repository scope)
- Site content and upstream command definitions are automatically aligned
- Local development ports, runtime parameters, and validation workflows are fixed

This article is based on the existing implementation in the repository and is split into four parts: Background, Analysis, Solution, and Practice.

## Background

In the current repository snapshot, the main lines directly related to `impeccable` are mainly in three places:

1. **Static site runtime orchestration**: `scripts/static-sites-dev.mjs`
2. **impeccable documentation site**: `repos/impeccable-site`
3. **UI task preset contract example**: `designs/task-preset-plugin-examples/ui-master`

The third item is a design example, not the body of the online backend runtime code. This needs to be made clear first, so that the "design contract" is not mistaken for "published behavior."

## Analysis

### 1) Structure design intent first to reduce "free-form" drift

In the backend contract example for `ui-master`, dependencies and inputs are fixed before execution begins.

`designs/task-preset-plugin-examples/ui-master/backend/task-preset.json`:

```json
{
  "taskKey": "uiMaster",
  "scriptKey": "autotask.ui-master",
  "requirements": [
    {
      "type": "skills",
      "name": "impeccable"
    },
    {
      "type": "cli",
      "name": "impeccable",
      "command": "npm",
      "args": ["exec", "--offline", "--", "impeccable", "--help"]
    }
  ],
  "inputBindings": [
    {
      "input": "uiMasterDescription",
      "promptParameter": "uiMasterDescription",
      "required": true
    },
    {
      "input": "uiMasterCommandIds",
      "promptParameter": "uiMasterCommandIds",
      "required": true
    },
    {
      "input": "sceneKey",
      "promptParameter": "sceneKey"
    }
  ]
}
```

Key points:

- Validate `skills:impeccable` and `cli:impeccable` first, so that a broken chain is not discovered only during execution.
- `uiMasterCommandIds` forces command-based input, which avoids "a long description with an unclear direction."
- `sceneKey` unifies the scene key, so each preset does not invent its own set of input names.

The value of this structure for stability is direct: failures happen early, failures are explainable, and inputs can be replayed.

### 2) Unify the command catalog and documentation routing to reduce semantic drift

`designs/task-preset-plugin-examples/ui-master/frontend/commands.json` defines command groups, documentation route templates, and command preludes:

```json
{
  "docs": {
    "baseUrl": "https://impeccable.hagicode.com",
    "routeTemplate": "/{lang}/docs/{commandId}",
    "languageResolver": "supported-language"
  },
  "commands": [
    {
      "id": "craft",
      "groupId": "build",
      "skill": "impeccable",
      "docsSlug": "craft",
      "preludeTemplate": "/impeccable {commandId} {uiMasterDescription}"
    }
  ]
}
```

This allows "command execution, documentation explanation, and language routing" to share the same set of IDs, which reduces common mismatches:

- The docs call it A, while the panel calls it B
- A Chinese page links to the wrong English command
- The prompt prelude and the docs slug do not match

### 3) Make content correctness a verifiable asset in the site implementation

In `repos/impeccable-site/package.json`, `validate` chains the entire quality gate:

```json
{
  "scripts": {
    "validate": "npm run i18n:check && npm run catalog:check && npm run typecheck && npm run test && npm run build"
  }
}
```

In addition, the script behind `catalog:check` (`scripts/build-command-catalog.mjs`) performs strict validation on the frontmatter structure:

```js
function parseFrontmatter(sourceText, sourcePath) {
  const match = sourceText.match(/^---\n([\s\S]*?)\n---\n?([\s\S]*)$/u);
  assert(match, `${sourcePath} must include YAML frontmatter`);
  const frontmatter = load(match[1]);
  assert(isPlainObject(frontmatter), `${sourcePath} frontmatter must be a mapping`);
  return {
    frontmatter,
    body: match[2].trim(),
  };
}
```

These asserts are simple, but they are especially critical for stability: it is better to fail directly locally and in CI than to discover a missing field in the documentation after release.

### 4) Fix development ports and env to avoid "it runs on my machine but not yours"

In the monorepo root script `scripts/static-sites-dev.mjs`, `impeccable` is explicitly orchestrated:

```js
{
  id: 'impeccable',
  name: 'Impeccable',
  repoPath: 'repos/impeccable-site',
  productionUrl: 'https://impeccable.hagicode.com/',
  command: 'npm',
  args: ['run', 'dev'],
  env: {
    PORT_IMPECCABLE_SITE: '36296'
  },
  portHint: 36296,
  order: 56
}
```

The test `scripts/static-sites-dev.test.mjs` also asserts these values (port, args, env, productionUrl).

This "hard-coded + tested" approach is not flashy, but it is stable:

- The local entry point is unified
- The troubleshooting path is fixed
- Documentation site links do not drift unpredictably

## Solution

If you want to use `impeccable` to improve both **interface quality** and **implementation stability** at the same time, the existing repository practice can be organized into four layers.

### Layer 1: Make task entry points contractual

Approach: reuse a preset structure like `ui-master`.

Goals:

- Limit the allowed repository scope (`targetRepositories`)
- Limit the command source (`uiMasterCommandIds`)
- Limit the context entry point (`uiMasterDescription`)

Benefit: every dispatch can be reviewed later in terms of "what the input was and why the change was made this way."

### Layer 2: Unify command semantics

Approach: bind together the command ID, docs slug, and prelude template.

Goals:

- A command selected in the panel can jump to the documentation with the same ID
- `/impeccable <command>` in the prompt and the documentation explanation are consistent

Benefit: reduces the hidden risk of "consistent terminology, inconsistent behavior."

### Layer 3: Make content asset validation systematic

Approach: keep `npm run validate` as the pre-commit gate.

Goals:

- No missing i18n keys
- The command catalog and upstream structure do not drift
- Types, tests, and build all pass once

Benefit: problems with content are caught locally at an early stage.

### Layer 4: Standardize the development runtime environment

Approach: start everything uniformly through `static-sites-dev`, with `PORT_IMPECCABLE_SITE` fixed.

Goals:

- Minimize port conflicts in multi-person collaboration
- Keep the multi-site integration path fixed

Benefit: saves time on environment setup and lets problems be traced to the code itself more quickly.

## Practice

```bash

```

### Step 2: Local development and full validation

```bash
env -u NPM_CONFIG_PREFIX npm run dev
env -u NPM_CONFIG_PREFIX npm run validate
```

`validate` covers i18n, catalog, typecheck, test, and build in one pass.

### Step 3: Run through the monorepo unified orchestration

From the monorepo root, use the `scripts/static-sites-dev.mjs` system and reuse the defined `PORT_IMPECCABLE_SITE=36296`.

The point of this step is not "it can run," but "everyone runs it in the same way."

### Step 4: Turn UI requests into command-based input

In the task preset flow, prefer turning requirements into:

- `uiMasterDescription`: the business goal
- `uiMasterCommandIds`: the commands for this round (such as `craft`, `audit`, `polish`)
- `sceneKey`: the scene context

Then enter the change phase, which reduces "directly changing the UI and drifting in direction."

## HagiCode Overview

HagiCode is a platform-oriented project that integrates multi-repository engineering, AI task execution, documentation sites, and toolchains. Its core capability is not the single point of "being able to generate code," but connecting task input constraints, execution context, validation gates, and cross-repository collaboration into one stable pipeline. Typical use cases include: structured UI iteration, cross-repository feature integration, specification-driven technical content production, and automated delivery with quality gates.

## Summary

The real value of `impeccable` is not in "helping you think of a nicer button," but in "engineering the work of interface optimization." In HagiCode's existing practice, this is accomplished through four actions: contractualizing tasks, unifying command semantics, front-loading content validation, and standardizing the runtime environment. Solidify these foundations first, and then pursue more striking design enhancements. The return is greater, and more sustainable.
