## Как мы используем impeccable для оптимизации дизайна фронтенд-интерфейсов и стабильности реализации

## Введение

Многие команды сталкиваются с одной и той же проблемой при работе над UI: язык дизайна держится на опыте, детали взаимодействия держатся в памяти, и в итоге результат легко получается «работающим, но нестабильным».

В монорепозитории HagiCode `impeccable` используется не как «инструмент для вдохновения», а встроен в исполнимую, проверяемую и регрессионно тестируемую инженерную цепочку:

- На входе задачи есть структурированные ограничения (команды, сценарии, область репозиториев)
- Содержимое сайта и определения команд upstream выравниваются автоматически
- Порты локальной разработки, параметры запуска и процесс проверки зафиксированы

Эта статья опирается на существующую реализацию в репозитории и разделена на четыре части: Background, Analysis, Solution, Practice.

## Фон (Background)

В текущем снимке репозитория основная связь с `impeccable` находится в трёх местах:

1. **Оркестрация запуска статических сайтов**: `scripts/static-sites-dev.mjs`
2. **Документационный сайт impeccable**: `repos/impeccable-site`
3. **Пример контракта UI task preset**: `designs/task-preset-plugin-examples/ui-master`

Третий пункт — это пример дизайна, а не сам код бэкенда, работающий в продакшене. Это важно прояснить сразу, чтобы не принять «контракт дизайна» за «опубликованное поведение».

## Анализ (Analysis)

### 1) Сначала структурируем намерение дизайна, чтобы уменьшить дрейф из-за «свободной импровизации»

В примере контракта бэкенда `ui-master` зависимости и входные данные фиксируются до того, как начинается выполнение.

`designs/task-preset-plugin-examples/ui-master/backend/task-preset.json`:

```json
{
  "taskKey": "uiMaster",
  "scriptKey": "autotask.ui-master",
  "requirements": [
    {
      "type": "skills",
      "name": "impeccable"
    },
    {
      "type": "cli",
      "name": "impeccable",
      "command": "npm",
      "args": ["exec", "--offline", "--", "impeccable", "--help"]
    }
  ],
  "inputBindings": [
    {
      "input": "uiMasterDescription",
      "promptParameter": "uiMasterDescription",
      "required": true
    },
    {
      "input": "uiMasterCommandIds",
      "promptParameter": "uiMasterCommandIds",
      "required": true
    },
    {
      "input": "sceneKey",
      "promptParameter": "sceneKey"
    }
  ]
}
```

Ключевые моменты:

- Сначала проверяются `skills:impeccable` и `cli:impeccable`, чтобы не обнаружить разрыв цепочки уже во время выполнения.
- `uiMasterCommandIds` делает вход командным, чтобы избежать ситуации «описание длинное, а направление неясно».
- `sceneKey` задаёт единый ключ сценария, чтобы каждый preset не придумывал собственный набор имён входов.

Ценность этой структуры для стабильности прямая: сбои обнаруживаются заранее, их легко объяснить, а входные данные можно воспроизвести.

### 2) Унифицируем каталог команд и маршрутизацию документации, чтобы уменьшить семантический дрейф

`designs/task-preset-plugin-examples/ui-master/frontend/commands.json` определяет группы команд, шаблоны маршрутов документации и префиксы команд (prelude):

```json
{
  "docs": {
    "baseUrl": "https://impeccable.hagicode.com",
    "routeTemplate": "/{lang}/docs/{commandId}",
    "languageResolver": "supported-language"
  },
  "commands": [
    {
      "id": "craft",
      "groupId": "build",
      "skill": "impeccable",
      "docsSlug": "craft",
      "preludeTemplate": "/impeccable {commandId} {uiMasterDescription}"
    }
  ]
}
```

Это позволяет использовать один и тот же набор ID для выполнения команд, документации и языковой маршрутизации, что снижает типичные рассогласования:

- В документации команда называется A, а на панели — B
- Страница на китайском ведёт по ссылке на неверную команду на английском
- Prelude в промпте и slug документации не совпадают

### 3) Делаем корректность содержимого проверяемым артефактом сайта

В `repos/impeccable-site/package.json` команда `validate` объединяет весь контур контроля качества:

```json
{
  "scripts": {
    "validate": "npm run i18n:check && npm run catalog:check && npm run typecheck && npm run test && npm run build"
  }
}
```

А скрипт за `catalog:check` (`scripts/build-command-catalog.mjs`) жёстко проверяет структуру frontmatter:

```js
function parseFrontmatter(sourceText, sourcePath) {
  const match = sourceText.match(/^---\n([\s\S]*?)\n---\n?([\s\S]*)$/u);
  assert(match, `${sourcePath} must include YAML frontmatter`);
  const frontmatter = load(match[1]);
  assert(isPlainObject(frontmatter), `${sourcePath} frontmatter must be a mapping`);
  return {
    frontmatter,
    body: match[2].trim(),
  };
}
```

Такие assert простые, но для стабильности они очень важны: лучше упасть локально и в CI, чем обнаружить после публикации, что в документе не хватает поля.

### 4) Фиксируем порты и env для разработки, чтобы не было «у меня работает, у тебя нет»

В корневом скрипте монорепозитория `scripts/static-sites-dev.mjs` `impeccable` оркестрируется явно:

```js
{
  id: 'impeccable',
  name: 'Impeccable',
  repoPath: 'repos/impeccable-site',
  productionUrl: 'https://impeccable.hagicode.com/',
  command: 'npm',
  args: ['run', 'dev'],
  env: {
    PORT_IMPECCABLE_SITE: '36296'
  },
  portHint: 36296,
  order: 56
}
```

Тест `scripts/static-sites-dev.test.mjs` также проверяет эти значения (порт, args, env, productionUrl).

Подход «зафиксировать и покрыть тестами» не выглядит эффектно, но он надёжен:

- Точка входа для локальной работы единая
- Путь диагностики проблем фиксирован
- Ссылки на документационный сайт не расползаются

## Решение (Solution)

Если вы хотите использовать `impeccable` одновременно для **качества интерфейса** и **стабильности реализации**, в существующей практике репозитория это можно выстроить в четыре уровня.

### Первый уровень: контрактизация входа задачи

Способ: переиспользовать структуру preset, например `ui-master`.

Цели:

- Ограничить допустимую область репозиториев (`targetRepositories`)
- Ограничить источник команд (`uiMasterCommandIds`)
- Ограничить вход контекста (`uiMasterDescription`)

Выгода: каждое назначение можно разобрать позже — что было на входе и почему изменение сделано именно так.

### Второй уровень: унификация семантики команд

Способ: связать три элемента — ID команды, docs slug и prelude template.

Цели:

- Команда, выбранная на панели, ведёт к документации с тем же ID
- `/impeccable <command>` в промпте и объяснение в документации совпадают

Выгода: снижается скрытый риск «термины совпадают, а поведение нет».

### Третий уровень: превращение проверки содержимого в процесс

Способ: использовать `npm run validate` как барьер перед коммитом.

Цели:

- Отсутствующие ключи i18n не проходят незамеченными
- Каталог команд и структура upstream не расходятся
- Типы, тесты и сборка проходят за один запуск

Выгода: «случайные проблемы с содержимым» выявляются ещё на локальной машине.

### Четвёртый уровень: стандартизация среды разработки

Способ: запускать всё через `static-sites-dev` и фиксировать `PORT_IMPECCABLE_SITE`.

Цели:

- Минимизировать конфликты портов при совместной работе
- Сделать путь совместной отладки нескольких сайтов предсказуемым

Выгода: меньше времени на настройку окружения, а проблемы быстрее локализуются в самом коде.

## Практика (Practice)

### Шаг 1: инициализация impeccable-site

```bash
cd /home/newbe36524/repos/hagicode-mono/repos/impeccable-site
git submodule update --init --recursive
env -u NPM_CONFIG_PREFIX npm install
```

### Шаг 2: локальная разработка и общая проверка

```bash
env -u NPM_CONFIG_PREFIX npm run dev
env -u NPM_CONFIG_PREFIX npm run validate
```

`validate` за один запуск покрывает i18n, catalog, typecheck, test и build.

### Шаг 3: запуск через общую оркестрацию монорепозитория

Из корня монорепозитория используйте систему `scripts/static-sites-dev.mjs` и применяйте уже определённый `PORT_IMPECCABLE_SITE=36296`.

На этом шаге важно не то, что «всё запустилось», а то, что «все запускают это одинаковым образом».

### Шаг 4: превращение запроса UI в команды

В потоке task preset лучше сразу оформлять требования в виде:

- `uiMasterDescription`: бизнес-цель
- `uiMasterCommandIds`: команды для этого изменения (например, `craft`, `audit`, `polish`)
- `sceneKey`: контекст сценария

Только после этого переходите к изменениям — так будет меньше смещения направления из-за прямого редактирования UI.

### Шаг 5: зафиксировать текущие пробелы в материалах

Исходя из текущего снимка репозитория, можно подтвердить следующее:

- Сайт `impeccable-site` и цепочка проверки представлены рабочим кодом.
- Глубокая связка `ui-master` с `impeccable` в основном выражена в `designs/task-preset-plugin-examples` и в проектной документации.

Если вы собираетесь утверждать, что это полностью включено в продакшен-бэкенде, текущих доказательств недостаточно — пока не делайте такого вывода.

## Информация о HagiCode

HagiCode — это платформа, которая объединяет многорепозиторный инжиниринг, выполнение задач с ИИ, документационные сайты и инструменты разработки. Её ключевая ценность не в отдельной возможности «генерировать код», а в том, что ограничения на входе задач, контекст выполнения, барьеры проверки и координация между репозиториями выстроены в единый стабильный конвейер. Типичные сценарии использования: структурированные итерации UI, совместная отладка функций между репозиториями, производство технического контента по стандартам и автоматизированная поставка с контролем качества.

## Заключение

Настоящая ценность `impeccable` не в том, что он помогает придумать более красивую кнопку, а в том, что он превращает оптимизацию интерфейса в инженерный процесс. В практике HagiCode это достигается четырьмя действиями: контрактизация задач, унификация семантики команд, проверка содержимого до этапа релиза и стандартизация среды запуска. Сначала стоит укрепить эти основы, и только потом переходить к более сложным улучшениям дизайна — так отдача будет выше и устойчивее.
