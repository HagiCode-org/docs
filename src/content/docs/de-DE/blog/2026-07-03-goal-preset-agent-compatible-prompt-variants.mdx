## Jeder Agent kann `/goal`: Kompatibles Erweiterungsdesign für HagiCodes Voreinstellung für dauerhaftes Arbeiten

## Einleitung

Einem KI-Agenten eine Aufgabe zum „dauerhaften Arbeiten" zu übergeben, sieht im Idealfall so aus: Du schreibst ein Ziel, wählst die Repositories aus, die verändert werden dürfen, klickst auf Absenden, und der Agent arbeitet sich Schritt für Schritt auf dieses Ziel zu, ohne zwischendurch nachzufragen, abzuschweifen oder andere Repositories zu verändern.

In HagiCode gibt es dafür einen eigenen Einstieg: die Voreinstellungsaufgabe `goal`, deren Befehlsoberfläche `/goal` ist. Das Problem: **Nicht jeder Agent kennt `/goal`.** Claude und Codex haben eine native Semantik für dauerhaftes Arbeiten und können `/goal` direkt verarbeiten. Andere CLIs (Gemini, Copilot, iFlow, OpenCode und weitere) besitzen dagegen gar keinen solchen Slash-Befehl. Wird dort `/goal ...` unverändert übergeben, wird es im besten Fall als ungültiger Befehl abgelehnt und im schlechtesten Fall wortwörtlich ausgeführt, mit entsprechenden Folgen.

Die naheliegendste Lösung war zunächst, `goal` nur auf Claude und Codex laufen zu lassen und alle anderen Agenten abzulehnen. Damit wäre aber ein großer Teil der Agenten-Matrix ausgeschlossen. Dieser Beitrag beschreibt, wie wir den besseren Weg umgesetzt haben: **Mit agentenbewussten Prompt-Varianten erhalten nativ unterstützte Agenten den nativen Befehl, und nicht unterstützte Agenten eine Ausweichanweisung. Das Verhalten ist dadurch abgestimmt und das Erlebnis konsistent.**

Der Inhalt basiert auf dem Preset-Paket `goal` in `repos/hagitask` und auf der Backend-Auswertung in `repos/hagicode-core`.

## Hintergrund

### Was ist `goal`?

`goal` ist ein eingebautes Plugin-Paket für Aufgabenvoreinstellungen unter `repos/hagitask/presets/goal/`. Seine `manifest.json` beschreibt die Plugin-Identität, das Icon, die Lokalisierungspakete sowie die Frontend- und Backend-Ressourcen:

```jsonc
{
  "taskPresetId": "goal",
  "version": "1.0.0",
  "icon": "flag",
  "kind": "custom-executor",
  "status": "experimental",
  "entrypoints": { "menuSurface": "session-create", "drawerId": "goal" },
  "ui": { "panel": "./frontend/panel.json", "commands": "./frontend/commands.json" },
  "backend": {
    "taskPreset": "./backend/task-preset.json",
    "prompts": "./backend/prompts.json"
  }
}
```

Es ist als „Modus für dauerhaftes Arbeiten" konzipiert: Nutzer:innen geben eine Zielbeschreibung (`goalDescription`) ein und können optional einen Bereich festlegen, in dem Repositories beschreibbar oder nur lesbar sind. Das Backend stellt daraus einen nicht-interaktiven Auto-Task-Lauf zusammen. Die zentralen Felder im Frontend-Panel `panel.json` sind:

- `goalCommandIds`: Befehlsauswahl; integriert ist nur `/goal`;
- `goalDescription`: Pflichtfeld für die Zielbeschreibung;
- `targetRepositories`: Auswahl des Repository-Zugriffs, unterschieden nach Lesen und Schreiben.

### Woher kommt `/goal`?

Die Befehlsoberfläche ist in `frontend/commands.json` definiert. Der Kern ist eine einzige Zeile `preludeTemplate`:

```jsonc
{
  "commands": [
    {
      "id": "goal",
      "label": "goal",
      "preludeTemplate": "/goal {goalDescription}"
    }
  ]
}
```

Das heißt, dem eigentlichen Prompt wird eine Zeile `/goal <Zielbeschreibung>` vorangestellt. Für Claude und Codex ist diese Zeile ein Befehl, den sie kennen. Für andere Agenten ist sie etwas, das „übersetzt" werden muss. Die eigentliche Schwierigkeit der Anpassung liegt genau darin, dass diese Zeile `/goal ...` bei verschiedenen Agenten unterschiedliche Bedeutung hat.

## Analyse

### Eine Vorlage pro Sprache reicht nicht mehr

Die frühen Prompt-Pakete von HagiTask waren **nur nach Sprache getrennt**: In `prompts.json` deklarierte jede Locale ein Set aus `systemTemplate` und `userTemplate`. Der `PresetTaskCatalogProvider` im Backend las diese in `PromptPackage.Locales` ein, und zur Laufzeit wurde anhand der Sprache der Anfrage eine Variante gerendert.

Für Voreinstellungen, deren Anweisungen unabhängig vom Agenten sind, genügt dieses Modell. Bei `goal` ist das anders:

- Claude / Codex: können sich direkt auf die native Befehlsoberfläche `/goal` stützen;
- Andere Agenten: brauchen einen ausführlicheren Prompt, der ausdrücklich erklärt, wie in den Modus für dauerhaftes Arbeiten zu wechseln ist, und der ihnen sagt, `/goal ...` nicht als Befehl auszuführen.

Innerhalb derselben Sprache entstehen also zwei grundverschiedene Anweisungen. Eine Trennung nur nach Sprache reicht daher nicht. Wir brauchen eine zusätzliche Dimension neben der Sprache: die **Agenten-Familie**.

### Die Ablehnung ist keine gute Lösung

Ursprünglich beschränkte `requirements` von `goal` den Agenten auf `["claude", "codex"]`, alle anderen wurden als inkompatibel abgelehnt. Das hatte im Produkt zwei Nachteile:

1. Im Auswahlpanel für Hero blieben kaum kompatible Hero übrig, sodass man leicht „keinen Hero zur Auswahl" hatte;
2. Viele Agenten sind durchaus in der Lage, dauerhaft zu arbeiten, sie haben nur keinen nativen `/goal`-Befehl. Eine pauschale Ablehnung verschwendet diese Fähigkeiten.

Das eigentliche Problem war also nicht „wer kann laufen", sondern: **Wie erhält dasselbe Ziel, je nach Fähigkeit des Agenten, unterschiedliche, aber gleichwertige Ausführungsanweisungen?** Die Antwort: Die agentenspezifischen Unterschiede werden in die Prompt-Schicht verlagert und mit Varianten plus Fallback gelöst, statt Personen an der Zulassungsschicht abzuweisen.

## Lösung

### Variantenauswahl: Agent × Sprache

Der neue Vertrag für Prompt-Pakete führt in `prompts.json` `variants` ein. Mit `selectors` werden die Abgleichsdimensionen deklariert, mit `entries` die Abgleichsregeln und Vorlagendateien jeder Variante:

```jsonc
{
  "version": "1.1.0",
  "templateEngine": "handlebars",
  "variants": {
    "selectors": ["agent", "language"],
    "entries": [
      {
        "id": "native-zh-cn",
        "match": { "agent": ["claude", "codex"], "language": ["zh-CN"] },
        "systemTemplate": "./templates/zh-CN/native.system.md",
        "userTemplate": "./templates/zh-CN/native.user.hbs"
      },
      {
        "id": "fallback-zh-cn",
        "match": { "language": ["zh-CN"] },
        "systemTemplate": "./templates/zh-CN/fallback.system.md",
        "userTemplate": "./templates/zh-CN/fallback.user.hbs"
      }
      // ... native-en-us / fallback-en-us 同理
    ],
    "fallback": {
      "id": "fallback-default",
      "systemTemplate": "./templates/en-US/fallback.system.md",
      "userTemplate": "./templates/en-US/fallback.user.hbs"
    }
  }
}
```

Drei Fallback-Stufen, schrittweise gelockert:

1. **native-Variante**: `match` beschränkt sowohl `agent` (claude/codex) als auch `language`; nur native Agenten treffen zu;
2. **fallback-Variante**: `match` beschränkt **nur `language`, nicht `agent`**, sodass jeder Agent trifft. Sie ist der Fallback für Agenten ohne nativen `/goal`;
3. **fallback-default**: letzte Absicherung, wenn selbst die Sprache nicht passt.

Die Reihenfolge ist entscheidend: `entries` werden in deklarierter Reihenfolge durchlaufen, native steht vor fallback. Claude/Codex treffen daher zuerst native; alle anderen Agenten landen bei der sprachbezogenen fallback-Variante.

### Zwei Vorlagen: nativ vs. Ausweichlösung

Bei gleichem Ziel unterscheiden sich die beiden System-Prompts vor allem darin, wie sie mit der Zeile `/goal` umgehen.

Native Vorlage (`templates/zh-CN/native.system.md`):

```text
你是 `goal` task preset plugin 的内置执行提示。

本次运行必须使用 `/goal` 作为持续工作模式的命令表面。把提供的项目路径与仓库范围视为权威工作边界。

这次运行处于非交互环境。不要追问用户；当合理假设可以继续推进时，直接继续并把这些假设明确写在响应里。
```

Ausweichvorlage (`templates/zh-CN/fallback.system.md`):

```text
你是 `goal` task preset plugin 的兜底执行提示。

当前 agent 可能不支持原生 `/goal` 命令。如果提示前面出现了 `/goal ...` 这一行，把它视为预设附带的目标元数据，不要把它当成必须逐字执行的斜杠命令。

请以持续工作模式完成任务，并把提供的项目路径与仓库范围视为权威工作边界。

这次运行处于非交互环境。不要追问用户；当合理假设可以继续推进时，直接继续并把这些假设明确写在响应里。
```

Der entscheidende Satz ist die Seele der Ausweichstrategie: **„Wenn vor dem Prompt eine Zeile `/goal ...` steht, behandle sie als Ziel-Metadaten der Voreinstellung und nicht als Slash-Befehl, der wortwörtlich ausgeführt werden muss."** Die Zeile `/goal <Ziel>`, die zuvor durch `preludeTemplate` angehängt wurde, ist für einen nativen Agenten ein Befehl. Für einen Ausweich-Agenten wird sie ausdrücklich zu „Ziel-Metadaten" herabgestuft. So wird dasselbe dauerhafte Arbeitsverhalten über gewöhnliches Prompt-Following erreicht.

Die User-Vorlagen (`.hbs`) gibt es ebenfalls in zwei Varianten. Die Ausweichvariante enthält zusätzlich einen Abschnitt mit Routing-Hinweis. Er teilt dem Agenten mit, dass er in den Zweig ohne nativen `/goal`-Support geleitet wurde, und verlangt, „nicht auf nativen `/goal`-Support zu vertrauen, sondern dasselbe dauerhafte Arbeitsverhalten über gewöhnliches Prompt-Following umzusetzen."

### Backend: Eine Auswertung entscheidet alles

Der Variantenabgleich findet im Backend in `PCode.Application/Services/PresetTaskCatalogProvider.cs` in `ResolvePromptSelection` statt. Zuerst wird die Locale aufgelöst, dann werden Sprache und Agent in ein Selektor-Wörterbuch gelegt, und die erste passende Variante in Reihenfolge wird gewählt:

```csharp
public PresetTaskResolvedPromptSelection ResolvePromptSelection(string? locale, string? agentFamily)
{
    var resolvedLocale = ResolvePromptLocale(locale);
    if (!PromptPackage.UsesVariants)
    {
        // 旧的仅按 locale 分文件的预设，走遗留路径，保持向后兼容
        var legacyTemplate = PromptPackage.Locales[resolvedLocale];
        return new PresetTaskResolvedPromptSelection(
            resolvedLocale, NormalizeAgentFamily(agentFamily), null, false,
            "legacy-locales", legacyTemplate);
    }

    var normalizedAgentFamily = NormalizeAgentFamily(agentFamily);
    var selectorInputs = new Dictionary<string, string>(StringComparer.OrdinalIgnoreCase)
    {
        [PresetTaskPromptSelectorNames.Language] = resolvedLocale,
    };
    if (!string.IsNullOrWhiteSpace(normalizedAgentFamily))
    {
        selectorInputs[PresetTaskPromptSelectorNames.Agent] = normalizedAgentFamily!;
    }

    foreach (var variant in PromptPackage.Variants)
    {
        if (!VariantMatches(variant, selectorInputs)) continue;
        return new PresetTaskResolvedPromptSelection(
            resolvedLocale, normalizedAgentFamily, variant.Id, false, "variants", variant.Template);
    }

    // 没有变体命中：落到显式声明的 fallback 变体
    return new PresetTaskResolvedPromptSelection(
        resolvedLocale, normalizedAgentFamily, PromptPackage.FallbackVariant?.Id, true,
        "variants", PromptPackage.FallbackVariant?.Template ?? PromptPackage.Locales[resolvedLocale]);
}
```

Die Abgleichsregel `VariantMatches` ist schlicht: **Jeder Selektor, den eine Variante deklariert, muss zur Laufzeit zutreffen**. Nicht deklarierte Dimensionen schränken nicht ein:

```csharp
private static bool VariantMatches(
    PresetTaskPromptVariantDefinition variant,
    IReadOnlyDictionary<string, string> selectorInputs)
{
    foreach (var selector in variant.Match)
    {
        if (!selectorInputs.TryGetValue(selector.Key, out var runtimeValue))
            return false;
        if (!selector.Value.Contains(runtimeValue, StringComparer.OrdinalIgnoreCase))
            return false;
    }
    return true;
}
```

Damit ist erklärt, warum die fallback-Variante mit nur `language` alle Agenten abfängt: Sie beschränkt die Dimension `agent` gar nicht, also trifft jeder Agent, dessen Sprache passt. Die native Variante beschränkt zusätzlich `agent`, daher erfüllen sie nur claude/codex.

Die Agenten-Familie ergibt sich aus dem Ausführungstyp des gewählten Hero, abgebildet in `PresetTaskRequirementModels.cs`:

```csharp
public static string? Resolve(AIProviderType? executorType) => executorType switch
{
    AIProviderType.ClaudeCodeCli => Claude,
    AIProviderType.CodexCli      => Codex,
    AIProviderType.GitHubCopilot => Copilot,
    AIProviderType.IFlowCli      => Iflow,
    AIProviderType.OpenCodeCli   => Opencode,
    // ... gemini / kimi / qoder / kiro / hermes / codebuddy / pi ...
    _ => null,
};
```

`SessionsController.PresetTasks.cs` holt beim Erstellen einer Sitzung zuerst den Hero, ruft dann `PresetTaskAgentFamilies.Resolve(hero.ExecutorType)` auf, um den Familiennamen zu erhalten, und übergibt ihn an `ResolvePromptSelection`. Nach der Auswahl der Variante rendert `RenderPrompt` die Vorlage mit Handlebars und stellt die aus `preludeTemplate` erzeugte Zeile `/goal <Ziel>` voran:

```csharp
var renderedPrompt = prompt.FillTemplate(normalizedContext);
var commandPrelude = BuildCommandPrelude(normalizedContext); // -> "/goal <goalDescription>"
return string.IsNullOrWhiteSpace(commandPrelude)
    ? renderedPrompt
    : $"{commandPrelude}\n\n{renderedPrompt}";
```

### Zulassung gelockert: von der Allowlist zu `any`

Mit der Ausweichanweisung muss `goal` nicht-native Agenten nicht mehr abweisen. In `backend/task-preset.json` wird `requirements` von `["claude","codex"]` auf `any` gelockert:

```jsonc
{
  "taskKey": "goal",
  "requirements": [ { "type": "agent", "name": "any" } ],
  "inputBindings": [
    { "input": "goalCommandIds",  "promptParameter": "goalCommandIds",  "required": true },
    { "input": "goalDescription", "promptParameter": "goalDescription", "required": true },
    { "input": "targetScopeMarkdown", "promptParameter": "targetScopeMarkdown", "producer": "frontend-computed" }
  ]
}
```

Die Zulassung wird geöffnet, die Unterschiede werden in die Prompt-Schicht verlagert. Das ist die zentrale Abwägung des ganzen Ansatzes: **Kompatibilität ist nicht mehr ein Schalter „läuft oder nicht", sondern eine Weiche „mit welchem Prompt läuft es".**

## Praxis

### Wie ein Lauf von Anfang bis Ende abläuft

1. Nutzer:innen füllen im Schubladen-Panel `goal` die Zielbeschreibung aus, wählen den Repository-Bereich und den Hero und senden ab;
2. Das Backend ermittelt aus dem Ausführungstyp des Hero die Agenten-Familie (z. B. `claude` / `gemini`);
3. `ResolvePromptSelection(locale, agentFamily)` sucht die Variante nach `Agent × Sprache`:
   - claude/codex + zh-CN → `native-zh-cn`;
   - gemini + zh-CN → native trifft nicht, daher `fallback-zh-cn`;
4. `RenderPrompt` rendert die gewählte Vorlage und stellt `/goal <Zielbeschreibung>` ganz vorne an;
5. Native Agenten führen die erste Zeile als Befehl aus. Ausweich-Agenten behandeln sie laut System-Prompt als Metadaten und setzen das dauerhafte Arbeiten über gewöhnliches Prompt-Following fort.

### Agentenbewusstsein für die eigene Voreinstellung ergänzen

Wenn du dieselbe Anpassung für eine neue Voreinstellung umsetzen willst, ist das Vorgehen festgelegt:

1. In `prompts.json` `locales` durch `variants` ersetzen und `agent` in `selectors` ergänzen;
2. Native Variante: `match` enthält `agent` und `language`. Fallback-Variante: nur `language`;
3. Zusätzlich eine oberste `variants.fallback` als letzte Absicherung deklarieren (das Schema verlangt im Variantenmodus einen Fallback);
4. Das Backend muss nicht geändert werden, `ResolvePromptSelection` / `VariantMatches` sind generisch;
5. Wenn die Zulassung nicht einschränken soll, `agent` in `requirements` auf `any` setzen.

### Einige typische Fallstricke

- **Die Reihenfolge der Varianten ist die Priorität.** Native muss vor fallback stehen. Sonst würde die nur auf Sprache beschränkte fallback-Variante alle Agenten vorab abfangen, und claude/codex würden den nativen Zweig nie erreichen.
- **Die Ausweichanweisung muss die Zeile `/goal` ausdrücklich herabstufen.** Das Präfix `/goal ...` wird bedingungslos vorangestellt (durch `preludeTemplate` festgelegt). Der Satz im Ausweich-System-Prompt, sie als Metadaten zu behandeln und nicht wortwörtlich auszuführen, darf daher nicht fehlen. Sonst könnte ein nicht-nativer Agent sie als ungültigen Befehl behandeln.
- **Die Nicht-Interaktivitäts-Vorgabe gehört in jede Vorlage.** `goal` ist ein in der Warteschlange ausgeführter Auto-Task. Die Vorlagen betonen wiederholt „kein AskUserQuestion, nicht nachfragen, mit vernünftigen Annahmen weitermachen und diese angeben". Das verhindert, dass der Agent ohne Aufsicht auf eine Eingabe wartet.
- **Repository-Grenzen werden durch den Prompt gesichert, nicht durch eine Sandbox.** Die Vorlagen verlangen ausdrücklich: „Nur innerhalb der ausdrücklich als beschreibbar gewählten Repositories ändern; nur lesbare Repositories dienen als ergänzender Kontext." Das ist eine weiche Einschränkung auf Prompt-Ebene, daher sollte der Repository-Bereich sorgfältig ausgefüllt werden.
- **Abwärtskompatibilität ist kostenlos.** Bei älteren Voreinstellungen, die nur `locales` statt `variants` haben, ist `UsesVariants` false. Sie laufen direkt über den Pfad `legacy-locales` und sind nicht betroffen. Bestehende Voreinstellungen müssen für das neue Modell nicht angefasst werden.

## Zusammenfassung

Die Frage „Wie erweitern wir das, wenn ein Agent `goal` nativ nicht unterstützt?" wird nicht durch fest verdrahtete Verzweigungen für jeden Agenten beantwortet. Stattdessen werden die Unterschiede als Prompt-Varianten nach dem Schema `Agent × Sprache` modelliert:

- Nativ unterstützte Agenten (Claude / Codex) nutzen die native Variante und verwenden direkt die Befehlsoberfläche `/goal`;
- Nicht unterstützte Agenten nutzen die fallback-Variante, die `/goal ...` ausdrücklich als Ziel-Metadaten herabstuft und dasselbe dauerhafte Arbeitsverhalten über gewöhnliches Prompt-Following erzeugt;
- Der Abgleich folgt einer generischen Regel („alle deklarierten Selektoren einer Variante müssen zutreffen") plus gestufter Fallbacks, und die Auswertung im Backend erfolgt einmal;
- Die Zulassung wurde von einer Allowlist auf `any` gelockert. Kompatibilität bedeutet nun nicht mehr „läuft oder nicht", sondern „mit welchem Prompt läuft es".

Der Nutzen dieses Entwurfs beschränkt sich nicht auf `goal`: Das Modell aus `Agent × Sprache`-Selektoren und Fallback ist generisch. Jede Voreinstellung, die je nach Fähigkeit des Agenten unterschiedliche Anweisungen braucht, kann es wiederverwenden, und bestehende Voreinstellungen bleiben unberührt.
