[이전 가이드](/ko-KR/blog/2026-11-23-mac-astro-site-claude-github-cloudflare/)에서는 깨끗한 Mac 환경에서 시작해 GitHub Pages와 Cloudflare에 배포되는 Astro 사이트를 만들었습니다. 사이트 공개는 절반만 끝난 상태입니다. 누가 방문하는지, 방문자가 무엇을 하는지, Google이 사이트를 찾을 수 있는지도 알아야 합니다.

이 가이드는 그 부분을 다룹니다. Google Analytics와 Google Search Console에 등록하고, Claude에게 추적 코드, 사이트맵, 소셜 태그, favicon을 적용하도록 요청합니다. 각 단계의 끝에는 직접 확인할 수 있는 결과가 있으며, 확인한 뒤에 다음 단계로 넘어가면 됩니다.

전체 과정은 다음과 같습니다.

1. Google Analytics 속성을 만들고 측정 ID를 복사합니다.
2. Claude에게 Google Analytics를 적용하고, 푸시한 뒤 배포가 끝날 때까지 기다리고, 실제 서비스 중인 페이지에 코드가 있는지 확인하게 합니다.
3. Google Analytics에서 내 방문이 실시간으로 잡히는지 확인합니다.
4. Google Search Console에 사이트를 등록합니다.
5. Search Console과 Google Analytics를 연결합니다.
6. Claude가 사이트에 맞는 이벤트 추적을 설계해 추가하게 한 뒤, 배포하고 검증합니다.
7. Claude가 기본 SEO 계층을 추가하게 합니다. 사이트맵, `robots.txt`, canonical 링크, Open Graph 태그, Twitter 태그가 여기에 포함됩니다.
8. Search Console에 사이트맵을 제출합니다.
9. Claude가 페이지별 제목, 설명, 키워드를 다듬고, Mac의 명령줄 도구로 여러 크기의 favicon을 생성하게 합니다.

## 이 가이드의 대상

이 가이드는 이전 가이드를 마친 분을 위한 것입니다. GitHub 저장소에 Astro 프로젝트가 있고, `main`에 푸시할 때마다 자동으로 배포되며, 공개 도메인이 있어야 합니다. 분석 도구를 써 본 경험은 필요하지 않습니다. 대신 짧은 프롬프트를 Claude Code에 붙여 넣을 수 있어야 하고, 몇 개의 Google 페이지에서 클릭할 수 있어야 합니다.

## 사전 준비

- 이전 가이드에서 배포한 Astro 사이트가 있고, 커스텀 도메인이 동작해야 합니다. 이 글에서는 저장소를 `my-astro-site`, 도메인을 `example.com`이라고 부르니 자신의 값으로 바꿔 읽으세요.
- Google 계정이 있어야 합니다.
- Claude Code가 설치되어 있고 로그인되어 있어야 합니다. `gh`도 로그인되어 있어야 합니다(`gh auth status`로 확인).
- 도메인의 DNS 설정을 변경할 수 있어야 합니다. 도메인이 Cloudflare에 있다면 이미 갖추어진 상태입니다.

## 1단계: Google Analytics 속성 만들기와 측정 ID 얻기

Google Analytics 4(GA4)의 구조는 다음과 같습니다. 계정 아래에 하나 이상의 속성이 있고, 속성 아래에 데이터 스트림이 있습니다. 웹사이트 하나는 웹 데이터 스트림 하나에 대응하며, 이 스트림에는 `G-`로 시작하는 측정 ID가 있습니다.

1. [analytics.google.com](https://analytics.google.com)을 열고 Google 계정으로 로그인합니다.
2. **측정 시작**을 클릭합니다. 이미 Analytics를 사용 중이라면 **관리 → 만들기 → 계정**을 선택합니다. 계정 이름은 예를 들어 `My sites`처럼 정합니다.
3. 속성을 만듭니다. 웹사이트 이름으로 속성 이름을 짓고, 보고서 시간대와 통화를 고르고, 이후에 나오는 비즈니스 질문에 답합니다.
4. 플랫폼을 선택할 때 **웹**을 고릅니다.
5. 웹사이트 주소(`https://example.com`)와 데이터 스트림 이름을 입력하고, **향상된 측정**은 켜 둡니다. 코드를 추가하지 않아도 페이지 조회, 스크롤, 외부 링크 클릭, 파일 다운로드를 기록합니다.
6. 데이터 스트림을 만듭니다. Google은 스트림 세부정보를 보여주며, 여기에 **측정 ID**가 있습니다.

측정 ID를 복사합니다. `G-ABCD123456`처럼 생겼습니다. 나중에 **관리 → 데이터 수집 및 수정 → 데이터 스트림 → 사용 중인 스트림**에서 다시 찾을 수 있습니다.

측정 ID는 비밀 값이 아닙니다. 이 ID를 사용하는 사이트의 페이지 소스에는 그대로 노출되므로 저장소에 커밋해도 괜찮습니다.

확인: `G-`로 시작하는 측정 ID를 얻었습니다.

## 2단계: Claude에게 Google Analytics 적용 요청하기

프로젝트 폴더에서 Claude를 실행합니다.

```bash
cd ~/Sites/my-astro-site
claude
```

그다음 배포와 검증까지 포함한 전체 작업을 하나의 요청으로 설명합니다. 최종 상태를 정확하게 설명할수록 나중에 고쳐야 할 부분이 줄어듭니다.

```text
이 Astro 사이트에 Google Analytics 4를 적용해 주세요. 측정 ID는 G-ABCD123456입니다.

요구 사항:
- gtag.js 로더와 config 호출은 공용 레이아웃의 <head>에 넣어서 모든 페이지에 정확히 한 번만 존재하게 해 주세요.
- 일반 인라인 스크립트(is:inline)를 사용해서 window.gtag가 실제 전역 함수가 되게 해 주세요. Astro는 일반 <script>를 모듈로 번들링하기 때문에, 그러면 이후 코드에서 gtag에 접근할 수 없습니다.
- 태그는 프로덕션 빌드에서만 렌더링하고, `npm run dev`에서는 렌더링하지 마세요.
- 측정 ID는 상수나 환경 변수에서 읽어 주세요. 여러 곳에 복사하지 마세요.
- `npm run build`를 실행하고, dist/index.html에 태그가 들어 있는지 확인해 주세요.

빌드가 통과하면 이해하기 쉬운 커밋 메시지로 커밋하고 main에 푸시해 주세요. 그다음 GitHub Pages 워크플로와 Cloudflare 빌드, 두 배포가 모두 끝날 때까지 기다려 주세요. 마지막으로 curl로 https://example.com/를 가져와서, 실제 서비스 중인 HTML에 측정 ID가 들어 있는지 확인해 주세요. 무엇을 확인했는지 보고해 주세요.
```

Claude가 레이아웃에 만드는 코드는 대략 다음과 비슷해야 합니다.

```astro
---
const GA_ID = 'G-ABCD123456';
const isProd = import.meta.env.PROD;
---
<head>
  {isProd && (
    <>
      <script is:inline async src={`https://www.googletagmanager.com/gtag/js?id=${GA_ID}`}></script>
      <script is:inline define:vars={{ GA_ID }}>
        window.dataLayer = window.dataLayer || [];
        window.gtag = function () { dataLayer.push(arguments); };
        gtag('js', new Date());
        gtag('config', GA_ID);
      </script>
    </>
  )}
</head>
```

"태그를 넣었는데 반응이 없다"는 문제가 가장 자주 생기는 이유이므로, 두 가지 세부 사항을 이해해 두세요.

- **`window.gtag`는 반드시 전역 함수여야 합니다.** 스크립트가 클로저 안에 감싸여 있으면 페이지 조회는 정상적으로 기록될 수 있지만, `window.gtag`는 정의되지 않습니다. 그러면 3단계에서 추가할 사용자 정의 이벤트가 모두 조용히 실패합니다. `window.gtag`에 명시적으로 할당하면 이 문제를 피할 수 있습니다.
- **프로덕션에서만 활성화합니다.** 태그가 `localhost`에서도 동작하면 개발 중 클릭이 데이터를 오염시킵니다.

배포를 기다리는 동안 Claude는 다음과 비슷한 명령을 사용합니다.

```bash
gh run watch
curl -s https://example.com/ | grep -o 'googletagmanager.com/gtag/js?id=G-[A-Z0-9]*'
```

`gh run watch`는 GitHub Actions 실행이 끝날 때까지 진행 상황을 따라갑니다. `curl` 명령은 실제 서비스 페이지에 로더 주소가 있을 때만 출력을 냅니다.

확인: Claude의 보고에 두 플랫폼 모두 배포에 성공했다고 나와 있고, 실제 서비스 HTML에서 측정 ID가 확인되어야 합니다. `curl`에서 아무것도 출력되지 않으면 배포가 아직 끝나지 않았거나, 캐시가 이전 페이지를 제공하고 있는 것입니다. 1분 뒤에 Claude에게 다시 시도하게 하고, 이전 페이지가 계속 보이면 Cloudflare 캐시를 지웁니다.

## 3단계: Google Analytics에서 사이트가 살아 있는지 확인하기

이제 나의 쪽뿐 아니라 Google 쪽에서도 확인합니다.

1. 브라우저에서 `https://example.com`을 엽니다. 광고 차단기나 프라이버시 브라우저를 쓴다면 이번 확인 동안에는 끄세요. 이런 도구는 Google Analytics를 차단합니다.
2. Google Analytics에서 **보고서 → 실시간**을 엽니다.
3. 약 1분 안에 **지난 30분 동안 사용자 1명**이 표시되고, 이벤트 목록에 `page_view` 이벤트가 보여야 합니다.
4. 페이지를 두세 개 열어 보면 페이지 제목이 실시간 보기에 나타납니다.

**관리 → 데이터 스트림 → 사용 중인 스트림**을 열어 확인할 수도 있습니다. 녹색 체크 표시와 함께 데이터가 들어오고 있다는 안내가 보이면 스트림이 트래픽을 받고 있는 것입니다.

확인: 내 방문이 **실시간** 보고서에 나타납니다. **수명 주기** 같은 표준 보고서는 몇 시간에서 하루까지 늦게 반영되므로, 그 보고서들이 아직 비어 있어도 걱정하지 않아도 됩니다.

## 4단계: Google Search Console에 사이트 등록하기

Google Analytics는 방문자가 도착한 뒤 무엇을 했는지 알려 줍니다. Google Search Console은 Google이 사이트를 어떻게 보는지 알려 줍니다. 어떤 검색어가 방문자를 데려왔는지, 어떤 페이지가 색인되었는지, Google이 어떤 오류를 발견했는지를 보여 줍니다.

1. [search.google.com/search-console](https://search.google.com/search-console)을 열고 Analytics와 같은 Google 계정으로 로그인합니다. 같은 계정을 쓰면 나중에 연결하기가 더 쉽습니다.
2. **속성 추가**를 클릭합니다. 두 가지 유형이 나옵니다.
   - **도메인**은 `example.com`과 모든 하위 도메인, 프로토콜을 포괄하며, DNS 레코드가 하나 필요합니다.
   - **URL 접두어**는 `https://example.com/`처럼 정확히 하나의 주소만 포괄하며, 여러 가지 확인 방법을 제공합니다.
3. DNS가 Cloudflare에 있다면 **도메인**을 선택하고 `example.com`을 입력합니다.
4. Search Console이 `TXT` 레코드 값을 보여 줍니다. `google-site-verification=`로 시작하는 값을 복사합니다.
5. Cloudflare 대시보드에서 도메인을 열고 **DNS → 레코드 → 레코드 추가**로 이동합니다. 유형은 `TXT`, 이름은 `@`로 두고, 복사한 값을 내용에 붙여 넣은 뒤 저장합니다.
6. Search Console로 돌아가 **확인**을 클릭합니다. DNS 변경은 보통 몇 분 안에 반영되지만 더 걸릴 수도 있습니다. 확인에 실패하면 잠시 기다렸다가 **확인**을 다시 클릭합니다.

**URL 접두어** 유형을 선택했다면, 가장 간단한 방법은 Google Analytics로 확인하는 것입니다. 같은 Google 계정을 쓰고 있다면, 2단계에서 설치한 태그를 Search Console이 소유권 증명으로 사용할 수 있습니다.

확인: Search Console에 "소유권이 확인되었습니다"라고 표시되고, 해당 속성의 개요 페이지가 열립니다. 한동안은 "아직 데이터가 없습니다"라고 나오는데, 이는 정상입니다.

## 5단계: Search Console과 Google Analytics 연결하기

연결하면 검색어와 방문 페이지 성과가 Analytics 보고서에 들어오므로, 검색으로 들어온 트래픽과 그 방문자들의 행동을 함께 볼 수 있습니다.

1. Google Analytics에서 **관리**를 엽니다.
2. **제품 연결** 아래에서 **Search Console 연결**을 선택합니다.
3. **연결**을 클릭하고, **계정 선택**을 클릭한 뒤 Search Console 속성을 선택합니다. 해당 Search Console 속성의 소유자이고, 이 Analytics 속성의 편집자여야 합니다.
4. **다음**을 클릭하고 웹 데이터 스트림을 선택한 뒤 **제출**을 클릭합니다.

Search Console 데이터는 며칠 뒤부터 들어오기 시작하며, 약 이틀 정도 지연됩니다. 여기서 기다릴 것은 없으니 바로 다음 단계로 넘어가면 됩니다.

연결이 만들어지면 **보고서 → 라이브러리**에서 관련 보고서를 찾을 수 있습니다. Search Console 보고서는 왼쪽 메뉴에 자동으로 추가되지 않습니다. 메뉴에 표시하려면 라이브러리에서 **Search Console** 컬렉션을 게시하세요.

확인: **관리 → 제품 연결 → Search Console 연결**에 해당 속성이 나열되어 있어야 합니다.

## 6단계: 사이트에 맞는 이벤트 추적 추가하기

향상된 측정은 페이지 조회, 스크롤, 외부 링크 클릭, 사이트 내 검색, 파일 다운로드를 이미 기록하므로 이것들을 다시 구현하지 마세요. 이벤트는 사이트 고유의 비즈니스 활동에 사용합니다. 주요 행동 유도 버튼 클릭, 뉴스레터 구독, 문의 양식, 가격 페이지 조회 같은 것들입니다.

가장 유용한 지시는 "이벤트를 몇 개 추가해 줘"가 아니라 "먼저 내 사이트를 보고, 이벤트 계획을 제안하고, 내가 승인하게 해 줘"입니다. 그래야 무엇을 측정할지 계속 직접 통제할 수 있습니다.

```text
이 Astro 사이트의 구조를 살펴봐 주세요. 페이지, 레이아웃, 컴포넌트, 행동 유도 버튼, 양식, 외부 링크를 확인해 주세요.

1단계: 코드를 수정하기 전에 이벤트 계획을 제안해 주세요. 표로 정리해 주시는데, 열은 이벤트 이름, 발생 시점, 매개변수, 그리고 이 이벤트가 답하는 비즈니스 질문입니다. 적절한 GA4 권장 이벤트 이름이 있으면 우선 사용하고(예: generate_lead, sign_up, select_content), 없으면 snake_case 형태의 사용자 정의 이름을 사용해 주세요. 향상된 측정이 이미 추적하는 것(페이지 조회, 스크롤, 외부 링크 클릭, 파일 다운로드)은 중복하지 마세요. 최대 10개까지만 제안해 주세요.

2단계: 제가 승인하면 계획을 구현해 주세요.
- 요소에는 data-ga-event, data-ga-label, data-ga-location 속성을 붙여 주세요.
- document에 위임된 클릭 리스너를 하나만 두고, 이 속성들을 읽어서 gtag('event', ...)를 호출하게 해 주세요. 인라인 onclick 핸들러는 추가하지 마세요.
- 매개변수에는 안정적인 id와 위치만 보내 주세요. 링크 텍스트, 양식 입력값, 이메일 주소, 방문자를 식별할 수 있는 어떤 정보도 절대 보내지 마세요.
- 페이지 이동을 지연시키거나 취소하지 마세요.

3단계: 빌드하고, 커밋하고, 푸시해 주세요. 두 배포가 끝날 때까지 기다리고, curl로 실제 서비스 사이트에 리스너 스크립트가 들어 있는지 확인해 주세요. 그런 다음 제가 GA4 DebugView에서 확인할 수 있도록, 어떤 위치를 클릭하면 되는지 알려 주세요.
```

Claude는 먼저 표를 보여 줍니다. 작은 사이트에 맞는 합리적인 계획은 대략 이런 모습입니다.

| 이벤트 | 발생 시점 | 매개변수 | 답하는 질문 |
| --- | --- | --- | --- |
| `cta_click` | 방문자가 주요 행동 유도 버튼을 클릭할 때 | `label`, `location` | 어떤 버튼과 페이지 영역이 행동으로 이어지는가? |
| `generate_lead` | 문의 양식 제출이 성공할 때 | `form_id` | 방문자 중 몇 명이 연락처가 되는가? |
| `nav_click` | 헤더 또는 푸터 링크를 클릭할 때 | `label`, `location` | 어떤 내비게이션 항목이 사용되는가? |
| `theme_toggle` | 테마 전환을 사용할 때 | `value` | 다크 모드 스위치를 유지할 가치가 있는가? |

이 표는 비판적으로 읽으세요. 아무도 보지 않을 이벤트는 삭제하고, 기능 중심으로 이름 붙은 이벤트는 결정 중심의 이름으로 바꿉니다. 그다음 "승인합니다. 단, `theme_toggle`은 빼 주세요."라고 답해서 구현을 진행하게 합니다.

Claude가 작성하는 리스너는 대략 다음과 같습니다.

```js
document.addEventListener(
  'click',
  (event) => {
    const el = event.target.closest('[data-ga-event]');
    if (!el || typeof window.gtag !== 'function') return;
    window.gtag('event', el.dataset.gaEvent, {
      label: el.dataset.gaLabel,
      location: el.dataset.gaLocation,
      transport_type: 'beacon',
    });
  },
  true,
);
```

표시가 붙은 버튼은 다음과 같습니다.

```astro
<a href="/contact" data-ga-event="cta_click" data-ga-label="hero_contact" data-ga-location="home_hero">
  문의하기
</a>
```

### 이벤트 검증하기

1. Google Analytics에서 **관리 → 데이터 표시 → DebugView**를 엽니다. DebugView에는 도착한 이벤트가 몇 초 안에 표시됩니다.
2. 브라우저를 디버그 모드로 전환하려면 Chrome 확장 프로그램 **Google Analytics Debugger**를 설치하거나, Claude에게 `config` 호출에 `debug_mode: true`를 임시로 넣게 합니다.
3. 실제 서비스 사이트에 접속해서 Claude가 나열한 클릭을 수행합니다.
4. 클릭할 때마다 DebugView 타임라인에 이벤트가 하나씩 나타나야 하고, 예상한 매개변수가 함께 보여야 합니다.

이벤트가 한 번 도착하면 **관리 → 데이터 표시 → 이벤트**에도 나타납니다. 표준 보고서에서 `label`이나 `location`을 쓰고 싶다면 **관리 → 데이터 표시 → 맞춤 정의 → 맞춤 측정기준 만들기**에서 등록하세요. 범위는 **이벤트**로 선택합니다. 이렇게 등록한 매개변수만 표준 보고서에 나타납니다.

임시로 넣은 `debug_mode` 설정은 모두 제거하고, Claude에게 깔끔한 버전을 푸시하게 합니다.

확인: 추적되는 모든 클릭이 올바른 이벤트 이름과 매개변수로 DebugView에 나타나고, 최종 코드가 `main`에 반영되어 있어야 합니다.

## 7단계: 기본 SEO 계층 추가하기

검색 엔진에는 페이지 지도, 크롤링 범위에 관한 안내, 그리고 사람들이 페이지를 공유할 때 보게 될 설명이 필요합니다. 첫 번째 항목인 사이트맵에는 Astro의 공식 통합 기능이 있고, 나머지는 레이아웃에 몇 줄의 코드를 추가하면 됩니다. Claude는 관련 Astro 컴포넌트와 통합 기능을 빠르게 추가할 수 있습니다.

```text
이 Astro 사이트에 기본 SEO를 추가해 주세요.

1. 사이트맵: `npx astro add sitemap`으로 공식 @astrojs/sitemap 통합 기능을 설치해 주세요. astro.config.mjs의 `site`가 운영 도메인 https://example.com인지 확인하고, GitHub Pages 프로젝트 호스팅에서 남은 `base` 설정은 삭제해 주세요.
2. robots.txt: src/pages/robots.txt.ts를 만들어서 "User-agent: *", "Allow: /", 그리고 https://example.com/sitemap-index.xml을 가리키는 Sitemap 한 줄을 반환해 주세요. 이 주소는 `site` 설정에서 생성되게 하고, 하드코딩하지 마세요.
3. 공용 레이아웃에서 쓸 재사용 가능한 SEO 컴포넌트를 만들어 주세요. 다음을 출력해야 합니다. <title>, meta description, 현재 URL과 `site`를 기반으로 생성한 canonical 링크, Open Graph 태그(og:type, og:title, og:description, og:url, og:image, og:site_name, og:locale), Twitter 카드 태그(twitter:card summary_large_image, twitter:title, twitter:description, twitter:image), 그리고 theme-color meta 태그. 각 페이지는 props로 자신의 제목과 설명을 전달합니다.
4. 페이지가 이미지를 제공하지 않을 때 쓸 기본 1200x630 소셜 공유 이미지를 public/og-default.png에 넣어 주세요.
5. 사이트 전체에 WebSite 유형의 JSON-LD 구조화 데이터를 추가해 주세요. 사이트에 블로그가 있다면 글에는 Article 유형도 추가해 주세요.
6. `npm run build`를 실행하고, dist/sitemap-index.xml을 나열하고, dist/robots.txt를 보여 주고, 홈페이지에서 빌드된 HTML에 위의 모든 태그가 들어 있는지 확인해 주세요.

모두 올바르면 커밋하고 푸시한 뒤 두 배포가 끝날 때까지 기다려 주세요. 그리고 curl로 https://example.com/sitemap-index.xml과 https://example.com/robots.txt가 모두 200을 반환하고 내용이 올바른지 확인해 주세요.
```

각 부분이 하는 일은 다음과 같습니다.

- **사이트맵.** `@astrojs/sitemap`은 빌드 시점에 `sitemap-index.xml`과 하나 이상의 `sitemap-0.xml` 파일을 생성합니다. 절대 URL을 만들려면 `site` 설정이 필요합니다.
- **`robots.txt`.** 크롤러가 무엇을 가져와도 되는지, 사이트맵이 어디에 있는지 알려 줍니다. 특정 페이지가 색인되지 않게 하려면 `robots.txt`에만 적지 말고 `noindex`를 사용해야 합니다.
- **Canonical 링크.** 같은 페이지에 여러 주소로 접근할 수 있을 때, 어느 주소가 정식 주소인지 Google에 알려 줍니다.
- **Open Graph와 Twitter 태그.** 소셜 네트워크나 메신저에서 링크를 공유할 때 표시되는 제목, 설명, 이미지를 결정합니다.
- **JSON-LD.** 구조화 데이터는 검색 엔진이 페이지의 내용을 이해하도록 돕습니다. 리치 결과가 나온다고 보장하지는 않지만, 추가하는 비용은 낮습니다.

확인: 실제 서비스 사이트의 `sitemap-index.xml`에 페이지가 나열되어 있고, `robots.txt`에 `Sitemap:` 줄이 있으며, 페이지 소스에서 canonical, Open Graph, Twitter 태그를 볼 수 있어야 합니다. 주소를 소셜 카드 미리보기 도구에 붙여 넣거나 메신저에서 공유해서 미리보기도 확인할 수 있습니다.

## 8단계: Search Console에 사이트맵 제출하기

Search Console에 알려 주기 전까지는 사이트맵이 있다는 사실을 알지 못합니다.

1. Search Console에서 속성을 열고, 왼쪽 메뉴에서 **사이트맵**을 선택합니다.
2. **새 사이트맵 추가** 아래에 `sitemap-index.xml`을 입력합니다.
3. **제출**을 클릭합니다.
4. 상태가 **성공**으로 바뀌고 발견된 페이지 수가 표시되어야 합니다. **가져올 수 없음**이 표시되면 먼저 브라우저에서 사이트맵 주소를 열어 보세요. 열린다면 첫 가져오기가 지연된 것일 수 있으니 몇 분 뒤에 새로 고칩니다.

다음으로, 가장 중요한 페이지를 Google이 바로 확인하도록 요청합니다.

1. Search Console 상단 검색창에 홈페이지 URL을 붙여 넣습니다.
2. 아직 색인되지 않았다면 **색인 생성 요청**을 클릭합니다.

색인에는 여전히 며칠이 걸리고, Search Console 보고서도 지연되니 일주일 뒤에 다시 확인하세요.

확인: **사이트맵** 목록에 `sitemap-index.xml`이 **성공** 상태로 나타나야 합니다.

## 9단계: 페이지별 메타데이터 다듬기와 여러 크기의 favicon 추가하기

기본 계층은 모든 페이지에 일반적인 메타데이터를 줍니다. 제목과 설명은 사람들이 검색 결과에서 읽는 글이므로 페이지마다 따로 다듬을 가치가 있습니다. Favicon은 여러 크기가 필요합니다. 브라우저, 휴대폰, 북마크가 각각 다른 파일을 요청하기 때문입니다.

### 제목, 설명, 키워드

```text
이 사이트의 각 페이지를 검토하고 검색 메타데이터를 개선해 주세요.

각 페이지마다 제목, meta description, 키워드를 수정 전후로 비교하는 표를 보여 준 뒤 변경을 적용해 주세요. 규칙은 다음과 같습니다.
- 제목: 페이지마다 고유해야 하며, 약 60자를 넘지 않아야 합니다. 주요 주제를 앞에 두고, 사이트 이름은 뒤에 둡니다.
- 설명: 페이지마다 고유해야 하며, 120자에서 160자 사이여야 합니다. 방문자가 무엇을 얻을 수 있는지 자연스러운 한 문장으로 설명하고 클릭을 유도합니다. 키워드를 나열하지 말고, 페이지 사이에 문장을 복사하지 마세요.
- 키워드: 페이지의 실제 내용에서 5개에서 8개의 단어를 뽑아 주세요. 레이아웃이 이미 지원하는 경우에만 keywords meta 태그를 유지하고, 페이지에서 다루지 않는 주제를 지어내지 마세요.
- 각 페이지에 제목 의미와 일치하는 <h1>이 정확히 하나 있는지 확인하고, 모든 이미지에 alt 속성이 있는지 확인해 주세요.

그런 다음 빌드를 실행하고, 여전히 제목이나 설명을 공유하고 있는 페이지를 나열한 짧은 보고서를 작성해 주세요.
```

기대치를 미리 맞춰 두세요. 검색 엔진은 keywords meta 태그를 대부분 무시합니다. 키워드를 적는 과정은 각 페이지가 무엇에 관한 것인지 분명히 하도록 강제하므로 여전히 도움이 됩니다. 실제로 검색 결과에 나타나는 것은 제목과 설명입니다.

### 여러 크기의 favicon

`favicon.svg` 하나로 시작하는 것도 괜찮지만, 어떤 곳에서는 특정 파일이 필요합니다. 오래된 브라우저와 북마크는 `favicon.ico`를 사용하고, iOS 홈 화면은 `apple-touch-icon`을 사용하며, Android와 웹 앱 매니페스트는 192와 512픽셀 PNG를 사용합니다.

macOS에는 PNG 크기를 조정하는 `sips`가 기본으로 있습니다. `.ico` 파일을 만들려면 ImageMagick이 필요하며, Homebrew로 설치할 수 있습니다. Claude가 Mac에서 직접 이 도구들을 사용하게 합니다.

```text
원본 이미지 public/logo-source.png(최소 512x512 정사각형 PNG)로 완전한 favicon 세트를 만들어 주세요.

1. macOS의 `sips` 명령으로 public/icon-192.png, public/icon-512.png, public/apple-touch-icon.png(180x180)을 만들어 주세요.
2. ImageMagick이 설치되어 있지 않다면 `brew install imagemagick`으로 설치해 주세요. `magick`으로 16x16, 32x32, 48x48 이미지를 포함한 public/favicon.ico를 만들어 주세요.
3. public/favicon.svg가 이미 있으면 그대로 두고, 없으면 로고와 어울리는 간단한 버전을 만들어 주세요.
4. icon-192.png와 icon-512.png를 나열하는 public/site.webmanifest를 추가해 주세요.
5. 레이아웃의 <head>를 업데이트해서 해당 <link> 태그를 추가해 주세요. SVG 아이콘, .ico 대체 파일, apple-touch-icon, 매니페스트가 필요합니다.
6. 생성된 각 이미지에 `file` 명령을 실행해서 실제 크기를 확인하고, 빌드를 실행한 뒤 이 파일들이 dist/에 있는지 확인해 주세요.
```

Claude가 실행하는 명령은 대략 다음과 비슷합니다.

```bash
sips -z 192 192 public/logo-source.png --out public/icon-192.png
sips -z 512 512 public/logo-source.png --out public/icon-512.png
sips -z 180 180 public/logo-source.png --out public/apple-touch-icon.png
brew install imagemagick
magick public/logo-source.png -define icon:auto-resize=48,32,16 public/favicon.ico
file public/*.png public/favicon.ico
```

head에 들어가는 링크는 다음과 같습니다.

```html
<link rel="icon" href="/favicon.svg" type="image/svg+xml" />
<link rel="icon" href="/favicon.ico" sizes="48x48" />
<link rel="apple-touch-icon" href="/apple-touch-icon.png" />
<link rel="manifest" href="/site.webmanifest" />
```

마지막으로, 앞선 단계와 마찬가지로 루프를 닫습니다.

```text
모든 변경 사항을 명확한 커밋 메시지로 커밋하고 main에 푸시해 주세요. 두 배포가 끝날 때까지 기다린 뒤, curl로 실제 서비스의 /favicon.ico, /apple-touch-icon.png, /site.webmanifest가 모두 200을 반환하는지 확인해 주세요.
```

브라우저에서 확인하세요. 탭에 아이콘이 표시되고, 북마크나 iOS의 "홈 화면에 추가"에서는 더 큰 이미지가 사용됩니다. 브라우저는 favicon을 적극적으로 캐시하므로, 여전히 이전 아이콘이 보이면 사이트를 개인 정보 보호 창에서 여세요.

## 자주 묻는 질문

- **실시간 보고서에 아무것도 없습니다.** 광고 차단기나 프라이버시 브라우저가 태그를 막고 있습니다. 확장 프로그램을 끈 개인 정보 보호 창에서 테스트하고, 실제 서비스 HTML에 측정 ID가 있는지 확인하세요.
- **페이지 조회는 정상인데 사용자 정의 이벤트가 동작하지 않습니다.** 실제 서비스 사이트에서 브라우저 콘솔을 열고 `typeof window.gtag`를 실행하세요. `function`이 출력되어야 합니다. `undefined`가 나오면 태그 스크립트가 모듈로 번들링된 것입니다. Claude에게 `is:inline`을 사용하고 `window.gtag`를 명시적으로 할당하도록 요청하세요.
- **이벤트는 DebugView에 나타나지만 보고서에는 나타나지 않습니다.** 표준 보고서는 최대 하루까지 지연되며, 사용자 정의 매개변수는 맞춤 측정기준으로 등록된 뒤에야 보고서에 나타납니다.
- **Search Console에서 도메인 확인이 실패합니다.** `TXT` 레코드가 루트 도메인(`@`)에 있는지, 값을 빠짐없이 복사했는지, Cloudflare 프록시를 사용하지 않았는지 확인하세요. TXT 레코드는 프록시되지 않습니다. 그다음 잠시 기다렸다가 다시 시도하세요.
- **사이트맵이 "가져올 수 없음"으로 표시됩니다.** `https://example.com/sitemap-index.xml`을 직접 열어 보세요. 404가 나오면 `astro.config.mjs`의 `site`가 운영 도메인인지, 사이트맵 통합 기능이 `integrations`에 등록되어 있는지 확인하세요.
- **소셜 미리보기가 예전 내용입니다.** 각 플랫폼은 미리보기를 캐시합니다. 태그를 수정한 뒤에는 플랫폼의 디버깅 도구에서 캐시를 새로 고치세요.

## 개인정보와 동의

분석 도구는 방문자의 데이터를 수집합니다. 방문자가 있는 지역에 따라서는 Google Analytics를 로드하기 전에 동의를 받아야 할 수 있습니다. 예를 들어 EU의 GDPR과 ePrivacy 규정이 그렇습니다. 개인정보 처리방침에도 이를 설명해야 할 수 있습니다. 이 가이드는 단계를 간결하게 유지하기 위해 태그를 무조건 설치합니다. 동의를 요구하는 지역의 방문자가 있다면, 방문자가 동의한 뒤에만 태그를 로드하는 동의 배너를 추가해 달라고 Claude에게 요청하세요. 위 내용은 일반적인 정보이며 법률 자문이 아닙니다.

## 계속 유지할 작업 순서

여기의 모든 단계는 같은 패턴을 따르며, 이것은 계속 익혀 둘 가치가 있는 습관입니다. 최종 상태를 Claude에게 설명하고, Claude가 수정하게 하고, 푸시하고 배포가 끝날 때까지 기다리게 하고, `curl`로 실제 서비스 사이트에서 결과를 증명하게 한 뒤, Google Analytics나 Search Console 같은 외부 도구로 확인합니다. 앞으로 기능을 추가할 때마다 같은 순서를 반복하면 됩니다.
