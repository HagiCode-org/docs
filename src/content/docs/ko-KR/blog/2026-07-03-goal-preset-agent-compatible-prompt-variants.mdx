## 모든 Agent가 `/goal`을 이해하도록: HagiCode 지속 작업 프리셋의 호환 확장 설계

## 소개

AI Agent에게 "지속 작업" 과제를 맡길 때 이상적인 흐름은 이렇습니다. 목표를 적고, 수정해도 되는 저장소를 고른 다음 제출하면, Agent가 중간에 되묻지도 않고 주제에서 벗어나지도 않으며 다른 저장소를 건드리지도 않은 채 목표를 향해 계속 나아갑니다.

HagiCode에는 이 기능을 위한 전용 진입점이 있습니다. `goal` 프리셋 작업이며, 명령 표면은 `/goal`입니다. 문제는 **모든 Agent가 `/goal`을 아는 것은 아니라는 점**입니다. Claude와 Codex에는 네이티브 지속 작업 명령 의미가 있어서 `/goal`을 그대로 전달하면 바로 처리합니다. 반면 다른 CLI(Gemini, Copilot, iFlow, OpenCode 등)에는 이런 슬래시 명령 자체가 없습니다. `/goal ...`을 그대로 넘기면 유효하지 않은 명령으로 취급되거나, 최악의 경우 글자 그대로 실행되어 문제가 생깁니다.

가장 간단한 해결책은 `goal`을 Claude / Codex에서만 실행하고 나머지 Agent는 모두 거부하는 것입니다. 하지만 그러면 Agent 매트릭스의 상당 부분이 제외됩니다. 이 글은 이 문제를 해결한 방법을 다룹니다. **"Agent를 인식하는" 프롬프트 변형(prompt variants)을 사용해, 네이티브를 지원하는 Agent는 네이티브 명령을 쓰고, 지원하지 않는 Agent는 폴백 프롬프트를 쓰게 함으로써 동작을 맞추고 경험을 일관되게 만듭니다.**

내용은 `repos/hagitask`의 `goal` 프리셋 패키지와 `repos/hagicode-core`의 백엔드 파싱 구현을 기준으로 합니다.

## 배경

### `goal`이란 무엇인가

`goal`은 내장 작업 프리셋 플러그인 패키지이며, 위치는 `repos/hagitask/presets/goal/`입니다. `manifest.json`은 플러그인 식별 정보, 아이콘, 로컬라이즈 패키지, 프론트엔드와 백엔드 자산을 선언합니다.

```jsonc
{
  "taskPresetId": "goal",
  "version": "1.0.0",
  "icon": "flag",
  "kind": "custom-executor",
  "status": "experimental",
  "entrypoints": { "menuSurface": "session-create", "drawerId": "goal" },
  "ui": { "panel": "./frontend/panel.json", "commands": "./frontend/commands.json" },
  "backend": {
    "taskPreset": "./backend/task-preset.json",
    "prompts": "./backend/prompts.json"
  }
}
```

이 프리셋의 역할은 "지속 작업 모드"입니다. 사용자가 목표 설명(`goalDescription`)을 입력하고, 선택적으로 쓰기 가능한 저장소와 읽기 전용 저장소의 범위를 지정하면, 백엔드가 이를 비대화형 auto-task 실행으로 조립합니다. 프론트엔드 패널 `panel.json`의 핵심 필드는 다음과 같습니다.

- `goalCommandIds`: 명령 선택기이며, 내장 항목은 `/goal` 하나뿐입니다.
- `goalDescription`: 필수 목표 설명입니다.
- `targetRepositories`: 저장소 접근 선택기이며, 읽기(read)와 쓰기(write)를 구분합니다.

### `/goal`은 어디서 오는가

명령 표면은 `frontend/commands.json`에 정의되어 있고, 핵심은 `preludeTemplate` 한 줄입니다.

```jsonc
{
  "commands": [
    {
      "id": "goal",
      "label": "goal",
      "preludeTemplate": "/goal {goalDescription}"
    }
  ]
}
```

즉 Agent에 최종적으로 전달되는 프롬프트의 본문 앞에는 `/goal <목표 설명>` 한 줄이 붙습니다. Claude / Codex에게 이 줄은 익숙한 명령입니다. 다른 Agent에게는 "번역이 필요한" 무언가입니다. 이 문서가 다루는 적응의 핵심 난점은 바로 이 `/goal ...` 한 줄이 Agent마다 다른 의미를 갖는다는 점입니다.

## 분석

### 단일 locale 템플릿으로는 부족하다

HagiTask의 초기 프롬프트 패키지(prompt package)는 **언어별로만 파일을 나누는** 구조였습니다. `prompts.json`에서 locale마다 `systemTemplate`과 `userTemplate` 한 쌍을 선언하고, 백엔드의 `PresetTaskCatalogProvider`가 이를 `PromptPackage.Locales`로 읽은 뒤 요청 언어에 따라 하나를 골라 렌더링합니다.

이 모델은 "실행 지시가 Agent와 무관한" 프리셋에는 충분합니다. 하지만 `goal`은 그렇지 않습니다.

- Claude / Codex: 네이티브 `/goal` 명령 표면에 바로 의존할 수 있습니다.
- 다른 Agent: `/goal ...`을 명령으로 실행하지 말아야 하며, "지속 작업 모드에 들어가는 방법"을 명시적으로 알려 주는 더 장황한 프롬프트가 필요합니다.

같은 locale 안에서 완전히 다른 두 지시가 필요하므로, 언어별 파일 분리만으로는 부족합니다. 언어 외에 **Agent 계열(family)**이라는 차원을 추가해야 했습니다.

### 실행 거부는 좋은 해법이 아니다

처음에는 `goal`의 `requirements`가 Agent를 `["claude", "codex"]`로 제한했고, 나머지 Agent는 호환되지 않는 것으로 판정되었습니다. 제품 관점에서 이 방식에는 두 가지 문제가 있었습니다.

1. 사용자가 영웅(hero) 선택 패널에서 호환 가능한 영웅을 거의 보지 못해서 고를 대상이 없어집니다.
2. 지속 작업을 수행할 능력이 있는 Agent가 많은데, 네이티브 `/goal`이 없다는 이유만으로 일괄 거부하는 것은 그 능력을 낭비합니다.

따라서 진짜 풀어야 할 문제는 "누가 실행할 수 있는가"가 아니라 "**같은 목표를 Agent 능력에 따라 다르지만 동등한 실행 지시로 어떻게 전달할 것인가**"였습니다. 답은 Agent를 인식하는 차이를 준비 단계에서 막지 않고 프롬프트 층으로 내려보내, 변형과 폴백으로 해결하는 것이었습니다.

## 해결

### 변형 선택기: agent × language

새 프롬프트 패키지 계약은 `prompts.json`에 `variants`를 도입합니다. `selectors`는 매칭 차원을 선언하고, `entries`는 각 변형의 매칭 규칙과 템플릿 파일을 선언합니다.

```jsonc
{
  "version": "1.1.0",
  "templateEngine": "handlebars",
  "variants": {
    "selectors": ["agent", "language"],
    "entries": [
      {
        "id": "native-zh-cn",
        "match": { "agent": ["claude", "codex"], "language": ["zh-CN"] },
        "systemTemplate": "./templates/zh-CN/native.system.md",
        "userTemplate": "./templates/zh-CN/native.user.hbs"
      },
      {
        "id": "fallback-zh-cn",
        "match": { "language": ["zh-CN"] },
        "systemTemplate": "./templates/zh-CN/fallback.system.md",
        "userTemplate": "./templates/zh-CN/fallback.user.hbs"
      }
      // ... native-en-us / fallback-en-us 同理
    ],
    "fallback": {
      "id": "fallback-default",
      "systemTemplate": "./templates/en-US/fallback.system.md",
      "userTemplate": "./templates/en-US/fallback.user.hbs"
    }
  }
}
```

폴백은 세 단계로 점점 느슨해집니다.

1. **native 변형**: `match`가 `agent`(claude/codex)와 `language`를 동시에 제약하므로, 네이티브 Agent만 매칭됩니다.
2. **fallback 변형**: `match`가 **`language`만 제약하고 `agent`는 제약하지 않으므로**, 어떤 Agent든 매칭됩니다. 네이티브 `/goal`이 없는 Agent를 위한 폴백입니다.
3. **fallback-default**: 언어조차 매칭되지 않을 때 쓰는 최종 보험입니다.

순서가 중요합니다. `entries`는 선언된 순서대로 순회되므로 native가 fallback보다 앞에 있어야 합니다. 그래서 claude/codex는 먼저 native에 매칭되고, 나머지 Agent는 언어 기준 fallback 변형으로 내려갑니다.

### 두 벌의 템플릿: 네이티브 vs 폴백

같은 목표라도 두 system 프롬프트의 차이는 `/goal` 줄을 어떻게 다루는지에 있습니다.

네이티브 템플릿(`templates/zh-CN/native.system.md`)의 내용은 다음과 같습니다.

```text
你是 `goal` task preset plugin 的内置执行提示。

本次运行必须使用 `/goal` 作为持续工作模式的命令表面。把提供的项目路径与仓库范围视为权威工作边界。

这次运行处于非交互环境。不要追问用户；当合理假设可以继续推进时，直接继续并把这些假设明确写在响应里。
```

폴백 템플릿(`templates/zh-CN/fallback.system.md`)의 내용은 다음과 같습니다.

```text
你是 `goal` task preset plugin 的兜底执行提示。

当前 agent 可能不支持原生 `/goal` 命令。如果提示前面出现了 `/goal ...` 这一行，把它视为预设附带的目标元数据，不要把它当成必须逐字执行的斜杠命令。

请以持续工作模式完成任务，并把提供的项目路径与仓库范围视为权威工作边界。

这次运行处于非交互环境。不要追问用户；当合理假设可以继续推进时，直接继续并把这些假设明确写在响应里。
```

폴백 전략의 핵심은 이 한 문장입니다. **"프롬프트 앞에 `/goal ...` 줄이 나타나면, 그것을 프리셋이 덧붙인 목표 메타데이터로 보고, 글자 그대로 실행해야 하는 슬래시 명령으로 취급하지 마십시오."** `preludeTemplate`이 앞에 붙인 `/goal <목표>` 줄은 네이티브 Agent에게는 명령이고, 폴백 Agent에게는 명시적으로 "메타데이터 / 목표 표시"로 격하됩니다. 이렇게 하면 일반적인 프롬프트 따르기(prompt following)만으로 같은 지속 작업 동작을 재현할 수 있습니다.

user 템플릿(`.hbs`)도 두 벌이며, 폴백 쪽에는 "라우팅 안내" 단락이 추가되어 있습니다. 이 단락은 Agent에게 지금 네이티브 `/goal` 지원에 의존하지 않는 분기로 라우팅되었음을 알리고, "네이티브 `/goal` 지원에 의존하지 말고, 일반적인 프롬프트 따르기 방식으로 같은 지속 작업 동작을 완료하라"고 요구합니다.

### 백엔드: 한 번의 파싱으로 결정한다

변형 매칭은 백엔드 `PCode.Application/Services/PresetTaskCatalogProvider.cs`의 `ResolvePromptSelection`에서 수행됩니다. 먼저 locale을 해석하고, language와 agent를 선택기 사전에 담은 뒤, 순서대로 첫 번째로 매칭되는 변형을 찾습니다.

```csharp
public PresetTaskResolvedPromptSelection ResolvePromptSelection(string? locale, string? agentFamily)
{
    var resolvedLocale = ResolvePromptLocale(locale);
    if (!PromptPackage.UsesVariants)
    {
        // 旧的仅按 locale 分文件的预设，走遗留路径，保持向后兼容
        var legacyTemplate = PromptPackage.Locales[resolvedLocale];
        return new PresetTaskResolvedPromptSelection(
            resolvedLocale, NormalizeAgentFamily(agentFamily), null, false,
            "legacy-locales", legacyTemplate);
    }

    var normalizedAgentFamily = NormalizeAgentFamily(agentFamily);
    var selectorInputs = new Dictionary<string, string>(StringComparer.OrdinalIgnoreCase)
    {
        [PresetTaskPromptSelectorNames.Language] = resolvedLocale,
    };
    if (!string.IsNullOrWhiteSpace(normalizedAgentFamily))
    {
        selectorInputs[PresetTaskPromptSelectorNames.Agent] = normalizedAgentFamily!;
    }

    foreach (var variant in PromptPackage.Variants)
    {
        if (!VariantMatches(variant, selectorInputs)) continue;
        return new PresetTaskResolvedPromptSelection(
            resolvedLocale, normalizedAgentFamily, variant.Id, false, "variants", variant.Template);
    }

    // 没有变体命中：落到显式声明的 fallback 变体
    return new PresetTaskResolvedPromptSelection(
        resolvedLocale, normalizedAgentFamily, PromptPackage.FallbackVariant?.Id, true,
        "variants", PromptPackage.FallbackVariant?.Template ?? PromptPackage.Locales[resolvedLocale]);
}
```

매칭 규칙 `VariantMatches`는 단순합니다. **변형이 선언한 selector는 런타임에서 모두 매칭되어야 하며, 선언하지 않은 차원은 제약하지 않습니다.**

```csharp
private static bool VariantMatches(
    PresetTaskPromptVariantDefinition variant,
    IReadOnlyDictionary<string, string> selectorInputs)
{
    foreach (var selector in variant.Match)
    {
        if (!selectorInputs.TryGetValue(selector.Key, out var runtimeValue))
            return false;
        if (!selector.Value.Contains(runtimeValue, StringComparer.OrdinalIgnoreCase))
            return false;
    }
    return true;
}
```

이 규칙 덕분에 fallback 변형이 `language`만 적어도 모든 Agent를 포괄할 수 있습니다. `agent` 차원을 제약하지 않기 때문에, language만 일치하면 어떤 Agent든 매칭됩니다. 반면 native 변형은 `agent`를 추가로 제약하므로 claude/codex만 조건을 만족합니다.

Agent 계열은 어디서 오는가? 런타임에서 선택된 영웅의 실행기 타입을 매핑해서 얻으며, 구현은 `PresetTaskRequirementModels.cs`에 있습니다.

```csharp
public static string? Resolve(AIProviderType? executorType) => executorType switch
{
    AIProviderType.ClaudeCodeCli => Claude,
    AIProviderType.CodexCli      => Codex,
    AIProviderType.GitHubCopilot => Copilot,
    AIProviderType.IFlowCli      => Iflow,
    AIProviderType.OpenCodeCli   => Opencode,
    // ... gemini / kimi / qoder / kiro / hermes / codebuddy / pi ...
    _ => null,
};
```

`SessionsController.PresetTasks.cs`는 세션을 만들 때 먼저 영웅을 가져오고, `PresetTaskAgentFamilies.Resolve(hero.ExecutorType)`로 계열 이름을 얻어 `ResolvePromptSelection`에 전달합니다. 변형이 선택되면 `RenderPrompt`가 Handlebars로 템플릿을 렌더링하고, `preludeTemplate`으로 만든 `/goal <목표>`를 맨 앞에 붙입니다.

```csharp
var renderedPrompt = prompt.FillTemplate(normalizedContext);
var commandPrelude = BuildCommandPrelude(normalizedContext); // -> "/goal <goalDescription>"
return string.IsNullOrWhiteSpace(commandPrelude)
    ? renderedPrompt
    : $"{commandPrelude}\n\n{renderedPrompt}";
```

### 실행 조건 완화: allowlist에서 `any`로

폴백 프롬프트가 있으므로 `goal`이 네이티브가 아닌 Agent를 문 밖에서 막을 이유가 없어졌습니다. `backend/task-preset.json`의 `requirements`를 `["claude","codex"]`에서 `any`로 완화했습니다.

```jsonc
{
  "taskKey": "goal",
  "requirements": [ { "type": "agent", "name": "any" } ],
  "inputBindings": [
    { "input": "goalCommandIds",  "promptParameter": "goalCommandIds",  "required": true },
    { "input": "goalDescription", "promptParameter": "goalDescription", "required": true },
    { "input": "targetScopeMarkdown", "promptParameter": "targetScopeMarkdown", "producer": "frontend-computed" }
  ]
}
```

실행 조건은 열고 차이는 프롬프트 층으로 내리는 것, 이것이 이 설계의 핵심적인 절충입니다. **호환성은 "실행 가능한가"라는 스위치가 아니라, "어떤 프롬프트로 실행할 것인가"라는 라우팅이 됩니다.**

## 실천

### 한 번의 실행이 전체적으로 어떻게 흘러가는가

1. 사용자가 `goal` 서랍에서 목표 설명을 입력하고, 저장소 범위를 고르고, 영웅을 선택한 뒤 제출합니다.
2. 백엔드가 선택된 영웅의 실행기 타입에 따라 Agent 계열(예: `claude` / `gemini`)을 구합니다.
3. `ResolvePromptSelection(locale, agentFamily)`가 `agent × language`로 변형을 찾습니다.
   - claude/codex + zh-CN → `native-zh-cn`
   - gemini + zh-CN → native에 매칭되지 않으므로 `fallback-zh-cn`
4. `RenderPrompt`가 선택된 템플릿을 렌더링하고, 맨 앞에 `/goal <목표 설명>`을 붙입니다.
5. 네이티브 Agent는 첫 줄을 명령으로 실행합니다. 폴백 Agent는 system 프롬프트의 지시에 따라 첫 줄을 메타데이터로 해석하고, 일반적인 프롬프트 따르기로 지속 작업을 재현합니다.

### 자신의 프리셋에 Agent 인식 추가하기

새 프리셋에 같은 적응을 적용하려면 방법은 정해져 있습니다.

1. `prompts.json`에서 `locales` 대신 `variants`를 사용하고, `selectors`에 `agent`를 추가합니다.
2. native 변형은 `agent`와 `language`를 함께 `match`에 씁니다. fallback 변형은 `language`만 씁니다.
3. 최상위에 `variants.fallback`을 선언해 최종 보험으로 둡니다(스키마상 variants 모드에는 fallback이 필수입니다).
4. 백엔드 코드는 바꿀 필요가 없습니다. `ResolvePromptSelection`과 `VariantMatches`는 범용입니다.
5. 실행 조건을 제한할 필요가 없다면 `requirements`의 agent를 `any`로 설정합니다.

### 자주 밟는 함정

- **변형의 순서가 곧 우선순위입니다.** native가 fallback보다 앞에 있어야 합니다. 그렇지 않으면 language만 제약하는 fallback이 모든 Agent를 먼저 가져가서, claude/codex가 네이티브 분기에 영영 도달하지 못합니다.
- **폴백 프롬프트는 `/goal` 줄을 명시적으로 "격하"해야 합니다.** 접두사 `/goal ...`은 `preludeTemplate`에 의해 무조건 붙습니다. 따라서 폴백 system 프롬프트의 "이것을 메타데이터로 보고 글자 그대로 실행하지 말 것"이라는 문장을 생략하면, 네이티브가 아닌 Agent가 이를 유효하지 않은 명령으로 처리할 수 있습니다.
- **비대화형 제약은 모든 템플릿에 명시해야 합니다.** `goal`은 대기열에서 실행되는 auto-task입니다. 템플릿에서 "AskUserQuestion을 사용하지 말 것, 되묻지 말 것, 합리적인 가정으로 진행하고 그 가정을 명시할 것"을 반복해서 강조하는 이유는, 무인 실행 중에 Agent가 입력을 기다리며 멈추는 일을 막기 위해서입니다.
- **저장소 경계는 샌드박스가 아니라 프롬프트로 제약합니다.** 템플릿은 "명시적으로 쓰기 가능으로 선택된 저장소 안에서만 수정하고, 읽기 전용 저장소는 보조 맥락으로만 사용할 것"을 분명히 요구합니다. 이것은 프롬프트 층의 연성 제약이므로, 저장소 범위를 설정할 때 신중하게 입력해야 합니다.
- **하위 호환에는 공짜 점심이 있습니다.** `variants` 없이 `locales`만 있는 기존 프리셋은 `UsesVariants`가 false가 되어 `legacy-locales` 경로를 그대로 타므로 전혀 영향을 받지 않습니다. 새 모델에 맞추려고 기존 프리셋을 고칠 필요가 없습니다.

## 요약

"Agent가 네이티브로 `goal`을 지원하지 않는다면 어떻게 확장해서 구현할 것인가"에 대한 답은 Agent마다 분기를 하드코딩하는 것이 아니라, 차이를 `agent × language` 프롬프트 변형으로 모델링하는 것이었습니다.

- 네이티브를 지원하는 Agent(Claude / Codex)는 native 변형을 사용하여 `/goal` 명령 표면을 그대로 씁니다.
- 지원하지 않는 Agent는 fallback 변형을 사용하여 `/goal ...`을 목표 메타데이터로 명시적으로 격하하고, 일반적인 프롬프트 따르기로 같은 지속 작업 동작을 재현합니다.
- 매칭은 "변형이 선언한 selector는 반드시 모두 일치해야 한다"는 범용 규칙과 단계적 폴백으로 이루어지며, 백엔드는 한 번의 파싱으로 결정합니다.
- 실행 조건은 allowlist에서 `any`로 완화되어, 호환성은 "실행 가능한가"에서 "어떤 프롬프트로 실행할 것인가"로 바뀝니다.

이 설계의 가치는 `goal` 프리셋 하나에만 있지 않습니다. `agent × language` 선택기와 폴백 모델은 범용적이므로, Agent 능력에 따라 다른 지시를 줘야 하는 모든 프리셋이 재사용할 수 있습니다. 게다가 기존 프리셋에는 아무 영향도 주지 않습니다.
