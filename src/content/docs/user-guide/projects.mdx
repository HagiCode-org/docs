**项目**就是 HagiCode 工作所在的文件夹。会话、Git 状态、标准用语和 MonoSpecs 设置都归属于某个项目，所以工作台左侧边缘的项目栏是大多数工作的起点。

## 项目栏

项目栏默认折叠，每个项目只显示一个圆形图标。点击项目栏顶部的小箭头即可展开。

![展开后的项目栏，列出 All Sessions 和 orbit-notes 项目，并带有添加项目的加号按钮](../img/user-guide/workbench/02-project-rail.png)

- **All Sessions**（全部会话）在同一个看板上显示所有项目的会话。
- 点击某个项目，看板会只显示该项目的会话，并在项目面板中展示它。
- 绿色的 **+** 按钮用于新建项目。它旁边的箭头可再次折叠项目栏。

:::tip[哪些项目会进入“All Sessions”看板？]
在 **Settings → Process & Interaction → Session List**（设置 → 流程与交互 → 会话列表）中，可以把范围从 *All Projects*（全部项目）切换为 *Custom Selection*（自定义选择）的若干项目。参见[设置](/user-guide/settings)。
:::

## 新建项目

点击项目栏中的 **+**，打开 **New Project**（新建项目）对话框。它提供三种添加项目的方式。

### 单个项目

磁盘上已有项目文件夹时使用这种方式。对应 **Single Project**（单个项目）标签页。

![新建项目对话框的 Single Project 标签页，已填写名称、文件夹路径和描述](../img/user-guide/projects/01-create-project.png)

| 字段 | 说明 |
| --- | --- |
| **Project Name**（项目名称） | 必填，最多 200 个字符。 |
| **Folder Path**（文件夹路径） | 必填，最多 1000 个字符。填写文件夹的绝对路径，例如 `/home/user/projects/orbit-notes`。 |
| **Project Description**（项目描述） | 选填，最多 1000 个字符。 |

当路径中包含 `.hagicode/monospecs.yaml` 时，对话框会识别出来，并为该项目显示 MonoSpecs 指引。参见 [MonoSpecs](/guides/monospecs)。

### 批量新建

多个仓库放在同一个父文件夹下时使用这种方式。对应 **Batch Create**（批量新建）标签页。

![新建项目对话框的 Batch Create 标签页，要求选择要扫描的文件夹](../img/user-guide/projects/02-create-project-batch.png)

填写父文件夹的完整路径。HagiCode 会向下扫描最多三层目录查找 Git 仓库，并把找到的每个仓库登记为一个项目。

### 演示项目

想在连接自己的代码之前先体验 HagiCode 时使用这种方式。对应 **Demo Project**（演示项目）标签页。

![新建项目对话框的 Demo Project 标签页，显示 MonoSpecs Demo 仓库及其目标路径](../img/user-guide/projects/03-create-project-demo.png)

HagiCode 会克隆官方 MonoSpecs Demo 仓库（`https://github.com/HagiCode-org/monospecs-demo`）并登记为项目。这需要你的机器上装有 Git。界面中显示的是默认路径，实际文件夹取决于你的运行时数据目录。

## 项目面板

选中一个项目后，看板右侧会显示该项目的项目面板。

![orbit-notes 项目的项目面板，包含 Quick actions 和 Repository status](../img/user-guide/workbench/06-project-panel.png)

**Quick actions**（快速操作）

| 按钮 | 作用 |
| --- | --- |
| **自动超级提交** | 为项目启动一次 AI 辅助提交。参见 [超级提交](/guides/ai-compose-commit)。 |
| **Open Code Server**（打开 Code Server） | 在基于浏览器的代码编辑器中打开项目。 |
| **Open Git Management**（打开 Git 管理） | 打开项目详情抽屉的 Git 标签页。 |
| **View Project Details**（查看项目详情） | 打开项目详情抽屉。 |

**Repository status**（仓库状态）列出项目的每个仓库及其当前分支。彩色圆点表示工作区状态；截图中的圆点是红色，因为 `src/server.js` 有未提交的更改。点击刷新按钮可重新读取状态。

看板工具栏中的 **Recent changes**（最近变更）菜单列出最近有变更的仓库。仓库有变更之前，它显示“暂无最近变更”。

## 项目详情

点击 **View Project Details** 打开抽屉。它有四个标签页。

### 详情

对应 **Details**（详情）标签页。

![项目详情抽屉的 Details 标签页，显示名称、路径、描述和图标设置](../img/user-guide/projects/04-project-details.png)

- **Name**（名称）、**Path**（路径）和 **Description**（描述）：项目的基本信息。
- **Icon Settings**（图标设置）：为项目头像选择 *Game Icon*（游戏图标）或 *Text Abbreviation*（文本缩写）。**Change Icon**（更改图标）会打开图标选择器。
- **Manage DESIGN.md**（管理 DESIGN.md）：管理项目的 `DESIGN.md` 文件。
- **Delete Project**（删除项目）：输入项目名称确认后删除项目。确认对话框会列出将被永久删除的内容：项目中的所有会话以及这些会话中的所有消息。此操作无法撤销。

### MonoSpecs

![MonoSpecs 标签页，提示为项目初始化 MonoSpecs](../img/user-guide/projects/05-project-monospecs.png)

MonoSpecs 会把项目变成一个协调规格与多个仓库的工作区。对于尚未成为 MonoSpecs 工作区的项目，**Initialize MonoSpecs**（初始化 MonoSpecs）只会创建必需的内容，不会自动克隆任何仓库：

- `.hagicode/monospecs.yaml`
- 用于存放子仓库的 `repos/` 文件夹
- `openspec/changes/archive/` 和 `openspec/specs/`
- 对 `.gitignore` 的更新，使 `repos/` 文件夹保持不被跟踪

初始化之前请先阅读 [MonoSpecs 指南](/guides/monospecs)。

### 标准用语

对应 **Standard Words**（标准用语）标签页。

![Standard Words 标签页，分组列表为空，带有 Add group 按钮](../img/user-guide/projects/06-project-standard-words.png)

标准用语是项目共享的术语，存放在 `.hagicode/standard_words.yaml` 中。该标签页显示分组、短语和标签的数量，并支持搜索、**Add group**（新增分类）、从磁盘 **Refresh**（刷新）以及 **Save changes**（保存更改）。

### Git

![Git 标签页，左侧是仓库列表，右侧是仓库概要以及 Push、Pull 和 Super Commit 操作](../img/user-guide/projects/07-git-management.png)

Git 标签页是项目的 Git 控制台。

- **仓库列表**（左侧）显示被监控的仓库；计数（例如 `1 / 15`）把它们与 **Settings → Integration → Git**（设置 → 集成 → Git）中的监控上限作比较。批量操作可使用 **Select Changed**（选中有变更的仓库）、**Select All**（选中全部仓库）和 **Clear Selection**（清空选择），也可以按名称搜索。**Manage Super Commit All exclusions**（管理超级提交全部排除项）用来控制快速提交会跳过哪些文件。
- **仓库概要**（右侧）显示分支、同步状态、是否有未提交的更改、远程仓库和仓库路径。
- 针对当前聚焦仓库的操作：**Super Commit**（超级提交）、**Push**（推送）、**Pull**（拉取）、**Rebase Upstream**（Rebase 上游分支）、**Open Remote Repository**（打开远程仓库）、**Open Code Server** 和 **Manage DESIGN.md**。

这里的概要有意取代了 diff 预览。需要更深入的 Git 操作时，请使用 **Open Code Server**。

配置文件（Git Profile）、状态监控和默认超级提交动作等 Git 行为，在 **Settings → Integration → Git** 中配置。

## .hagicode 数据文件

项目自己的数据文件统一放在项目根目录下的 `.hagicode/` 文件夹中，可以随 Git 一起提交。目前包括：

- `.hagicode/monospecs.yaml`：MonoSpecs 配置，参见上文 **MonoSpecs** 一节。
- `.hagicode/standard_words.yaml`：标准用语，参见上文 **标准用语** 一节。
- `.hagicode/plans/`：计划定义，见下文。

### 计划定义（.hagicode/plans/）

项目的每个计划对应 `.hagicode/plans/` 下的一个文件。计划的配置写在文件里，因此可以像其他项目文件一样查看、回滚和分享。计划的运行状态不写在文件里，见下文 **文件中不保存的内容**。

**文件形式**

| 文件名 | 范围 | 说明 |
| --- | --- | --- |
| `<名称>.yaml` | 团队（`team`） | 团队计划，随项目一起提交到 Git，团队成员共享。 |
| `<名称>.user.yaml` | 个人（`personal`） | 个人计划，只属于你自己。 |

范围由文件名的后缀决定，不写在文件内容里。应用只读取该文件夹顶层的文件；子文件夹中的文件，以及 `.yml`、`.yaml.bak`、`.md` 等其他文件都会被忽略。文件夹不存在时，项目没有计划；读取计划不会创建文件夹，保存第一个计划时才会创建。

**文件名规则**

- 名称部分（去掉 `.yaml` 或 `.user.yaml` 后剩下的部分）只能使用英文字母、数字和连字符，例如 `weekly-release-check`。包含空格、下划线、点号或路径分隔符，或以点号开头的名称，都不会被读取为计划。
- 同一文件夹中，如果一个 `.yaml` 文件和一个 `.user.yaml` 文件的名称部分相同（字母大小写不计），两个文件都不会被读取为计划，应用会报告这个冲突。请重命名其中一个文件。
- 重命名文件会得到一个新的计划，原来的计划不再存在。

**忽略个人计划**

个人计划通常不应提交到 Git。在项目的 `.gitignore` 中加入下面这一行，即可排除所有个人计划，团队计划不受影响：

```gitignore
.hagicode/plans/*.user.yaml
```

HagiCode 不会修改 `.gitignore`，这一行需要你自己添加。

**字段**

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `schemaVersion` | 否 | 文件格式版本，写 `"1.0"`。读取时不做校验。 |
| `type` | 是 | `proposal`（提案计划）或 `hagitask`（HagiTask 计划）。 |
| `name` | 是 | 计划名称，不能为空白，最多 200 个字符。 |
| `enabled` | 否 | `true` 或 `false`，默认 `true`。设为 `false` 的计划不会自动运行。 |
| `payload` | 是 | 任务输入。字段名与对应的创建请求相同（驼峰命名），例如提案计划使用 `title`、`chiefComplaint`，HagiTask 计划使用 `presetTaskId` 等字段。`title` 必填。计划中不能附带图片，`draftImageRefs` 必须省略或为空列表。 |
| `schedule` | 是 | 时间表，见下表。 |
| `agentPool` | HagiTask 计划必填 | Agent 池。`strategy` 只能是 `random`；`agents` 必须且只能包含一个 Agent，并写该 Agent 的 `heroId`。提案计划可以省略。 |
| `exceptions` | 否 | 单独修改或删除某一次时由应用写入的列表，手写时可以省略。 |

`payload.projectId` 可以省略，省略时计划属于文件所在的项目。如果写了，它必须与该项目的 ID 相同，否则这个文件会被跳过并报告问题。计划所属的项目由文件夹决定，文件本身不能把计划绑定到其他项目。

**时间表（schedule）**

| 写法 | 说明 |
| --- | --- |
| `mode: once` | 单次计划，必须写 `runAt`。建议写带时区偏移的时间，例如 `2026-11-02T09:00:00+08:00`；不写偏移时，按运行后端所在机器的本地时区解释。通过应用创建或修改时，`runAt` 必须晚于当前时间。 |
| `mode: recurring` | 周期计划，必须写 `timeZone`（IANA 时区，例如 `Asia/Shanghai`）、`startDate` 和 `endDate`（`yyyy-MM-dd` 格式，两端都包含）、`timeOfDay`（`HH:mm` 格式）和 `repeat`。 |
| `endDate` | 不能早于 `startDate`。 |
| `repeat.rule` | `daily`（每天）或 `weekly`（每周）。 |
| `repeat.weekdays` | `weekly` 时必填，至少一天，写英文星期名，即 `monday` 到 `sunday`。 |

**文件中不保存的内容**

计划文件只保存配置。计划的状态和下次运行时间由应用记录在本机的调度状态中，不会写入计划文件。因此计划运行时，文件内容保持不变。计划的创建和更新时间没有单独保存，显示时取自文件的修改时间。

**手动创建计划**

1. 在项目根目录下创建 `.hagicode/plans/` 文件夹（如果还不存在）。
2. 新建文件，名称按上面的规则命名，例如团队计划 `weekly-release-check.yaml`，或个人计划 `weekly-release-check.user.yaml`。
3. 把下面的示例复制进文件，按需修改，保存为 UTF-8 文本。
4. 保存后，应用会发现这个文件，计划出现在该项目的计划列表中。

```yaml
schemaVersion: "1.0"
type: proposal
name: Weekly release check
enabled: true
payload:
  title: Weekly release check
  chiefComplaint: 检查本周待发布的变更，列出需要补充的发布说明。
schedule:
  mode: recurring
  timeZone: Asia/Shanghai
  startDate: 2026-11-02
  endDate: 2026-12-31
  timeOfDay: "09:00"
  repeat:
    rule: weekly
    weekdays:
      - monday
```

**格式错误的文件**

无法解析或不符合上述规则的文件会被跳过，应用会在问题列表中报告它的路径，其他计划照常读取和运行。应用不会改写、重命名或删除被跳过的文件。修正文件后，应用会重新读取它。

**旧的全局计划文件**

早期版本把所有计划保存在一个全局的 `scheduled-plans.json` 中。应用不会读取、转换或删除这个文件，其中的计划不会显示，也不会运行。需要保留的计划请在项目的 `.hagicode/plans/` 中重新创建。
