## Tornar todos os Agents capazes de `/goal`: design de extensão compatível do predefinido de trabalho contínuo do HagiCode

## Introdução

Ao atribuir a um Agente de IA uma tarefa de "trabalho contínuo", o ideal é assim: você escreve um objetivo, escolhe os repositórios que podem ser alterados, clica em enviar, e o Agente avança em direção a esse objetivo do começo ao fim, sem interromper com perguntas, sem fugir do assunto e sem alterar outros repositórios fora do escopo.

No HagiCode, essa capacidade tem uma entrada dedicada: a tarefa predefinida `goal`, cuja superfície de comando é `/goal`. O problema é que **nem todo Agente reconhece `/goal`.** Claude e Codex têm semântica nativa de comando para trabalho contínuo, então recebem `/goal` diretamente. Já outras CLIs (Gemini, Copilot, iFlow, OpenCode etc.) simplesmente não têm esse comando de barra. Se o `/goal ...` for enviado literalmente, na melhor das hipóteses será tratado como comando inválido e, na pior, será executado ao pé da letra e causará problemas.

A solução mais simples no início seria permitir o `goal` apenas no Claude e no Codex e recusar todos os outros Agentes. Mas isso deixaria de fora grande parte da matriz de Agentes. Este artigo descreve como fizemos esse caminho funcionar: **usando variantes de prompt sensíveis ao Agente, os Agentes com suporte nativo seguem o comando nativo e os que não têm suporte seguem um prompt de fallback, com comportamento alinhado e experiência consistente.**

O conteúdo se baseia no pacote predefinido `goal` em `repos/hagitask` e na implementação de parsing do backend em `repos/hagicode-core`.

## Contexto

### O que é `goal`

`goal` é um pacote de plugin de tarefa predefinida embutido, localizado em `repos/hagitask/presets/goal/`. Seu `manifest.json` declara a identidade do plugin, o ícone, os pacotes de localização e os recursos de front-end e back-end:

```jsonc
{
  "taskPresetId": "goal",
  "version": "1.0.0",
  "icon": "flag",
  "kind": "custom-executor",
  "status": "experimental",
  "entrypoints": { "menuSurface": "session-create", "drawerId": "goal" },
  "ui": { "panel": "./frontend/panel.json", "commands": "./frontend/commands.json" },
  "backend": {
    "taskPreset": "./backend/task-preset.json",
    "prompts": "./backend/prompts.json"
  }
}
```

Seu posicionamento é o de "modo de trabalho contínuo": o usuário preenche uma descrição do objetivo (`goalDescription`), opcionalmente delimita o escopo de repositórios com permissão de escrita ou somente leitura, e o backend monta uma execução de auto-task não interativa. Os campos principais de `panel.json` no painel de front-end são:

- `goalCommandIds`: seletor de comando; o padrão tem apenas um `/goal`;
- `goalDescription`: descrição obrigatória do objetivo;
- `targetRepositories`: seletor de acesso a repositórios, que distingue leitura e escrita.

### De onde vem o `/goal`

A superfície de comando é definida em `frontend/commands.json`, cujo núcleo é uma única linha, `preludeTemplate`:

```jsonc
{
  "commands": [
    {
      "id": "goal",
      "label": "goal",
      "preludeTemplate": "/goal {goalDescription}"
    }
  ]
}
```

Ou seja, o prompt final enviado ao Agente terá uma linha `/goal <descrição do objetivo>` antes do corpo. Para Claude e Codex, essa linha é um comando que eles reconhecem. Para os outros Agentes, é algo que precisa ser "traduzido". A dificuldade central de adaptação de todo o artigo é exatamente o fato de que essa linha `/goal ...` tem significados divergentes em cada Agente.

## Análise

### Um template por locale não dá conta

Os pacotes de prompt iniciais do HagiTask eram **separados apenas por idioma**: em `prompts.json`, cada locale declarava um conjunto de `systemTemplate` e `userTemplate`. O `PresetTaskCatalogProvider` do backend os carregava em `PromptPackage.Locales` e, em tempo de execução, escolhia um conjunto de acordo com o idioma da requisição para renderizar.

Esse modelo basta para predefinições cujas instruções de execução são independentes do Agente. Mas o `goal` não é assim:

- Claude e Codex: podem depender diretamente da superfície nativa do comando `/goal`;
- Outros Agentes: precisam de um prompt mais longo e explícito que ensine "como entrar no modo de trabalho contínuo", e também precisam ser instruídos a não executar `/goal ...` como comando.

Dentro do mesmo locale, passam a existir duas instruções completamente diferentes, e separar apenas por idioma já não basta. Precisamos introduzir uma dimensão além do idioma: **a família do Agente**.

### Recusar a execução não é boa solução

Originalmente, o `requirements` do `goal` limitava o Agente a `["claude", "codex"]`, e os demais eram marcados diretamente como incompatíveis. Isso trazia dois problemas no produto:

1. No painel de seleção de herói, quase nenhum herói compatível sobrava, e era fácil ficar sem opção;
2. Muitos Agentes são capazes de realizar trabalho contínuo, só não têm o `/goal` nativo. Recusar todos de uma vez desperdiçava essas capacidades.

Portanto, o problema real não é "quem pode executar", mas "**como, para o mesmo objetivo, fornecer instruções de execução diferentes porém equivalentes conforme a capacidade de cada Agente**". A resposta é levar a diferença sensível ao Agente para a camada de prompt e resolvê-la com variantes e fallback, em vez de barrar na camada de admissão.

## Solução

### Seletor de variantes: agente × idioma

O novo contrato de pacote de prompt introduz `variants` em `prompts.json`. Ele usa `selectors` para declarar as dimensões de correspondência e `entries` para declarar, em cada variante, a regra de correspondência e os arquivos de template:

```jsonc
{
  "version": "1.1.0",
  "templateEngine": "handlebars",
  "variants": {
    "selectors": ["agent", "language"],
    "entries": [
      {
        "id": "native-zh-cn",
        "match": { "agent": ["claude", "codex"], "language": ["zh-CN"] },
        "systemTemplate": "./templates/zh-CN/native.system.md",
        "userTemplate": "./templates/zh-CN/native.user.hbs"
      },
      {
        "id": "fallback-zh-cn",
        "match": { "language": ["zh-CN"] },
        "systemTemplate": "./templates/zh-CN/fallback.system.md",
        "userTemplate": "./templates/zh-CN/fallback.user.hbs"
      }
      // ... native-en-us / fallback-en-us 同理
    ],
    "fallback": {
      "id": "fallback-default",
      "systemTemplate": "./templates/en-US/fallback.system.md",
      "userTemplate": "./templates/en-US/fallback.user.hbs"
    }
  }
}
```

Há três níveis de fallback, relaxando progressivamente:

1. **Variante nativa**: `match` restringe simultaneamente `agent` (claude/codex) e `language`, então só Agentes nativos casam;
2. **Variante fallback**: `match` restringe **apenas `language`, não `agent`**, então qualquer Agente pode casar. É o fallback para quem não tem `/goal` nativo;
3. **fallback-default**: a garantia final, usada quando nem o idioma casa.

A ordem é crucial: `entries` é percorrido na ordem de declaração, e a nativa vem antes da fallback. Assim, claude e codex casam primeiro com a nativa; os demais Agentes chegam à variante fallback do idioma.

### Dois templates: nativo versus fallback

Para o mesmo objetivo, a diferença entre os dois prompts de sistema está na postura em relação àquela linha `/goal`.

Template nativo (`templates/zh-CN/native.system.md`):

```text
你是 `goal` task preset plugin 的内置执行提示。

本次运行必须使用 `/goal` 作为持续工作模式的命令表面。把提供的项目路径与仓库范围视为权威工作边界。

这次运行处于非交互环境。不要追问用户；当合理假设可以继续推进时，直接继续并把这些假设明确写在响应里。
```

Template de fallback (`templates/zh-CN/fallback.system.md`):

```text
你是 `goal` task preset plugin 的兜底执行提示。

当前 agent 可能不支持原生 `/goal` 命令。如果提示前面出现了 `/goal ...` 这一行，把它视为预设附带的目标元数据，不要把它当成必须逐字执行的斜杠命令。

请以持续工作模式完成任务，并把提供的项目路径与仓库范围视为权威工作边界。

这次运行处于非交互环境。不要追问用户；当合理假设可以继续推进时，直接继续并把这些假设明确写在响应里。
```

O núcleo da estratégia de fallback está nesta frase: **"如果提示前面出现了 `/goal ...` 这一行，把它视为预设附带的目标元数据，不要把它当成必须逐字执行的斜杠命令。"** Ou seja, "se antes do prompt aparecer a linha `/goal ...`, trate-a como metadados de objetivo fornecidos pela predefinição, e não como um comando de barra a ser executado literalmente." A linha `/goal <objetivo>` que o `preludeTemplate` anexa ao início é, para o Agente nativo, um comando; para o Agente de fallback, é explicitamente rebaixada a "metadados ou marcador de objetivo", o que reproduz o mesmo comportamento de trabalho contínuo por meio de seguimento comum de prompt.

O template de usuário (`.hbs`) também tem dois conjuntos. O de fallback tem um parágrafo adicional de "instruções de roteamento", que informa explicitamente ao Agente que esta execução foi encaminhada para uma ramificação que não depende do `/goal` nativo, e pede que ele "não dependa do suporte nativo a `/goal`; use o seguimento comum de prompt para completar o mesmo comportamento de trabalho contínuo".

### Backend: uma resolução define tudo

A correspondência de variantes é feita em `ResolvePromptSelection`, em `PCode.Application/Services/PresetTaskCatalogProvider.cs`. Primeiro ela resolve o locale, depois coloca idioma e Agente em um dicionário de seletores e percorre em ordem, procurando a primeira variante que case:

```csharp
public PresetTaskResolvedPromptSelection ResolvePromptSelection(string? locale, string? agentFamily)
{
    var resolvedLocale = ResolvePromptLocale(locale);
    if (!PromptPackage.UsesVariants)
    {
        // 旧的仅按 locale 分文件的预设，走遗留路径，保持向后兼容
        var legacyTemplate = PromptPackage.Locales[resolvedLocale];
        return new PresetTaskResolvedPromptSelection(
            resolvedLocale, NormalizeAgentFamily(agentFamily), null, false,
            "legacy-locales", legacyTemplate);
    }

    var normalizedAgentFamily = NormalizeAgentFamily(agentFamily);
    var selectorInputs = new Dictionary<string, string>(StringComparer.OrdinalIgnoreCase)
    {
        [PresetTaskPromptSelectorNames.Language] = resolvedLocale,
    };
    if (!string.IsNullOrWhiteSpace(normalizedAgentFamily))
    {
        selectorInputs[PresetTaskPromptSelectorNames.Agent] = normalizedAgentFamily!;
    }

    foreach (var variant in PromptPackage.Variants)
    {
        if (!VariantMatches(variant, selectorInputs)) continue;
        return new PresetTaskResolvedPromptSelection(
            resolvedLocale, normalizedAgentFamily, variant.Id, false, "variants", variant.Template);
    }

    // 没有变体命中：落到显式声明的 fallback 变体
    return new PresetTaskResolvedPromptSelection(
        resolvedLocale, normalizedAgentFamily, PromptPackage.FallbackVariant?.Id, true,
        "variants", PromptPackage.FallbackVariant?.Template ?? PromptPackage.Locales[resolvedLocale]);
}
```

A regra de correspondência `VariantMatches` é simples: **cada seletor declarado pela variante precisa casar em tempo de execução**, e dimensões não declaradas não restringem nada:

```csharp
private static bool VariantMatches(
    PresetTaskPromptVariantDefinition variant,
    IReadOnlyDictionary<string, string> selectorInputs)
{
    foreach (var selector in variant.Match)
    {
        if (!selectorInputs.TryGetValue(selector.Key, out var runtimeValue))
            return false;
        if (!selector.Value.Contains(runtimeValue, StringComparer.OrdinalIgnoreCase))
            return false;
    }
    return true;
}
```

Isso explica por que a variante fallback, que só declara `language`, consegue abarcar qualquer Agente: ela não restringe a dimensão `agent`, então qualquer Agente com o idioma correspondente casa. Já a variante nativa, que também restringe `agent`, só é satisfeita por claude e codex.

De onde vem a família do Agente? Em tempo de execução, ela é mapeada a partir do tipo de executor do herói selecionado, em `PresetTaskRequirementModels.cs`:

```csharp
public static string? Resolve(AIProviderType? executorType) => executorType switch
{
    AIProviderType.ClaudeCodeCli => Claude,
    AIProviderType.CodexCli      => Codex,
    AIProviderType.GitHubCopilot => Copilot,
    AIProviderType.IFlowCli      => Iflow,
    AIProviderType.OpenCodeCli   => Opencode,
    // ... gemini / kimi / qoder / kiro / hermes / codebuddy / pi ...
    _ => null,
};
```

Ao criar a sessão, `SessionsController.PresetTasks.cs` primeiro obtém o herói e depois chama `PresetTaskAgentFamilies.Resolve(hero.ExecutorType)` para obter o nome da família, que é passado a `ResolvePromptSelection`. Depois de selecionada a variante, `RenderPrompt` renderiza o template com Handlebars e antepõe a linha `/goal <objetivo>` gerada por `preludeTemplate`:

```csharp
var renderedPrompt = prompt.FillTemplate(normalizedContext);
var commandPrelude = BuildCommandPrelude(normalizedContext); // -> "/goal <goalDescription>"
return string.IsNullOrWhiteSpace(commandPrelude)
    ? renderedPrompt
    : $"{commandPrelude}\n\n{renderedPrompt}";
```

### Relaxando a admissão: de allowlist para `any`

Com o prompt de fallback, não há mais necessidade de barrar os Agentes não nativos. Em `backend/task-preset.json`, `requirements` passa de `["claude","codex"]` para `any`:

```jsonc
{
  "taskKey": "goal",
  "requirements": [ { "type": "agent", "name": "any" } ],
  "inputBindings": [
    { "input": "goalCommandIds",  "promptParameter": "goalCommandIds",  "required": true },
    { "input": "goalDescription", "promptParameter": "goalDescription", "required": true },
    { "input": "targetScopeMarkdown", "promptParameter": "targetScopeMarkdown", "producer": "frontend-computed" }
  ]
}
```

Abrir a camada de admissão e empurrar as diferenças para a camada de prompt é a escolha central de todo o esquema: **a compatibilidade deixa de ser um interruptor de "pode executar ou não" e passa a ser um roteamento de "qual prompt usar para executar".**

## Prática

### Como é uma execução completa, de ponta a ponta

1. O usuário preenche, na gaveta do `goal`, a descrição do objetivo, escolhe o escopo dos repositórios e o herói, e envia;
2. O backend resolve a família do Agente (como `claude` ou `gemini`) a partir do tipo de executor do herói selecionado;
3. `ResolvePromptSelection(locale, agentFamily)` procura a variante por `agent × language`:
   - claude/codex + zh-CN → `native-zh-cn`;
   - gemini + zh-CN → a nativa não casa, então cai em `fallback-zh-cn`;
4. `RenderPrompt` renderiza o template selecionado e antepõe `/goal <descrição do objetivo>`;
5. Agentes nativos executam a primeira linha como comando; Agentes de fallback, guiados pelo prompt de sistema, tratam a primeira linha como metadados e reproduzem o trabalho contínuo por seguimento comum de prompt.

### Adicionando sensibilidade ao Agente à sua própria predefinição

Se você quiser fazer a mesma adaptação em uma nova predefinição, o procedimento é fixo:

1. Em `prompts.json`, use `variants` no lugar de `locales` e adicione `agent` em `selectors`;
2. A variante nativa declara `agent` e `language` juntos em `match`; a variante fallback declara apenas `language`;
3. Declare também um `variants.fallback` de nível superior como garantia final (o schema exige que o modo variants tenha fallback);
4. O backend não precisa mudar, pois `ResolvePromptSelection` e `VariantMatches` são genéricos;
5. Se a admissão não deve restringir, defina o agente em `requirements` como `any`.

### Algumas armadilhas comuns

- **A ordem das variantes é a prioridade.** A nativa precisa vir antes da fallback. Caso contrário, a fallback, que restringe apenas o idioma, capturaria todos os Agentes primeiro, e claude e codex nunca chegariam à ramificação nativa.
- **O prompt de fallback precisa rebaixar explicitamente a linha `/goal`.** O prefixo `/goal ...` é anexado incondicionalmente (definido por `preludeTemplate`), então a frase do prompt de sistema de fallback que diz para tratá-la como metadados, e não executá-la ao pé da letra, não pode ser omitida. Sem ela, Agentes não nativos podem tratá-la como comando inválido.
- **A restrição de não interatividade precisa estar em todos os templates.** O `goal` é uma auto-task executada em fila. Os templates repetem "não use AskUserQuestion, não faça perguntas, continue com premissas razoáveis e registre-as" para evitar que o Agente trave esperando uma entrada que ninguém vai dar.
- **Os limites dos repositórios são impostos pelo prompt, não por sandbox.** Os templates exigem "modificar apenas dentro dos repositórios explicitamente marcados como graváveis; repositórios somente leitura servem apenas como contexto complementar". Trata-se de uma restrição suave na camada de prompt, então é preciso preencher o escopo de repositórios com cuidado.
- **A compatibilidade retroativa vem de graça.** Predefinições antigas que não declaram `variants` e têm apenas `locales` têm `UsesVariants` como falso e seguem diretamente o caminho `legacy-locales`, sem nenhuma alteração. Não é preciso migrar predefinições existentes para o novo modelo.

## Resumo

"Se o Agente não suporta nativamente o `goal`, como estendemos o sistema para implementá-lo?" A resposta não é escrever um conjunto fixo de ramos para cada Agente, mas modelar a diferença como variantes de prompt `agent × language`:

- Agentes com suporte nativo (Claude e Codex) seguem a variante nativa e usam diretamente a superfície de comando `/goal`;
- Agentes sem suporte seguem a variante fallback, rebaixando explicitamente `/goal ...` a metadados de objetivo e reproduzindo o mesmo trabalho contínuo por seguimento comum de prompt;
- A correspondência usa a regra genérica "toda dimensão declarada pela variante precisa casar", somada a fallbacks em camadas, e o backend define tudo em uma única resolução;
- A admissão passa de allowlist para `any`: a compatibilidade deixa de ser "pode executar ou não" e passa a ser "qual prompt usar para executar".

O valor deste design não se limita à predefinição `goal`. O seletor `agent × language` com o modelo de fallback é genérico: qualquer predefinição que precise de "instruções diferentes conforme a capacidade do Agente" pode reutilizá-lo, e ele não afeta predefinições antigas.
