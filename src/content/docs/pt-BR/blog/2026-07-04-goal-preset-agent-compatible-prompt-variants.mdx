## Como usamos o impeccable para otimizar o design de interfaces front-end e a estabilidade da implementação

## Introdução

Muitas equipes enfrentam a mesma dor ao trabalhar com UI: a linguagem de design depende da experiência, os detalhes de interação dependem da memória, e o resultado final tende a "funcionar, mas não ser estável".

No monorepo do HagiCode, o `impeccable` não é usado como uma "ferramenta de inspiração". Ele é colocado em uma cadeia de engenharia executável, verificável e passível de regressão:

- A entrada da tarefa tem restrições estruturadas (comandos, cenários, escopo do repositório)
- O conteúdo do site e as definições de comandos upstream são alinhados automaticamente
- A porta de desenvolvimento local, os parâmetros de execução e o fluxo de validação são fixados

Este artigo se baseia na implementação atual do repositório e está dividido em quatro partes: Background, Analysis, Solution e Practice.

## Contexto (Background)

No snapshot atual do repositório, a linha principal diretamente relacionada ao `impeccable` está concentrada em três lugares:

1. **Orquestração de execução dos sites estáticos**: `scripts/static-sites-dev.mjs`
2. **Site de documentação do impeccable**: `repos/impeccable-site`
3. **Exemplo de contrato de UI task preset**: `designs/task-preset-plugin-examples/ui-master`

O terceiro item é um exemplo de design, não o código de runtime de backend em produção. Isso precisa ficar claro desde o início, para não confundir "contrato de design" com "comportamento já publicado".

## Análise (Analysis)

### 1) Estruturar primeiro a intenção de design para reduzir a instabilidade do "improviso"

No exemplo de contrato de backend do `ui-master`, as dependências e entradas são fixadas antes da execução.

`designs/task-preset-plugin-examples/ui-master/backend/task-preset.json`:

```json
{
  "taskKey": "uiMaster",
  "scriptKey": "autotask.ui-master",
  "requirements": [
    {
      "type": "skills",
      "name": "impeccable"
    },
    {
      "type": "cli",
      "name": "impeccable",
      "command": "npm",
      "args": ["exec", "--offline", "--", "impeccable", "--help"]
    }
  ],
  "inputBindings": [
    {
      "input": "uiMasterDescription",
      "promptParameter": "uiMasterDescription",
      "required": true
    },
    {
      "input": "uiMasterCommandIds",
      "promptParameter": "uiMasterCommandIds",
      "required": true
    },
    {
      "input": "sceneKey",
      "promptParameter": "sceneKey"
    }
  ]
}
```

Pontos-chave:

- Validar `skills:impeccable` e `cli:impeccable` antes, para não descobrir a quebra da cadeia só durante a execução.
- `uiMasterCommandIds` torna a entrada obrigatoriamente baseada em comandos, evitando descrições longas com direção pouco clara.
- `sceneKey` unifica a chave de cenário, evitando que cada preset invente seu próprio nome de entrada.

Para a estabilidade, o valor é direto: falhas são detectadas antes, são explicáveis e as entradas podem ser reproduzidas.

### 2) Unificar o catálogo de comandos e o roteamento de documentação para reduzir desvios semânticos

`designs/task-preset-plugin-examples/ui-master/frontend/commands.json` define os grupos de comandos, o template de rota da documentação e o prelúdio do comando:

```json
{
  "docs": {
    "baseUrl": "https://impeccable.hagicode.com",
    "routeTemplate": "/{lang}/docs/{commandId}",
    "languageResolver": "supported-language"
  },
  "commands": [
    {
      "id": "craft",
      "groupId": "build",
      "skill": "impeccable",
      "docsSlug": "craft",
      "preludeTemplate": "/impeccable {commandId} {uiMasterDescription}"
    }
  ]
}
```

Isso faz com que "executar o comando", "explicar o comando na documentação" e "roteamento de idioma" compartilhem o mesmo conjunto de IDs, reduzindo desalinhamentos comuns:

- A documentação chama de A, mas o painel chama de B
- A página em chinês leva a um comando errado em inglês
- O prelúdio do prompt e o slug da documentação não coincidem

### 3) Transformar a correção do conteúdo do site em um recurso verificável

Em `repos/impeccable-site/package.json`, o script `validate` encadeia toda a porta de qualidade:

```json
{
  "scripts": {
    "validate": "npm run i18n:check && npm run catalog:check && npm run typecheck && npm run test && npm run build"
  }
}
```

E o script por trás de `catalog:check` (`scripts/build-command-catalog.mjs`) faz uma validação rígida da estrutura do frontmatter:

```js
function parseFrontmatter(sourceText, sourcePath) {
  const match = sourceText.match(/^---\n([\s\S]*?)\n---\n?([\s\S]*)$/u);
  assert(match, `${sourcePath} must include YAML frontmatter`);
  const frontmatter = load(match[1]);
  assert(isPlainObject(frontmatter), `${sourcePath} frontmatter must be a mapping`);
  return {
    frontmatter,
    body: match[2].trim(),
  };
}
```

Esses asserts são simples, mas são essenciais para a estabilidade: é melhor falhar localmente e no CI do que descobrir após a publicação que um documento está sem algum campo.

### 4) Fixar porta e env no ambiente de desenvolvimento para evitar o "na minha máquina funciona"

No script raiz do monorepo, `scripts/static-sites-dev.mjs`, o `impeccable` é orquestrado explicitamente:

```js
{
  id: 'impeccable',
  name: 'Impeccable',
  repoPath: 'repos/impeccable-site',
  productionUrl: 'https://impeccable.hagicode.com/',
  command: 'npm',
  args: ['run', 'dev'],
  env: {
    PORT_IMPECCABLE_SITE: '36296'
  },
  portHint: 36296,
  order: 56
}
```

O teste `scripts/static-sites-dev.test.mjs` também faz asserções sobre esses valores (porta, args, env, productionUrl).

Esse método de "valores fixos + testes" não é sofisticado, mas é estável:

- A entrada local é unificada
- O caminho de diagnóstico é fixo
- Os links do site de documentação não se desviam

## Solução (Solution)

Se você quer usar o `impeccable` para melhorar ao mesmo tempo a **qualidade da interface** e a **estabilidade da implementação**, com base nas práticas atuais do repositório, isso pode ser organizado em quatro camadas.

### Camada 1: contratualizar a entrada da tarefa

Abordagem: reutilizar uma estrutura de preset como a do `ui-master`.

Objetivos:

- Limitar o escopo de repositórios permitidos (`targetRepositories`)
- Limitar a origem dos comandos (`uiMasterCommandIds`)
- Limitar o ponto de entrada do contexto (`uiMasterDescription`)

Benefício: cada despacho pode ser revisado depois, com a pergunta "qual foi a entrada e por que a mudança foi feita dessa forma".

### Camada 2: unificar a semântica dos comandos

Abordagem: vincular o trio ID do comando, slug da documentação e template de prelúdio.

Objetivos:

- O comando selecionado no painel leva à documentação com o mesmo ID
- `/impeccable <command>` no prompt e a explicação na documentação são consistentes

Benefício: reduz o risco oculto de "terminologia consistente, comportamento inconsistente".

### Camada 3: transformar a validação de conteúdo em processo

Abordagem: manter `npm run validate` como portão de qualidade antes do commit.

Objetivos:

- Nenhuma chave i18n ausente
- O catálogo de comandos não se desvia da estrutura upstream
- Tipos, testes e build passam de uma vez

Benefício: antecipa para o ambiente local os problemas de conteúdo que apareceriam de forma intermitente.

### Camada 4: padronizar o ambiente de execução

Abordagem: iniciar tudo pelo `static-sites-dev` e fixar `PORT_IMPECCABLE_SITE`.

Objetivos:

- Minimizar conflitos de porta em colaboração entre pessoas
- Caminho fixo para integração entre vários sites

Benefício: economiza tempo de configuração do ambiente e faz com que os problemas sejam localizados mais rapidamente no código em si.

## Prática (Practice)

### Passo 1: inicializar o impeccable-site

```bash
cd /home/newbe36524/repos/hagicode-mono/repos/impeccable-site
git submodule update --init --recursive
env -u NPM_CONFIG_PREFIX npm install
```

### Passo 2: desenvolvimento local e validação completa

```bash
env -u NPM_CONFIG_PREFIX npm run dev
env -u NPM_CONFIG_PREFIX npm run validate
```

O `validate` cobre de uma vez i18n, catalog, typecheck, test e build.

### Passo 3: executar pela orquestração unificada do monorepo

A partir da raiz do monorepo, use o sistema `scripts/static-sites-dev.mjs` e reutilize `PORT_IMPECCABLE_SITE=36296`, já definido.

O foco deste passo não é "conseguir rodar", mas "todos rodarem da mesma forma".

### Passo 4: transformar pedidos de UI em entradas baseadas em comandos

No fluxo de task preset, dê prioridade a transformar a demanda em:

- `uiMasterDescription`: objetivo de negócio
- `uiMasterCommandIds`: comandos desta vez (como `craft`, `audit`, `polish`)
- `sceneKey`: contexto de cenário

Só então entre na fase de alteração, reduzindo mudanças diretas na UI que desviam a direção.

### Passo 5: explicitar as lacunas de material atuais

Com base no snapshot atual do repositório, é possível confirmar que:

- A cadeia de site e validação do `impeccable-site` está implementada no código.
- A integração mais profunda entre `ui-master` e `impeccable` aparece principalmente em `designs/task-preset-plugin-examples` e nos documentos de design.

Se você quiser afirmar que "está totalmente habilitado no backend de produção", as evidências atuais não são suficientes. Não faça essa conclusão por enquanto.

## Informações sobre o HagiCode

HagiCode é uma plataforma que integra projetos com múltiplos repositórios, execução de tarefas com IA, sites de documentação e cadeia de ferramentas. Seu núcleo não é apenas "gerar código" pontualmente, mas encadear restrições de entrada de tarefas, contexto de execução, portões de validação e colaboração entre repositórios em um pipeline estável. Cenários típicos incluem: iteração estruturada de UI, integração de funcionalidades entre repositórios, produção de conteúdo técnico orientada por especificações e entrega automatizada com portões de qualidade.

## Resumo

O valor real do `impeccable` não está em "ajudar você a pensar em um botão mais bonito", mas em "transformar a otimização da interface em engenharia". Na prática atual do HagiCode, isso é feito com quatro ações: contratualizar tarefas, unificar a semântica dos comandos, antecipar a validação de conteúdo e padronizar o ambiente de execução. Consolidar primeiro essas bases e só depois pensar em melhorias de design mais sofisticadas traz mais retorno e é mais sustentável.
