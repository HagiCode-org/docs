## Cómo usamos impeccable para optimizar el diseño de interfaces frontend y la estabilidad de su implementación

## Introducción

Muchos equipos que trabajan en UI tienen el mismo problema: el lenguaje de diseño depende de la experiencia, los detalles de interacción dependen de la memoria, y al final el resultado tiende a ser "funciona, pero no es estable".

En el monorepo de HagiCode, `impeccable` no se usa como una "herramienta de inspiración". Se integra en una cadena de ingeniería ejecutable, verificable y repetible:

- La entrada de las tareas tiene restricciones estructuradas (comandos, escenarios, alcance del repositorio)
- El contenido del sitio y las definiciones de comandos upstream se alinean automáticamente
- El puerto de desarrollo local, los parámetros de ejecución y el flujo de validación están fijados

Este artículo se basa en la implementación actual del repositorio y se divide en cuatro bloques: Background, Analysis, Solution y Practice.

## Antecedentes (Background)

En la instantánea actual del repositorio, la línea principal directamente relacionada con `impeccable` está en tres lugares:

1. **Orquestación de ejecución del sitio estático**: `scripts/static-sites-dev.mjs`
2. **Sitio de documentación de impeccable**: `repos/impeccable-site`
3. **Ejemplo de contrato de preset de tarea de UI**: `designs/task-preset-plugin-examples/ui-master`

El tercer bloque es un ejemplo de diseño, no el código de runtime de backend en producción. Conviene aclararlo primero para no confundir un "contrato de diseño" con un "comportamiento ya publicado".

## Análisis (Analysis)

### 1) Estructurar primero la intención de diseño para reducir las oscilaciones por "improvisación libre"

En el ejemplo de contrato de backend de `ui-master`, primero se fijan las dependencias y las entradas, y solo después se pasa a la ejecución.

`designs/task-preset-plugin-examples/ui-master/backend/task-preset.json`:

```json
{
  "taskKey": "uiMaster",
  "scriptKey": "autotask.ui-master",
  "requirements": [
    {
      "type": "skills",
      "name": "impeccable"
    },
    {
      "type": "cli",
      "name": "impeccable",
      "command": "npm",
      "args": ["exec", "--offline", "--", "impeccable", "--help"]
    }
  ],
  "inputBindings": [
    {
      "input": "uiMasterDescription",
      "promptParameter": "uiMasterDescription",
      "required": true
    },
    {
      "input": "uiMasterCommandIds",
      "promptParameter": "uiMasterCommandIds",
      "required": true
    },
    {
      "input": "sceneKey",
      "promptParameter": "sceneKey"
    }
  ]
}
```

Puntos clave:

- Se validan `skills:impeccable` y `cli:impeccable` por adelantado, para no descubrir una cadena rota durante la ejecución.
- `uiMasterCommandIds` obliga a una entrada basada en comandos, para evitar descripciones muy largas con una dirección poco clara.
- `sceneKey` unifica la clave de escenario, para que cada preset no invente su propio conjunto de nombres de entrada.

Desde el punto de vista de la estabilidad, esta estructura aporta algo directo: los fallos se detectan antes, son explicables y las entradas se pueden reproducir.

### 2) Unificar el catálogo de comandos y el enrutamiento de documentación para reducir la deriva semántica

`designs/task-preset-plugin-examples/ui-master/frontend/commands.json` define los grupos de comandos, la plantilla de enrutamiento de documentación y el prelude de cada comando:

```json
{
  "docs": {
    "baseUrl": "https://impeccable.hagicode.com",
    "routeTemplate": "/{lang}/docs/{commandId}",
    "languageResolver": "supported-language"
  },
  "commands": [
    {
      "id": "craft",
      "groupId": "build",
      "skill": "impeccable",
      "docsSlug": "craft",
      "preludeTemplate": "/impeccable {commandId} {uiMasterDescription}"
    }
  ]
}
```

Esto hace que "ejecutar el comando", "explicar el comando en la documentación" y "enrutar el idioma" compartan el mismo conjunto de IDs, lo que reduce los desajustes habituales:

- La documentación lo llama A, mientras el panel lo llama B
- La página en chino enlaza a un comando equivocado en inglés
- El prelude del prompt y el slug de la documentación no coinciden

### 3) Convertir la corrección del contenido del sitio en un activo verificable

En `repos/impeccable-site/package.json`, `validate` encadena toda la puerta de calidad:

```json
{
  "scripts": {
    "validate": "npm run i18n:check && npm run catalog:check && npm run typecheck && npm run test && npm run build"
  }
}
```

Además, el script detrás de `catalog:check` (`scripts/build-command-catalog.mjs`) hace una validación estricta de la estructura del frontmatter:

```js
function parseFrontmatter(sourceText, sourcePath) {
  const match = sourceText.match(/^---\n([\s\S]*?)\n---\n?([\s\S]*)$/u);
  assert(match, `${sourcePath} must include YAML frontmatter`);
  const frontmatter = load(match[1]);
  assert(isPlainObject(frontmatter), `${sourcePath} frontmatter must be a mapping`);
  return {
    frontmatter,
    body: match[2].trim(),
  };
}
```

Este tipo de assert es sencillo, pero para la estabilidad es muy importante: es mejor fallar en local y en CI que descubrir después de publicar que a un documento le faltan campos.

### 4) Fijar el puerto y las variables de entorno de desarrollo para evitar el "en mi máquina funciona"

En el script raíz del monorepo, `scripts/static-sites-dev.mjs`, `impeccable` se orquesta explícitamente:

```js
{
  id: 'impeccable',
  name: 'Impeccable',
  repoPath: 'repos/impeccable-site',
  productionUrl: 'https://impeccable.hagicode.com/',
  command: 'npm',
  args: ['run', 'dev'],
  env: {
    PORT_IMPECCABLE_SITE: '36296'
  },
  portHint: 36296,
  order: 56
}
```

La prueba `scripts/static-sites-dev.test.mjs` también verifica estos valores (puerto, args, env, productionUrl).

Este enfoque de "valores fijos + pruebas" no es llamativo, pero es estable:

- La entrada local es unificada
- La ruta de diagnóstico es fija
- Los enlaces del sitio de documentación no se desvían

## Solución (Solution)

Si quieres usar `impeccable` para mejorar a la vez la **calidad de la interfaz** y la **estabilidad de la implementación**, según la práctica actual del repositorio se puede construir en cuatro capas.

### Primera capa: contratizar la entrada de tareas

Método: reutilizar una estructura de preset como la de `ui-master`.

Objetivos:

- Limitar los repositorios permitidos (`targetRepositories`)
- Limitar el origen de los comandos (`uiMasterCommandIds`)
- Limitar la entrada de contexto (`uiMasterDescription`)

Beneficio: cada asignación permite revisar después qué entrada hubo y por qué se hizo el cambio.

### Segunda capa: unificar la semántica de los comandos

Método: vincular los tres elementos: ID del comando, slug de la documentación y plantilla de prelude.

Objetivos:

- Los comandos seleccionados en el panel pueden saltar a la documentación con el mismo ID
- `/impeccable <command>` en el prompt y la explicación en la documentación coinciden

Beneficio: se reduce el riesgo oculto de "terminología consistente, comportamiento inconsistente".

### Tercera capa: convertir los activos de contenido en validaciones

Método: mantener `npm run validate` como puerta de calidad antes de cada commit.

Objetivos:

- No faltan claves de i18n
- El catálogo de comandos y la estructura upstream no se desvían
- Tipos, pruebas y build pasan de una vez

Beneficio: los problemas de contenido ocasionales se detectan en local.

### Cuarta capa: estandarizar el entorno de ejecución de desarrollo

Método: levantarlo de forma unificada con `static-sites-dev` y fijar `PORT_IMPECCABLE_SITE`.

Objetivos:

- Minimizar los conflictos de puertos en el trabajo colaborativo
- Fijar la ruta de depuración conjunta de varios sitios

Beneficio: se ahorra tiempo de configuración del entorno y los problemas se localizan antes en el código.

## Práctica (Practice)

### Paso 1: inicializar impeccable-site

```bash
cd /home/newbe36524/repos/hagicode-mono/repos/impeccable-site
git submodule update --init --recursive
env -u NPM_CONFIG_PREFIX npm install
```

### Paso 2: desarrollo local y validación completa

```bash
env -u NPM_CONFIG_PREFIX npm run dev
env -u NPM_CONFIG_PREFIX npm run validate
```

`validate` cubre de una vez i18n, catalog, typecheck, test y build.

### Paso 3: ejecutar mediante la orquestación unificada del monorepo

Desde el directorio raíz del monorepo, usa el sistema `scripts/static-sites-dev.mjs` y reutiliza el `PORT_IMPECCABLE_SITE=36296` ya definido.

En este paso, lo importante no es "que arranque", sino que "todos lo ejecuten de la misma manera".

### Paso 4: convertir las solicitudes de UI en entradas basadas en comandos

En el flujo de task preset, prioriza que los requisitos se concreten en:

- `uiMasterDescription`: objetivo de negocio
- `uiMasterCommandIds`: comandos de esta ronda (como `craft`, `audit`, `polish`)
- `sceneKey`: contexto del escenario

Solo después se pasa a la fase de cambios, lo que reduce la desviación de dirección causada por modificar la UI directamente.

### Paso 5: explicitar las carencias actuales de material

Según la instantánea actual del repositorio, lo que se puede confirmar es:

- El sitio de `impeccable-site` y su cadena de validación son código implementado.
- La integración profunda entre `ui-master` e `impeccable` aparece principalmente en `designs/task-preset-plugin-examples` y en los documentos de diseño.

Si quieres afirmar que "está habilitado en su totalidad en el backend de producción", la evidencia actual no es suficiente, así que no conviene llegar a esa conclusión todavía.

## Información sobre HagiCode

HagiCode es una plataforma que integra ingeniería multirepositorio, ejecución de tareas con IA, sitios de documentación y cadenas de herramientas. Su valor principal no es un único punto de "sabe generar código", sino que une restricciones de entrada de tareas, contexto de ejecución, puertas de validación y colaboración entre repositorios en una cadena estable. Entre los escenarios típicos están: iteración estructurada de UI, integración de funciones entre repositorios, producción de contenido técnico guiada por especificaciones y entrega automatizada con puertas de calidad.

## Resumen

El verdadero valor de `impeccable` no está en "ayudarte a imaginar un botón más bonito", sino en "convertir la optimización de la interfaz en ingeniería". En la práctica actual de HagiCode, esto se logra con cuatro acciones: contratizar las tareas, unificar la semántica de los comandos, adelantar la validación del contenido y estandarizar el entorno de ejecución. Primero hay que consolidar estas bases; solo después tiene sentido hablar de mejoras de diseño más vistosas, y el beneficio es mayor y más sostenible.
