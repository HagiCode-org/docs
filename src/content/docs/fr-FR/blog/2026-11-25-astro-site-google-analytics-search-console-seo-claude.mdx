Dans le [guide précédent](/fr-FR/blog/2026-11-23-mac-astro-site-claude-github-cloudflare/), vous êtes parti d'un Mac vierge et avez créé un site Astro déployé sur GitHub Pages et Cloudflare. La mise en ligne n'est qu'une moitié du travail : il faut encore savoir si des personnes visitent le site, ce qu'elles y font, et si Google parvient à le trouver.

Ce guide ajoute cette couche. Vous allez créer un compte Google Analytics et Google Search Console, puis demander à Claude de mettre en place le suivi, le plan du site, les balises sociales et le favicon. Chaque étape se termine par un résultat que vous pouvez vérifier avant de passer à la suivante.

Le déroulement complet :

1. Créer une propriété Google Analytics et copier son ID de mesure.
2. Demander à Claude d'intégrer Google Analytics, d'envoyer les modifications, d'attendre le déploiement et de prouver que le code est bien présent en ligne.
3. Vérifier dans Google Analytics que votre visite apparaît en temps réel.
4. Ajouter le site dans Google Search Console.
5. Relier Search Console à Google Analytics.
6. Demander à Claude de concevoir et d'ajouter un suivi d'événements adapté à votre site, puis de le publier et de le vérifier.
7. Demander à Claude d'ajouter la couche SEO de base : plan du site, `robots.txt`, lien canonique, Open Graph et balises Twitter.
8. Soumettre le plan du site dans Search Console.
9. Demander à Claude d'optimiser le titre, la description et les mots-clés de chaque page, puis de générer un favicon multi-tailles avec les outils en ligne de commande de votre Mac.

## Public visé

Ce guide s'adresse à celles et ceux qui ont suivi le guide précédent : vous avez un projet Astro dans un dépôt GitHub, chaque envoi sur `main` déclenche un déploiement automatique, et le site possède un domaine public. Vous n'avez pas besoin d'expérience avec les outils d'analyse, mais vous devez savoir coller de courtes consignes dans Claude Code et cliquer sur quelques pages Google.

## Prérequis

- Un site Astro déjà en ligne sur un domaine personnalisé, comme décrit dans le guide précédent. Ce guide appelle le dépôt `my-astro-site` et le domaine `example.com` : remplacez-les par les vôtres.
- Un compte Google.
- Claude Code installé et connecté, ainsi que `gh` connecté (`gh auth status`).
- Un accès à la configuration DNS du domaine. Si le domaine est géré par Cloudflare, vous y avez déjà accès.

## Étape 1 : créer la propriété Google Analytics et obtenir l'ID de mesure

Google Analytics 4 (GA4) est organisé ainsi : un compte contient une ou plusieurs propriétés, et une propriété contient des flux de données. Un site web correspond à un flux de données Web, et ce flux possède un ID de mesure qui commence par `G-`.

1. Ouvrez [analytics.google.com](https://analytics.google.com) et connectez-vous avec votre compte Google.
2. Cliquez sur **Commencer à mesurer** (si vous utilisez déjà Analytics, choisissez **Administration → Créer → Compte**). Donnez un nom au compte, par exemple `My sites`.
3. Créez la propriété. Nommez-la d'après votre site, choisissez le fuseau horaire et la devise pour les rapports, et répondez aux questions professionnelles demandées.
4. Lorsqu'on vous demande la plateforme, choisissez **Web**.
5. Saisissez l'adresse du site (`https://example.com`) et un nom de flux, puis laissez **Mesure améliorée** activée. Elle enregistre les pages vues, le défilement, les clics vers l'extérieur et les téléchargements de fichiers, sans aucun code.
6. Créez le flux. Google affiche alors les détails du flux, qui comprennent l'**ID de mesure**.

Copiez l'ID de mesure, qui ressemble à `G-ABCD123456`. Vous pourrez le retrouver plus tard dans **Administration → Collecte et modification des données → Flux de données → votre flux**.

L'ID de mesure n'est pas un secret. Il apparaît directement dans le code source de chaque page qui l'utilise. Vous pouvez donc le committer dans le dépôt sans crainte.

Vérification : vous avez un ID de mesure commençant par `G-`.

## Étape 2 : demander à Claude d'intégrer Google Analytics

Lancez Claude depuis le dossier du projet :

```bash
cd ~/Sites/my-astro-site
claude
```

Décrivez ensuite toute la tâche dans une seule demande, y compris l'envoi et la vérification. Plus l'état final est précis, moins vous aurez de corrections à faire ensuite.

```text
Merci d'intégrer Google Analytics 4 à ce site Astro. L'ID de mesure est G-ABCD123456.

Exigences :
- Placer le chargeur gtag.js et l'appel config dans le <head> de la mise en page partagée, pour qu'il y ait exactement un exemplaire par page.
- Utiliser un script inline ordinaire (is:inline) pour que window.gtag soit une vraie fonction globale. Astro regroupe les <script> ordinaires en modules, ce qui rendrait gtag inaccessible au code suivant.
- Ne rendre la balise que dans le build de production. Elle ne doit pas apparaître avec `npm run dev`.
- Lire l'ID de mesure depuis une constante ou une variable d'environnement, sans le dupliquer à plusieurs endroits.
- Lancer `npm run build` et vérifier que dist/index.html contient la balise.

Une fois le build réussi, committez avec un message clair et poussez sur main. Attendez ensuite la fin des deux déploiements : le workflow GitHub Pages et le build Cloudflare. Enfin, récupérez https://example.com/ avec curl et confirmez que le HTML en ligne contient l'ID de mesure. Indiquez précisément ce que vous avez vérifié.
```

Le fragment généré par Claude dans la mise en page devrait ressembler à ceci :

```astro
---
const GA_ID = 'G-ABCD123456';
const isProd = import.meta.env.PROD;
---
<head>
  {isProd && (
    <>
      <script is:inline async src={`https://www.googletagmanager.com/gtag/js?id=${GA_ID}`}></script>
      <script is:inline define:vars={{ GA_ID }}>
        window.dataLayer = window.dataLayer || [];
        window.gtag = function () { dataLayer.push(arguments); };
        gtag('js', new Date());
        gtag('config', GA_ID);
      </script>
    </>
  )}
</head>
```

Deux points méritent d'être compris, car ce sont les causes les plus fréquentes de « j'ai ajouté la balise mais rien ne se passe ».

- **`window.gtag` doit être une fonction globale.** Si le script est enfermé dans une closure, les pages vues peuvent fonctionner, mais `window.gtag` reste indéfini. Tous les événements personnalisés que vous ajouterez à l'étape 6 échoueront alors silencieusement. Affecter explicitement `window.gtag` évite ce problème.
- **N'activez la balise qu'en production.** Si elle tourne aussi sur `localhost`, vos propres clics pendant le développement fausseront les données.

Pendant l'attente du déploiement, Claude utilisera des commandes de ce type :

```bash
gh run watch
curl -s https://example.com/ | grep -o 'googletagmanager.com/gtag/js?id=G-[A-Z0-9]*'
```

`gh run watch` suit l'exécution GitHub Actions jusqu'à sa fin. La commande `curl` n'affiche quelque chose que si la page en ligne contient bien l'adresse du chargeur.

Vérification : le rapport de Claude indique que les deux plateformes ont bien déployé, et l'ID de mesure figure dans le HTML en ligne. Si `curl` n'affiche rien, le déploiement n'est peut-être pas terminé, ou le cache sert encore une ancienne page. Demandez à Claude de réessayer une minute plus tard, et si l'ancienne page persiste, purgez le cache Cloudflare.

## Étape 3 : vérifier dans Google Analytics que le site est en ligne

Vérifions maintenant côté Google, et pas seulement côté navigateur.

1. Ouvrez `https://example.com` dans votre navigateur. Si vous utilisez un bloqueur de publicités ou un navigateur axé sur la vie privée, désactivez-le pour ce test, car il bloque Google Analytics.
2. Dans Google Analytics, ouvrez **Rapports → Temps réel**.
3. Dans la minute qui suit, vous devriez voir **1 utilisateur au cours des 30 dernières minutes**, avec l'événement `page_view` dans la liste des événements.
4. Ouvrez deux ou trois pages. Leurs titres apparaîtront dans la vue en temps réel.

Vous pouvez aussi ouvrir **Administration → Flux de données → votre flux**. Une coche verte indiquant que les données arrivent confirme que le flux reçoit du trafic.

Vérification : votre propre visite apparaît dans **Temps réel**. Les rapports standard, comme **Acquisition**, prennent quelques heures à un jour pour se remplir. Ne vous inquiétez pas s'ils sont encore vides.

## Étape 4 : ajouter le site dans Google Search Console

Google Analytics vous indique ce que font les visiteurs une fois arrivés. Google Search Console vous indique comment Google perçoit votre site : quelles requêtes amènent des visiteurs, quelles pages sont indexées et quelles erreurs Google a repérées.

1. Ouvrez [search.google.com/search-console](https://search.google.com/search-console) et connectez-vous avec le même compte Google que pour Analytics. Utiliser le même compte facilitera la liaison à l'étape 5.
2. Cliquez sur **Ajouter une propriété**. Deux types sont proposés.
   - **Domaine** couvre `example.com`, tous ses sous-domaines et tous les protocoles. Il nécessite un enregistrement DNS.
   - **Préfixe d'URL** ne couvre qu'une adresse exacte, par exemple `https://example.com/`, et propose plusieurs méthodes de vérification.
3. Si votre DNS est géré par Cloudflare, choisissez **Domaine** et saisissez `example.com`.
4. Search Console affiche un enregistrement `TXT`. Copiez sa valeur, qui commence par `google-site-verification=`.
5. Dans le tableau de bord Cloudflare, ouvrez votre domaine et allez dans **DNS → Enregistrements → Ajouter un enregistrement**. Choisissez le type `TXT`, indiquez `@` comme nom, collez la valeur dans le contenu, puis enregistrez.
6. Revenez dans Search Console et cliquez sur **Vérifier**. Les modifications DNS prennent généralement quelques minutes, mais parfois plus longtemps. Si la vérification échoue, attendez un peu puis cliquez à nouveau sur **Vérifier**.

Si vous avez choisi **Préfixe d'URL**, le plus simple est de vérifier via Google Analytics : tant que vous utilisez le même compte Google, Search Console peut utiliser la balise installée à l'étape 2 comme preuve de propriété.

Vérification : Search Console affiche « Propriété vérifiée » et ouvre la page de présentation de la propriété. Il est normal qu'elle affiche « Aucune donnée » pendant un certain temps.

## Étape 5 : relier Search Console à Google Analytics

Une fois la liaison établie, les performances des requêtes et des pages de destination apparaissent dans les rapports Analytics. Vous pouvez alors comparer le trafic issu de la recherche avec le comportement de ces visiteurs.

1. Dans Google Analytics, ouvrez **Administration**.
2. Sous **Liens vers des produits**, choisissez **Liens Search Console**.
3. Cliquez sur **Lier**, puis sur **Choisir des comptes** et sélectionnez votre propriété Search Console. Vous devez être propriétaire de cette propriété Search Console et éditeur de la propriété Analytics.
4. Cliquez sur **Suivant**, sélectionnez le flux de données Web, puis cliquez sur **Envoyer**.

Les données de Search Console mettent quelques jours à arriver, avec un décalage d'environ deux jours. Il n'y a rien à attendre ici : passez directement à l'étape suivante.

Une fois la liaison créée, les rapports correspondants se trouvent dans **Rapports → Bibliothèque**. Les rapports Search Console n'apparaissent pas automatiquement dans le menu de gauche. Pour les y faire figurer, publiez la collection **Search Console** depuis la bibliothèque.

Vérification : **Administration → Liens vers des produits → Liens Search Console** affiche votre propriété.

## Étape 6 : ajouter un suivi d'événements adapté à votre site

La mesure améliorée enregistre déjà les pages vues, le défilement, les clics sur les liens sortants, la recherche sur le site et les téléchargements de fichiers. Ne les réimplémentez pas. Les événements servent aux actions propres à votre activité : clic sur l'appel à l'action principal, inscription à une lettre d'information, formulaire de contact, consultation de la page tarifs.

La consigne la plus utile n'est pas « ajoute quelques événements », mais « examine mon site, propose un plan d'événements, et attends mon accord ». Vous gardez ainsi la maîtrise de ce que vous mesurez.

```text
Merci d'examiner la structure de ce site Astro : pages, mises en page, composants, appels à l'action, formulaires et liens sortants.

Étape 1 : avant de modifier le moindre code, proposez un plan d'événements. Présentez un tableau avec : le nom de l'événement, le moment du déclenchement, les paramètres et la question métier auquel il répond. Privilégiez les noms d'événements recommandés par GA4 lorsqu'ils existent (par exemple generate_lead, sign_up, select_content), sinon utilisez des noms personnalisés en snake_case. Ne dupliquez pas ce que la mesure améliorée suit déjà : pages vues, défilement, clics sortants, téléchargements de fichiers. Maximum 10 événements.

Étape 2 : une fois mon accord donné, implémentez le plan :
- Marquez les éléments avec les attributs data-ga-event, data-ga-label et data-ga-location.
- Utilisez un écouteur de clic délégué sur document qui lit ces attributs et appelle gtag('event', ...). N'ajoutez aucun gestionnaire onclick en ligne.
- Dans les paramètres, n'envoyez que des identifiants stables et des emplacements. N'envoyez jamais le texte des liens, les saisies de formulaire, les adresses e-mail ni rien qui permette d'identifier un visiteur.
- Ne retardez ni n'annulez jamais la navigation.

Étape 3 : lancez le build, committez, poussez, attendez la fin des deux déploiements, puis vérifiez avec curl que le site en ligne contient le script d'écoute. Indiquez-moi ensuite sur quels éléments cliquer pour vérifier dans GA4 DebugView.
```

Claude vous répondra d'abord par un tableau. Voici à quoi peut ressembler un plan raisonnable pour un petit site :

| Événement | Déclencheur | Paramètres | Question à laquelle il répond |
| --- | --- | --- | --- |
| `cta_click` | Le visiteur clique sur le bouton d'appel à l'action principal | `label`, `location` | Quels boutons, dans quelles zones des pages, incitent à l'action ? |
| `generate_lead` | Envoi réussi du formulaire de contact | `form_id` | Combien de visiteurs deviennent des contacts ? |
| `nav_click` | Clic sur un lien d'en-tête ou de pied de page | `label`, `location` | Quels éléments de navigation sont utilisés ? |
| `theme_toggle` | Utilisation du sélecteur de thème | `value` | Le bouton de mode sombre mérite-t-il d'être conservé ? |

Lisez ce tableau avec un regard critique. Supprimez les événements que personne ne consultera, et renommez ceux qui décrivent une fonctionnalité plutôt qu'une décision. Répondez ensuite « d'accord, mais supprime `theme_toggle` » pour lancer l'implémentation.

L'écouteur écrit par Claude ressemble à peu près à ceci :

```js
document.addEventListener(
  'click',
  (event) => {
    const el = event.target.closest('[data-ga-event]');
    if (!el || typeof window.gtag !== 'function') return;
    window.gtag('event', el.dataset.gaEvent, {
      label: el.dataset.gaLabel,
      location: el.dataset.gaLocation,
      transport_type: 'beacon',
    });
  },
  true,
);
```

L'élément marqué :

```astro
<a href="/contact" data-ga-event="cta_click" data-ga-label="hero_contact" data-ga-location="home_hero">
  Nous contacter
</a>
```

### Vérifier les événements

1. Dans Google Analytics, ouvrez **Administration → Affichage des données → DebugView**. DebugView affiche les événements reçus en quelques secondes.
2. Pour passer le navigateur en mode débogage, installez l'extension Chrome **Google Analytics Debugger**, ou demandez à Claude d'ajouter temporairement `debug_mode: true` à l'appel `config`.
3. Ouvrez le site en ligne et effectuez les clics indiqués par Claude.
4. Chaque clic doit apparaître comme un événement dans la chronologie de DebugView, avec les paramètres attendus.

Une fois qu'un événement a été reçu une fois, il apparaît aussi dans **Administration → Affichage des données → Événements**. Si vous voulez utiliser `label` ou `location` dans les rapports standard, enregistrez-les dans **Administration → Affichage des données → Définitions personnalisées → Créer une dimension personnalisée** avec la portée **Événement**. Seuls les paramètres ainsi enregistrés apparaissent dans les rapports standard.

Supprimez tous les réglages `debug_mode` temporaires, puis demandez à Claude de pousser une version propre.

Vérification : chaque clic suivi apparaît dans DebugView avec le bon nom d'événement et les bons paramètres, et le code final est sur `main`.

## Étape 7 : ajouter la couche SEO de base

Les moteurs de recherche ont besoin d'un plan du site, d'indications sur ce qui peut être exploré, et de descriptions affichées lorsque les pages sont partagées. Le premier élément dispose d'une intégration officielle pour Astro, les autres ne demandent que quelques lignes dans la mise en page. Claude peut ajouter les composants et intégrations Astro concernés rapidement.

```text
Merci d'ajouter les bases du SEO à ce site Astro.

1. Plan du site : installez l'intégration officielle @astrojs/sitemap avec `npx astro add sitemap`. Assurez-vous que `site` dans astro.config.mjs vaut le domaine de production https://example.com, et supprimez l'ancienne option `base` héritée de l'hébergement de projet GitHub Pages.
2. robots.txt : créez src/pages/robots.txt.ts, qui renvoie "User-agent: *", "Allow: /" et une ligne Sitemap pointant vers https://example.com/sitemap-index.xml. Cette adresse doit être générée à partir de la configuration `site`, et non écrite en dur.
3. Un composant SEO réutilisable pour la mise en page partagée, qui produit : <title> ; la meta description ; le lien canonique généré à partir de l'URL courante et de `site` ; les balises Open Graph (og:type, og:title, og:description, og:url, og:image, og:site_name, og:locale) ; les balises de carte Twitter (twitter:card summary_large_image, twitter:title, twitter:description, twitter:image) ; et la meta theme-color. Chaque page transmet son propre titre et sa description par des props.
4. Fournissez une image de partage par défaut de 1200x630 dans public/og-default.png, utilisée lorsqu'une page n'en fournit pas.
5. Ajoutez des données structurées JSON-LD de type WebSite pour le site, et de type Article pour les articles si le site possède un blog.
6. Lancez `npm run build`, puis listez dist/sitemap-index.xml, affichez dist/robots.txt, et confirmez que le HTML généré pour la page d'accueil contient toutes les balises ci-dessus.

Une fois tout correct, committez, poussez, attendez la fin des deux déploiements, puis vérifiez avec curl que https://example.com/sitemap-index.xml et https://example.com/robots.txt renvoient 200 avec le bon contenu.
```

Le rôle de chaque élément :

- **Plan du site.** `@astrojs/sitemap` génère `sitemap-index.xml` et un ou plusieurs fichiers `sitemap-0.xml` pendant le build. Il a besoin de la configuration `site` pour produire des URL absolues.
- **`robots.txt`.** Il indique aux robots ce qu'ils peuvent explorer et où se trouve le plan du site. Pour empêcher l'indexation d'une page, utilisez `noindex` ; `robots.txt` seul ne suffit pas.
- **Lien canonique.** Lorsqu'une même page est accessible par plusieurs adresses, il indique à Google laquelle est la version officielle.
- **Balises Open Graph et Twitter.** Elles déterminent le titre, la description et l'image affichés lorsqu'un lien est partagé sur un réseau social ou dans une application de messagerie.
- **JSON-LD.** Les données structurées aident les moteurs de recherche à comprendre ce qu'est la page. Elles ne garantissent pas l'affichage de résultats enrichis, mais leur coût d'ajout est faible.

Vérification : le `sitemap-index.xml` en ligne liste vos pages, `robots.txt` contient une ligne `Sitemap:`, et le code source des pages montre les balises canonical, Open Graph et Twitter. Vous pouvez aussi coller l'URL dans un outil de validation de cartes sociales, ou la partager dans une application de messagerie pour voir l'aperçu.

## Étape 8 : soumettre le plan du site dans Search Console

Tant que vous ne l'avez pas indiqué à Search Console, elle ignore l'existence de votre plan du site.

1. Dans Search Console, ouvrez votre propriété et choisissez **Sitemaps** dans le menu de gauche.
2. Sous **Ajouter un sitemap**, saisissez `sitemap-index.xml`.
3. Cliquez sur **Envoyer**.
4. Le statut doit passer à **Réussi** et afficher le nombre de pages découvertes. S'il affiche **Impossible de récupérer**, ouvrez d'abord l'adresse du plan du site dans votre navigateur. Si elle s'ouvre, patientez quelques minutes puis actualisez, car la première récupération peut être retardée.

Ensuite, demandez à Google d'examiner tout de suite vos pages les plus importantes :

1. Collez l'URL de la page d'accueil dans la barre de recherche en haut de Search Console.
2. Si la page n'est pas encore indexée, cliquez sur **Demander l'indexation**.

L'indexation prend encore quelques jours, et les rapports de Search Console ont aussi du retard. Revenez les consulter dans une semaine.

Vérification : **Sitemaps** affiche `sitemap-index.xml` avec le statut **Réussi**.

## Étape 9 : optimiser les métadonnées de chaque page et ajouter un favicon multi-tailles

La couche de base donne à chaque page des métadonnées génériques. Le titre et la description sont les textes que les personnes lisent dans les résultats de recherche : ils méritent d'être travaillés page par page. Le favicon doit exister en plusieurs tailles, car les navigateurs, les téléphones et les favoris demandent chacun des fichiers différents.

### Titres, descriptions et mots-clés

```text
Merci d'examiner chaque page de ce site et d'optimiser ses métadonnées de recherche.

Pour chaque page, présentez-moi un tableau avant/après avec le titre, la meta description et les mots-clés, puis appliquez les modifications. Règles :
- Titre : unique pour chaque page, pas plus d'environ 60 caractères, sujet principal en premier, nom du site ensuite.
- Description : unique pour chaque page, entre 120 et 160 caractères, une phrase claire qui explique ce que le visiteur va trouver et l'invite à cliquer. Pas de bourrage de mots-clés, et pas de texte copié d'une page à l'autre.
- Mots-clés : 5 à 8 termes extraits du contenu réel de la page. Ne conservez la balise meta keywords que si la mise en page la prend déjà en charge, et n'inventez aucun sujet absent de la page.
- Vérifiez que chaque page contient exactement un <h1> cohérent avec le titre, et que chaque image possède un attribut alt.

Lancez ensuite le build et rédigez un court rapport listant les pages qui partagent encore un titre ou une description identiques.
```

Gardez les attentes réalistes : les moteurs de recherche ignorent en grande partie la balise meta keywords. Les mots-clés vous aident quand même, car les écrire vous oblige à préciser le sujet de chaque page. Ce qui apparaît réellement dans les résultats de recherche, ce sont le titre et la description.

### Favicons en plusieurs tailles

Un fichier `favicon.svg` est un bon point de départ, mais certains emplacements exigent des fichiers précis : les anciens navigateurs et les favoris utilisent `favicon.ico`, l'écran d'accueil d'iOS utilise `apple-touch-icon`, et Android ainsi que le manifeste des applications web utilisent des PNG de 192 et 512 pixels.

macOS inclut `sips` pour redimensionner les PNG. Pour générer un `.ico`, il faut ImageMagick, installable avec Homebrew. Demandez à Claude de les utiliser directement sur votre Mac :

```text
Merci de générer un jeu complet de favicons à partir de mon image source public/logo-source.png (PNG carré d'au moins 512x512).

1. Utilisez la commande `sips` de macOS pour créer public/icon-192.png, public/icon-512.png et public/apple-touch-icon.png (180x180).
2. Si ImageMagick n'est pas installé, installez-le avec `brew install imagemagick`. Avec `magick`, générez public/favicon.ico contenant des images de 16x16, 32x32 et 48x48.
3. Si public/favicon.svg existe déjà, conservez-le ; sinon créez une version simple adaptée au logo.
4. Ajoutez public/site.webmanifest, qui référence icon-192.png et icon-512.png.
5. Mettez à jour le <head> de la mise en page avec les balises <link> correspondantes : icône SVG, repli .ico, apple-touch-icon et manifeste.
6. Exécutez `file` sur chaque image générée pour vérifier les dimensions réelles, lancez le build, et assurez-vous que ces fichiers sont présents dans dist/.
```

Commandes que Claude exécutera, à peu près :

```bash
sips -z 192 192 public/logo-source.png --out public/icon-192.png
sips -z 512 512 public/logo-source.png --out public/icon-512.png
sips -z 180 180 public/logo-source.png --out public/apple-touch-icon.png
brew install imagemagick
magick public/logo-source.png -define icon:auto-resize=48,32,16 public/favicon.ico
file public/*.png public/favicon.ico
```

Les liens dans le head :

```html
<link rel="icon" href="/favicon.svg" type="image/svg+xml" />
<link rel="icon" href="/favicon.ico" sizes="48x48" />
```

## À vérifier une semaine plus tard

- **Search Console → Pages** indique combien de pages sont indexées et pourquoi certaines ne le sont pas.
- **Search Console → Performances** affiche les requêtes, les clics et la position moyenne. Utilisez ces requêtes pour améliorer les titres et les descriptions.
- **Analytics → Rapports → Engagement → Événements** indique la fréquence de vos événements personnalisés.
- **Analytics → Rapports → Bibliothèque** est l'endroit où apparaît la collection Search Console une fois les données arrivées.

## Dépannage

- **Le rapport Temps réel est vide.** Un bloqueur de publicités ou un navigateur axé sur la vie privée bloque la balise. Testez dans une fenêtre privée avec les extensions désactivées, et vérifiez l'ID de mesure dans le HTML en ligne.
- **Les pages vues fonctionnent, mais les événements personnalisés non.** Dans la console du navigateur sur le site en ligne, exécutez `typeof window.gtag`. Il doit afficher `function`. Si le résultat est `undefined`, le script de la balise a été regroupé en module : demandez à Claude d'utiliser `is:inline` et d'affecter explicitement `window.gtag`.
- **Les événements apparaissent dans DebugView, mais pas dans les rapports.** Les rapports standard ont jusqu'à un jour de retard, et les paramètres personnalisés n'apparaissent qu'une fois enregistrés comme dimensions personnalisées.
- **Search Console ne parvient pas à vérifier le domaine.** Vérifiez que l'enregistrement `TXT` est bien sur le domaine racine (`@`), que la valeur a été copiée intégralement, et qu'il n'est pas passé par le proxy Cloudflare (les enregistrements TXT ne sont pas proxifiés). Attendez ensuite un peu avant de réessayer.
- **Le plan du site affiche « Impossible de récupérer ».** Ouvrez `https://example.com/sitemap-index.xml` vous-même. Si la page renvoie une 404, vérifiez que `site` dans `astro.config.mjs` est bien le domaine de production et que l'intégration du plan du site figure dans `integrations`.
- **L'aperçu social est ancien.** Les plateformes mettent en cache les aperçus. Après avoir modifié les balises, utilisez leurs outils de débogage pour actualiser le cache.

## Vie privée et consentement

L'analyse collecte des données sur les visiteurs. Selon leur région, vous devrez peut-être obtenir leur consentement avant de charger Google Analytics, par exemple au titre du RGPD et de la directive ePrivacy dans l'Union européenne, et l'indiquer dans votre politique de confidentialité. Pour garder ce guide simple, la balise est installée sans condition. Si votre site reçoit des visiteurs de régions qui exigent un consentement, demandez à Claude d'ajouter une bannière de consentement qui ne charge la balise qu'après acceptation. Ces informations sont générales et ne constituent pas un avis juridique.

## La boucle à garder

Chaque étape de ce guide suit le même schéma, et c'est une habitude qui vaut la peine d'être gardée : décrivez à Claude l'état final souhaité, laissez-le effectuer les modifications, faites-le pousser et attendre le déploiement, faites-lui prouver le résultat sur le site en ligne avec `curl`, puis confirmez avec un outil externe comme Google Analytics ou Search Console. Répétez ce même cycle chaque fois que vous ajouterez une fonctionnalité.
