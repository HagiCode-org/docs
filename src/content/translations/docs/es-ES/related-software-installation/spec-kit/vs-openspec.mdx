Spec Kit y OpenSpec son herramientas de código abierto con licencia MIT que atacan el mismo problema: cuando los requisitos solo viven en el historial del chat, el resultado de un asistente de programación con IA es difícil de predecir, así que se escribe la especificación y se deja que la persona y la IA se pongan de acuerdo antes de escribir código. Se diferencian en el peso del proceso, en cómo se organizan las especificaciones y en la cadena de herramientas.

:::note[Primero, nuestra postura]
El flujo de trabajo del propio HagiCode está construido sobre OpenSpec, así que tenemos una preferencia. Los hechos que siguen proceden de la documentación oficial de ambos proyectos, comprobada el 26-10-2026, y lo que es opinión nuestra está indicado como tal. Ambos proyectos evolucionan rápido, así que lee la documentación más reciente de cada uno antes de elegir.
:::

## Qué se compara

- **Spec Kit**: de GitHub. La línea de comandos es `specify` (el paquete de Python `specify-cli`); la instalación y el uso están en [Instalar Spec Kit](/es-ES/related-software-installation/spec-kit/installation).
- **OpenSpec**: de Fission AI. La línea de comandos es `openspec` (el paquete de npm `@fission-ai/openspec`); consulta la [Introducción a OpenSpec](/es-ES/related-software-installation/openspec/intro-openspec).

## Diferencias principales

| Dimensión | Spec Kit | OpenSpec |
| --- | --- | --- |
| Entorno de ejecución | Python 3.11+, se instala con uv o pipx | Node.js 20.19.0+, se instala con npm o Homebrew |
| Comando de instalación | `uv tool install specify-cli` | `npm install -g @fission-ai/openspec@latest` |
| Inicialización | `specify init my-project --integration claude` | `openspec init` dentro del proyecto |
| Prefijo de comandos | `/speckit-*` | `/opsx:*` (`/opsx-*` en algunos asistentes, `$openspec-*` en Codex) |
| Flujo principal | constitution → specify → clarify → plan → checklist → tasks → analyze → implement → converge; el camino más corto es specify → plan → tasks → implement → converge | El perfil por defecto tiene propose, explore, apply, update, sync y archive; el perfil ampliado añade new, continue, ff, verify y más |
| Artefactos por funcionalidad | `spec.md`, `plan.md`, `tasks.md`, además de listas de comprobación y resultados de análisis | Una carpeta de cambio con `proposal.md`, `specs/`, `design.md` y `tasks.md` |
| Cómo se organizan las especificaciones | Una especificación completa escrita en torno a una sola funcionalidad | Basado en especificaciones delta: `ADDED` y `MODIFIED` describen el cambio y se fusionan en las especificaciones de larga duración al archivar |
| Extensibilidad | Extensiones y presets; entre las oficiales hay bug y assess | Esquemas propios y esquemas de la comunidad |
| Varios repositorios | No encontramos soporte específico entre repositorios en el flujo principal de la documentación oficial | Stores (beta) guardan la planificación en un repositorio propio y la comparten con varios repositorios de código |
| Asistentes compatibles | La documentación oficial enumera decenas de integraciones | La documentación oficial habla de más de 30 herramientas |
| Licencia | MIT | MIT |

## Peso del proceso: la diferencia que más se menciona

El README de OpenSpec resume Spec Kit como minucioso pero pesado, con puertas de fase rígidas, mucho Markdown y una configuración de Python, y se presenta a sí mismo como más ligero, porque permite revisar cualquier artefacto en cualquier momento. Esa es la descripción del propio OpenSpec.

Para ser justos: el inicio rápido de Spec Kit ofrece por sí mismo un camino corto de cinco pasos en el que constitution, clarify, checklist y analyze son opcionales, y el perfil ampliado de OpenSpec también tiene muchos comandos. La diferencia real no está en el número de comandos, sino en la postura por defecto. Spec Kit se parece más a una cadena que va de la especificación a la implementación y converge al final, mientras que OpenSpec subraya que cada cambio es una carpeta independiente que puedes editar en cualquier momento.

## Elegir según el escenario

Los consejos siguientes son un juicio nuestro, no una conclusión oficial de ninguno de los dos proyectos.

| Tu situación | Mejor opción | Por qué |
| --- | --- | --- |
| Un proyecto nuevo y quieres un flujo completo desde la especificación hasta la implementación | Spec Kit | Un flujo completo, una constitution que limita todo el proyecto y `converge` para cerrar el ciclo frente a la especificación |
| Mucho código existente y cambios pequeños cada vez | OpenSpec | Las especificaciones delta describen solo lo que cambia, sin tener que reescribir una especificación completa de las funciones existentes |
| Un equipo sobre todo de Python y acostumbrado a uv | Spec Kit | El método de instalación encaja con la pila |
| Un equipo sobre todo de Node.js | OpenSpec | Se instala con un solo comando de npm |
| Una funcionalidad toca varios repositorios | OpenSpec | Stores pueden guardar el plan en un repositorio compartido; ten en cuenta que aún es beta |
| Quieres muchas extensiones ya hechas (corrección de errores, evaluación de ideas) | Spec Kit | El sitio oficial enumera más extensiones y presets |
| Los requisitos cambian a menudo y quieres editar especificaciones y planes en cualquier momento | OpenSpec | Los artefactos no tienen fases estrictas, así que puedes volver atrás y editar |

## Guía para decidir

1. **Mira primero tu pila y tus costumbres, y después las funciones.** Los dos se solapan mucho en capacidades, y la fricción de un entorno que no encaja suele pesar más.
2. **Pasa ambos por la misma funcionalidad pequeña.** Elige un requisito de media jornada y recorre el flujo completo con cada uno. Es más fiable que leer diez artículos comparativos.
3. **No instales los dos en un mismo proyecto.** Ambas herramientas generan comandos y directorios en el proyecto, y mezclarlas desordena la lista de comandos de tu asistente.
4. **Evalúa tres cosas:** si escribir la especificación redujo de verdad el trabajo repetido, si tu asistente de IA tiene soporte oficial y si el equipo está dispuesto a mantener estos archivos Markdown.

## Camino recomendado

- **Para probar uno rápido:** elige el que case con tu pila, instálalo y recorre solo el camino más corto en una funcionalidad pequeña.
- **Para comparar en serio:** sigue el punto 2 de arriba con los dos y decide por «cantidad de trabajo repetido» y «aceptación del equipo».
- **Para profundizar:** lee [Instalar Spec Kit](/es-ES/related-software-installation/spec-kit/installation) y la [Introducción a OpenSpec](/es-ES/related-software-installation/openspec/intro-openspec).
