Spec Kit и OpenSpec — открытые инструменты с лицензией MIT, которые решают одну проблему: когда требования существуют только в истории чата, результат работы ИИ-ассистента трудно предсказать, поэтому спецификацию записывают, а человек и ИИ договариваются до написания кода. Отличаются они тяжестью процесса, способом организации спецификаций и набором инструментов.

:::note[Сначала о нашей позиции]
Рабочий процесс самого HagiCode построен на OpenSpec, так что у нас есть предпочтение. Факты ниже взяты из официальной документации обоих проектов и проверены 2026-10-26; наши собственные оценки помечены как таковые. Оба проекта быстро развиваются, поэтому перед выбором прочитайте актуальную документацию каждого.
:::

## Что сравнивается

- **Spec Kit** — от GitHub. Командная строка `specify` (пакет Python `specify-cli`); установка и использование описаны в [Установка Spec Kit](/ru-RU/related-software-installation/spec-kit/installation).
- **OpenSpec** — от Fission AI. Командная строка `openspec` (пакет npm `@fission-ai/openspec`); подробности в [Введение в OpenSpec](/ru-RU/related-software-installation/openspec/intro-openspec).

## Ключевые различия

| Параметр | Spec Kit | OpenSpec |
| --- | --- | --- |
| Среда выполнения | Python 3.11+, установка через uv или pipx | Node.js 20.19.0+, установка через npm или Homebrew |
| Команда установки | `uv tool install specify-cli` | `npm install -g @fission-ai/openspec@latest` |
| Инициализация | `specify init my-project --integration claude` | `openspec init` в каталоге проекта |
| Префикс команд | `/speckit-*` | `/opsx:*` (в некоторых ассистентах `/opsx-*`, в Codex `$openspec-*`) |
| Основной процесс | constitution → specify → clarify → plan → checklist → tasks → analyze → implement → converge; короткий путь: specify → plan → tasks → implement → converge | В профиле по умолчанию: propose, explore, apply, update, sync, archive; расширенный профиль добавляет new, continue, ff, verify и другие |
| Артефакты на функцию | `spec.md`, `plan.md`, `tasks.md`, а также чек-листы и результаты анализа | Один каталог изменения с `proposal.md`, `specs/`, `design.md` и `tasks.md` |
| Организация спецификаций | Полная спецификация, написанная вокруг одной функции | Основа — дельта-спецификации: `ADDED` и `MODIFIED` описывают изменение и при архивации вливаются в долгоживущие спецификации |
| Расширяемость | Расширения и пресеты; среди официальных есть bug и assess | Собственные схемы и схемы сообщества |
| Несколько репозиториев | В основном процессе официальной документации мы не нашли отдельной поддержки нескольких репозиториев | Stores (бета) хранят планирование в отдельном репозитории и делятся им между репозиториями кода |
| Поддерживаемые ассистенты | В официальной документации перечислены десятки интеграций | В официальной документации указано более 30 инструментов |
| Лицензия | MIT | MIT |

## Тяжесть процесса: различие, о котором говорят чаще всего

В README OpenSpec Spec Kit описан как основательный, но тяжёлый: жёсткие этапы с барьерами, много Markdown и необходимость настраивать Python. Сам OpenSpec позиционируется как более лёгкий, позволяющий менять любой артефакт в любой момент. Это описание от самого OpenSpec.

Для справедливости: в быстром старте Spec Kit есть пятишаговый короткий путь, где constitution, clarify, checklist и analyze необязательны, а в расширенном профиле OpenSpec тоже немало команд. Настоящая разница не в количестве команд, а в позиции по умолчанию. Spec Kit больше похож на конвейер от спецификации до реализации с завершающей сверкой, а OpenSpec подчёркивает, что каждое изменение — отдельный каталог, который можно править в любой момент.

## Выбор по сценарию

Рекомендации ниже — наша оценка, а не официальный вывод какого-либо из проектов.

| Ваша ситуация | Что подходит лучше | Почему |
| --- | --- | --- |
| Новый проект и нужен полный путь от спецификации до реализации | Spec Kit | Полный процесс, constitution задаёт ограничения для всего проекта, а `converge` замыкает цикл сверкой со спецификацией |
| Много существующего кода, каждый раз меняется небольшая часть | OpenSpec | Дельта-спецификации описывают только изменения, не нужно переписывать полную спецификацию для существующих функций |
| Команда в основном на Python и привыкла к uv | Spec Kit | Способ установки совпадает со стеком |
| Команда в основном на Node.js | OpenSpec | Устанавливается одной командой npm |
| Одна функция затрагивает несколько репозиториев | OpenSpec | Stores позволяют держать план в общем репозитории; учтите, что это пока бета |
| Нужно много готовых расширений (исправление ошибок, оценка идей) | Spec Kit | На официальном сайте больше расширений и пресетов |
| Требования часто меняются, и вы хотите в любой момент править спецификации и планы | OpenSpec | У артефактов нет жёстких этапов, к ним можно вернуться и отредактировать |

## Рекомендации по выбору

1. **Сначала смотрите на стек и привычки, потом на функции.** По возможностям инструменты во многом пересекаются, а трение от несоответствия среды обычно важнее.
2. **Прогоните оба на одной небольшой функции.** Возьмите задачу на полдня и пройдите с каждым полный процесс. Это надёжнее, чем читать десять статей-сравнений.
3. **Не ставьте оба в один проект.** Оба инструмента создают в проекте команды и каталоги, и смешивание засоряет список команд вашего ассистента.
4. **Оценивайте по трём пунктам:** действительно ли написанная спецификация уменьшила переделки, поддерживается ли ваш ИИ-ассистент официально и готова ли команда сопровождать эти Markdown-файлы.

## Как это делает HagiCode

Мы давно используем OpenSpec и построили вокруг него управление спецификациями в нескольких репозиториях и выбор разных agents по этапам. Об этом рассказано в двух статьях: [Оптимизация эффективности каждого этапа OpenSpec с помощью разных agents: практическое резюме HagiCode](/ru-RU/blog/2026-05-08-optimizing-openspec-with-different-agents) и [MonoSpecs: что это и почему это является дальнейшим обновлением и расширением OpenSpec](/ru-RU/blog/2026-06-20-monospecs-openspec-upgrade-and-extension). Это наш выбор, и он не обязательно лучше для каждой команды. Если Spec Kit подходит вашей команде больше, он так же работает с поддерживаемыми в HagiCode Agent CLI, например Claude Code и Codex; подготовка описана в [Установка AI Agent CLI](/ru-RU/related-software-installation/ai-agent-cli/).

## Рекомендуемый путь

- **Чтобы быстро попробовать:** выберите инструмент, подходящий вашему стеку, установите его и пройдите только короткий путь на небольшой функции.
- **Чтобы сравнить всерьёз:** выполните пункт 2 выше с обоими, затем решайте по объёму переделок и принятию командой.
- **Чтобы разобраться глубже:** прочитайте [Установка Spec Kit](/ru-RU/related-software-installation/spec-kit/installation) и [Введение в OpenSpec](/ru-RU/related-software-installation/openspec/intro-openspec).
