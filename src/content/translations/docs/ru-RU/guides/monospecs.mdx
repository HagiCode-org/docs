## Обзор

MonoSpecs — решение HagiCode для управления несколькими репозиториями: оно отслеживает и объединяет несколько субрепозиториев через файл `.hagicode/monospecs.yaml`. Его можно использовать в любом проекте, где нужно централизованно управлять несколькими независимыми репозиториями.

> **Напоминание о миграции**: файл `monospecs.yaml` перенесён из корневого каталога проекта в `.hagicode/monospecs.yaml`. Файл `monospecs.yaml` в корневом каталоге больше не обнаруживается и не поддерживается как запасной вариант; в существующих проектах нужно вручную создать каталог `.hagicode/` и переместить файл.

> 💡 **Быстрый старт**: чтобы увидеть полную структуру проекта MonoSpecs, включая файл конфигурации, скрипт получения репозиториев и документацию README, откройте репозиторий [monospecs-demo](https://github.com/HagiCode-org/monospecs-demo).

### Основные понятия

**Файл конфигурации**

`.hagicode/monospecs.yaml` — основа всего решения. В этом файле определяются:

- список и расположение субрепозиториев
- Git URL каждого репозитория
- отображаемое имя и значок
- поведение интеграции с OpenSpec

**Отличия от использования OpenSpec в обычном репозитории**

И проекты под управлением MonoSpecs, и обычные одиночные репозитории могут использовать процесс OpenSpec из HagiCode для управления изменениями. Различия между ними такие:

| Особенность | Обычный репозиторий | Проект под управлением MonoSpecs |
|------|---------|---------------------|
| **Расположение OpenSpec** | `openspec/` в корне репозитория | `openspec/` в корне основного репозитория |
| **Область изменений** | Только текущий репозиторий | Может затрагивать несколько субрепозиториев |
| **Чистота субрепозитория** | Спецификации смешаны с кодом | Спецификации хранятся отдельно в основном репозитории, субрепозитории чище |
| **Автоматический коммит при архивации** | Изменения спецификаций нужно коммитить вручную | `commit_when_archive` автоматически коммитит спецификации в основной репозиторий |

Проще говоря, решение MonoSpecs отделяет спецификации от кода субрепозиториев, сохраняя субрепозитории чистыми, а автоматический коммит упрощает управление спецификациями.

### Зачем использовать MonoSpecs

- **Единое управление**: все субрепозитории отслеживаются в одном файле конфигурации
- **Поддержка автоматизации**: метаданные репозиториев для скриптов и инструментов
- **Удобство для ИИ**: структурированная конфигурация помогает AI Agent понять связи между репозиториями
- **Интеграция с OpenSpec**: бесшовная интеграция с рабочим процессом управления изменениями

### Когда нужен MonoSpecs

В первую очередь стоит рассмотреть MonoSpecs в следующих сценариях:

**1. Совместная разработка в нескольких репозиториях**

Когда проект разбит на несколько независимых репозиториев, ими нужно управлять централизованно:
- фронтенд-приложение, бэкенд-сервис и настольное приложение разрабатываются независимо
- вспомогательные проекты: документация, официальный сайт, инструменты сборки
- между репозиториями есть зависимости, нужно согласовывать версии и изменения

**2. Разработка функциональности, затрагивающей несколько репозиториев**

При управлении изменениями с помощью OpenSpec:
- одно изменение функциональности может затрагивать несколько репозиториев
- нужно отслеживать, в каких репозиториях применяется изменение
- изменения автоматически коммитятся в нужный целевой репозиторий

**3. Разработка с помощью ИИ**

Передача AI Agent сведений о структуре проекта:
- через `AGENTS.md` описываются стек технологий и правила каждого репозитория
- по конфигурации ИИ может понять связи между репозиториями
- поддерживаются генерация кода и рефакторинг сразу в нескольких репозиториях

**4. Непрерывная интеграция и развёртывание**

Конвейерам CI/CD нужно:
- массово обрабатывать несколько репозиториев
- автоматически выполнять сборку и развёртывание по конфигурации
- отслеживать версии и зависимости каждого репозитория

### Чем MonoSpecs отличается от обычных репозиториев

| Особенность | Обычный проект из нескольких репозиториев | Проект под управлением MonoSpecs |
|------|---------------|---------------------|
| **Обнаружение репозиториев** | Поиск и учёт вручную | Автоматическое чтение из `.hagicode/monospecs.yaml` |
| **Массовые операции** | Скрипты нужно писать вручную | Единые скрипты, управляемые конфигурацией |
| **Поддержка ИИ** | Опирается на описания в документации | Структурированная конфигурация + `AGENTS.md` |
| **Метаданные репозиториев** | Разбросаны по разным местам | Управляются централизованно (значок, имя, URL) |
| **Вхождение новых участников** | Нужно прочитать несколько документов | Достаточно запустить один скрипт |

### Описание структуры проекта

При использовании MonoSpecs нужен основной репозиторий для управления конфигурацией. Сам основной репозиторий тоже является Git-репозиторием и служит для того, чтобы:

- хранить файл конфигурации `.hagicode/monospecs.yaml`
- управлять конфигурацией и скриптами, общими для нескольких репозиториев
- отслеживать связи метаданных субрепозиториев

На примере проекта HagiCode Mono типичная структура проекта MonoSpecs выглядит так:

<FileTree>
- your-project/         # Основной репозиторий (Git-репозиторий)
  - .git/              # История Git основного репозитория
  - .gitignore         # Исключает каталог repos/
  - .hagicode/         # Каталог данных проекта HagiCode
    - monospecs.yaml   # Файл конфигурации репозиториев
  - openspec/          # Каталог изменений OpenSpec (необязательно)
  - repos/             # Каталог субрепозиториев (не в Git)
    - frontend/        # Субрепозиторий (независимый Git-репозиторий)
    - backend/         # Субрепозиторий (независимый Git-репозиторий)
    - ...              # Другие субрепозитории
</FileTree>

Все субрепозитории должны находиться в каталоге `repos/`, а этот каталог **обязательно должен быть исключён из контроля версий Git основного репозитория**. Для этого добавьте в файл `.gitignore` основного репозитория следующее:

```plaintext
# 排除所有子仓库
repos/
```

Так основной репозиторий не будет отслеживать содержимое субрепозиториев, и каждый субрепозиторий самостоятельно управляет своим контролем версий.

## Быстрый старт

В этом разделе описана начальная настройка MonoSpecs, после которой вы сможете быстро начать пользоваться управлением несколькими репозиториями.

### Инициализация

Выполните начальную настройку MonoSpecs, следуя этим шагам:

#### 1. Создайте пустую папку git

В основном репозитории создайте пустую папку `git` (обратите внимание: это именно `git`, а не `repos` — таково соглашение MonoSpecs):

```bash
mkdir git
cd git
git init
cd ..
```

#### 2. Настройте файл MonoSpecs

В корне основного репозитория создайте файл конфигурации `.hagicode/monospecs.yaml` и добавьте в него субрепозитории, которыми вы хотите управлять:

```bash
mkdir -p .hagicode
```

```yaml
version: "1.0"
commit_when_archive: true

repositories:
  - path: "repos/frontend"
    url: "https://github.com/your-org/frontend.git"
    displayName: "前端应用"
    icon: "🌐"
  - path: "repos/backend"
    url: "https://github.com/your-org/backend.git"
    displayName: "后端服务"
    icon: "⚙️"
```

#### 3. Добавьте настройку .gitignore

Добавьте в файл `.gitignore` основного репозитория следующее, чтобы исключить каталог субрепозиториев:

```plaintext
# 排除所有子仓库
repos/
```

#### 4. Получите все субрепозитории (repo)

Получите настроенные субрепозитории с помощью скрипта clone.

Он клонирует все субрепозитории в каталог `repos/` в соответствии с конфигурацией в `.hagicode/monospecs.yaml`.

#### 5. Добавьте родительский репозиторий в HagiCode

Если вы используете настольное приложение HagiCode, откройте его и добавьте основной репозиторий как проект через интерфейс. Нажмите «Добавить проект» или кнопку «+» и выберите папку основного репозитория.

Если всё настроено правильно, вы увидите список всех субрепозиториев и сведения об их состоянии.

## Конфигурация .hagicode/monospecs.yaml

### Расположение файла конфигурации

Файл конфигурации находится в корневом каталоге проекта:

<FileTree>
  - your-project/
    - .hagicode/
      - monospecs.yaml
</FileTree>

### Описание параметров конфигурации

```yaml
# 版本号
version: "1.0"

# 归档时自动提交（OpenSpec 使用）
commit_when_archive: true

# 仓库列表
repositories:
  # 仓库路径（相对于项目根目录）
  - path: "repos/frontend"
    # Git 仓库 URL
    url: "https://github.com/your-org/frontend.git"
    # 显示名称
    displayName: "前端应用"
    # 图标（emoji）
    icon: "🌐"
```

| Параметр | Тип | Обязательный | Описание |
|--------|------|------|------|
| `version` | string | Да | Версия файла конфигурации |
| `commit_when_archive` | boolean | Нет | Автоматически ли коммитить спецификации в основной репозиторий при архивации (код субрепозиториев не коммитится) |
| `repositories` | array | Да | Список конфигураций репозиториев |
| `repositories[].path` | string | Да | Относительный путь репозитория |
| `repositories[].url` | string | Да | Git URL репозитория |
| `repositories[].displayName` | string | Да | Отображаемое имя репозитория |
| `repositories[].icon` | string | Нет | Значок репозитория (emoji) |

## Операции управления репозиториями

### Добавление нового репозитория

Добавьте новую запись в массив `repositories` файла `.hagicode/monospecs.yaml`:

```yaml
repositories:
  # ... 现有仓库
  - path: "repos/new-service"
    url: "https://github.com/HagiCode-org/new-service.git"
    displayName: "新服务"
    icon: "🆕"
```

### Обновление конфигурации репозитория

Когда меняются URL репозитория или его метаданные:

1. Отредактируйте `.hagicode/monospecs.yaml`, обновив соответствующую запись
2. Проверьте корректность синтаксиса YAML
3. Если изменения нужно синхронизировать, обновите конфигурацию локального репозитория вручную

## Основные функции

В этом разделе описаны основные визуальные функции MonoSpecs при интеграции с OpenSpec — они помогут вам нагляднее понять и использовать эти возможности.

> **Примечание**: на приведённых ниже снимках экрана показан результат при включённом MonoSpecs.

### Выбор субрепозитория

При создании нового предложения вы можете выбрать целевые субрепозитории, на которые нужно опираться и которые нужно редактировать. Система автоматически определяет и показывает список доступных субрепозиториев.

![Выбор субрепозитория при создании предложения](../../img/screenshots/product/create-proposal/original.png)

При создании изменения OpenSpec читает конфигурацию `.hagicode/monospecs.yaml` и выводит все доступные субрепозитории на выбор. Вы выбираете субрепозитории, которые нужно изменить, а система автоматически отслеживает область, затронутую изменением.

### Предпросмотр сведений о репозитории

Если на панели проекта навести указатель на репозиторий, появятся подробные сведения о нём и быстрые действия.

![Просмотр сведений о репозитории при наведении](../../img/screenshots/guides/repository-hover-actions/original.png)

Благодаря такому интерактивному предпросмотру вы можете быстро узнать:
- имя, путь и текущую ветку репозитория
- текущее состояние репозитория (есть ли незакоммиченные изменения и на сколько коммитов он опережает удалённый репозиторий или отстаёт от него)
- быстрые действия для этого репозитория: открыть Code Server, открыть управление Git, Super Commit, управление DESIGN.md, перейти к репозиторию

### Выбор субрепозитория в Super Commit

При коммите изменений с помощью Super Commit можно выбрать конкретный субрепозиторий в качестве цели.

![Выбор субрепозитория в Super Commit](../../img/screenshots/product/git-super-commit/original.png)

Функция Super Commit:
1. читает конфигурацию `.hagicode/monospecs.yaml`
2. анализирует ваши изменения
3. предлагает, в какие субрепозитории стоит выполнить коммит
4. вы можете принять предложение или указать целевые репозитории вручную

## Интеграция с OpenSpec

И проекты под управлением MonoSpecs, и обычные репозитории могут использовать процесс OpenSpec из HagiCode. Основное различие — в расположении папки OpenSpec и способе распределения изменений.

### Расположение папки OpenSpec

**Обычный репозиторий**:
```
my-repo/
  - openspec/          # OpenSpec 变更目录（与代码混在一起）
  - src/
```

**Проект под управлением MonoSpecs**:
```
your-project/          # 主仓库
  - openspec/          # OpenSpec 变更目录（独立管理）
  - .hagicode/
    - monospecs.yaml
  - repos/
    - frontend/        # 子仓库（更干净，无 openspec/）
    - backend/         # 子仓库（更干净，无 openspec/）
```

**Преимущество**: спецификации хранятся отдельно в основном репозитории, а субрепозитории остаются чистыми, содержат только реальный код и не смешиваются с документами спецификаций.

### Механизм распределения изменений

**Обычный репозиторий**:
- изменения действуют только на текущий репозиторий
- спецификации и код находятся в одном репозитории
- после архивации изменения, связанные со спецификациями, нужно коммитить вручную

**Проект под управлением MonoSpecs**:
- OpenSpec читает `.hagicode/monospecs.yaml`, чтобы определить область репозиториев
- по путям изменённых файлов автоматически подбирается целевой репозиторий
- при `commit_when_archive: true` при архивации спецификации автоматически коммитятся в основной репозиторий, вручную ничего делать не нужно
- изменения кода в субрепозиториях нужно коммитить вручную

### Описание commit_when_archive

Если задано `commit_when_archive: true`:

```yaml
version: "1.0"
commit_when_archive: true  # 归档时自动提交 specs 到主仓库
```

**Поведение при архивации**:
- OpenSpec автоматически коммитит изменения спецификаций (proposal, design, tasks и т. д.) в основной репозиторий
- изменения кода субрепозиториев не коммитятся (код нужно коммитить вручную)
- не нужно вручную заниматься контролем версий спецификаций

**Пример процесса**:
1. Создайте изменение `openspec/changes/add-user-auth/`
2. Завершите проектирование и задачи, реализуйте функциональность в коде
3. Выполните архивацию
4. OpenSpec автоматически коммитит спецификации в основной репозиторий
5. Вручную закоммитьте изменения кода в субрепозитории

### Пример

Создание изменения в проекте под управлением MonoSpecs:

```
openspec/changes/add-user-auth/
  - proposal.md
  - design.md
  - tasks.md
```

Когда это изменение затрагивает `repos/frontend/src/components/Login.tsx`:

1. OpenSpec читает `.hagicode/monospecs.yaml`
2. Определяет конфигурацию репозитория, соответствующую `repos/frontend`
3. Разработчик реализует изменения кода
4. При архивации OpenSpec автоматически коммитит спецификации в основной репозиторий
5. Разработчик вручную коммитит изменения кода в субрепозитории frontend

### Поддержка конфигурации AI Agent

Проекты, использующие MonoSpecs, поддерживают через `AGENTS.md` проектно-специфичные указания для AI Agent:

<FileTree>
- your-project/
  - AGENTS.md           # Конфигурация Agent на уровне основного репозитория
  - repos/
    - frontend/
      - AGENTS.md       # Конфигурация Agent для конкретного репозитория (наследует основную)
    - backend/
      - AGENTS.md       # Конфигурация Agent для бэкенд-репозитория
</FileTree>

`AGENTS.md` каждого репозитория может содержать:

- **Описание стека технологий**: фреймворки, инструменты сборки, управление состоянием и т. д.
- **Правила кода**: соглашения об именовании, структура файлов, лучшие практики
- **Проектно-специфичное поведение**: расширения или отличия от конфигурации основного репозитория
- **Интеграция с OpenSpec**: как участвовать в рабочем процессе управления изменениями

Такая многоуровневая конфигурация позволяет AI Agent:
1. понимать глобальные правила основного репозитория
2. определять особые требования каждого репозитория
3. сохранять согласованность при операциях сразу в нескольких репозиториях

## Лучшие практики

### Соглашения об именовании

- **Путь репозитория**: используйте префикс `repos/` для единообразия
- **Имя репозитория**: используйте kebab-case (строчные буквы и дефисы)
- **Отображаемое имя**: используйте краткое название на китайском языке
- **Выбор значка**: используйте emoji, связанный с назначением репозитория

### Сопровождение конфигурации

1. **Синхронизируйте конфигурацию с реальным состоянием**: регулярно проверяйте, что `.hagicode/monospecs.yaml` отражает реальную структуру репозиториев

## Миграция с monospecs.yaml в корневом каталоге

Если проект всё ещё использует `monospecs.yaml` в корневом каталоге, вручную перенесите его в новый каталог данных проекта HagiCode:

```bash
mkdir -p .hagicode
mv monospecs.yaml .hagicode/monospecs.yaml
git add .hagicode/monospecs.yaml
git rm monospecs.yaml
git commit -m "Move MonoSpecs config to .hagicode"
```

После миграции HagiCode читает только `.hagicode/monospecs.yaml`. Если оставить лишь `monospecs.yaml` в корневом каталоге, проект будет считаться ненастроенным для MonoSpecs, а связанные скрипты не будут читать его как запасной путь.

- Убедитесь, что путь репозитория не содержит специальных символов
- Проверьте корректность синтаксиса YAML
