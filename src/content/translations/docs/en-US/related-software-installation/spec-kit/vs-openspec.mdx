Spec Kit and OpenSpec are both MIT-licensed open-source tools aimed at the same problem: when requirements live only in chat history, the output of an AI coding assistant is hard to predict, so you write the spec down and let the human and the AI agree before any code is written. They differ in how heavy the process is, how specs are organized, and the toolchain.

:::note[Our position first]
HagiCode's own workflow is built on OpenSpec, so we have a bias. The facts below come from the official documentation of both projects, checked on 2026-10-26, and anything that is our opinion is labelled as such. Both projects iterate quickly, so read each one's latest documentation before choosing.
:::

## What is being compared

- **Spec Kit**: from GitHub. The command line is `specify` (the Python package `specify-cli`); see [Install Spec Kit](/en-US/related-software-installation/spec-kit/installation) for installation and usage.
- **OpenSpec**: from Fission AI. The command line is `openspec` (the npm package `@fission-ai/openspec`); see the [Introduction to OpenSpec](/en-US/related-software-installation/openspec/intro-openspec).

## Key differences

| Dimension | Spec Kit | OpenSpec |
| --- | --- | --- |
| Runtime | Python 3.11+, installed with uv or pipx | Node.js 20.19.0+, installed with npm or Homebrew |
| Install command | `uv tool install specify-cli` | `npm install -g @fission-ai/openspec@latest` |
| Initialization | `specify init my-project --integration claude` | `openspec init` inside the project |
| Command prefix | `/speckit-*` | `/opsx:*` (`/opsx-*` in some assistants, `$openspec-*` in Codex) |
| Main flow | constitution → specify → clarify → plan → checklist → tasks → analyze → implement → converge; the shortest path is specify → plan → tasks → implement → converge | The default profile has propose, explore, apply, update, sync and archive; the expanded profile adds new, continue, ff, verify and more |
| Artifacts per feature | `spec.md`, `plan.md`, `tasks.md`, plus checklists and analysis results | One change folder containing `proposal.md`, `specs/`, `design.md` and `tasks.md` |
| How specs are organized | A complete spec written around a single feature | Built around delta specs: `ADDED` and `MODIFIED` describe the change and are merged into the long-lived specs on archive |
| Extensibility | Extensions and presets; official ones include bug and assess | Custom schemas and community schemas |
| Multiple repositories | We did not find dedicated cross-repo support in the core flow of the official docs | Stores (beta) keep planning in a repo of its own and share it across code repos |
| Supported assistants | The official docs list dozens of integrations | The official docs say 30+ tools |
| License | MIT | MIT |

## Process weight: the difference people mention most

OpenSpec's README sums Spec Kit up as thorough but heavyweight, with rigid phase gates, lots of Markdown and a Python setup, and positions itself as lighter, letting you revise any artifact at any time. That is OpenSpec's own description.

To be fair: Spec Kit's own quickstart gives a five-step shortest path in which constitution, clarify, checklist and analyze are all optional, and OpenSpec's expanded profile has plenty of commands too. The real difference is not the number of commands but the default stance. Spec Kit reads more like a pipeline that runs from spec through implementation and converges at the end, while OpenSpec stresses that each change is an independent folder you can edit at any time.

## Choose by scenario

The advice below is our judgment, not an official conclusion from either project.

| Your situation | Better fit | Why |
| --- | --- | --- |
| A new project, and you want a complete flow from spec to implementation | Spec Kit | A full flow, a constitution that constrains the whole project, and `converge` to close the loop against the spec |
| A lot of existing code, with small changes each time | OpenSpec | Delta specs describe only what changes, with no need to rewrite a full spec for existing features |
| A mostly Python team used to uv | Spec Kit | The install method matches the stack |
| A mostly Node.js team | OpenSpec | One npm command installs it |
| One feature touches several repositories | OpenSpec | Stores can keep the plan in a shared repo; note that it is still beta |
| You want many ready-made extensions (bug fixing, idea assessment) | Spec Kit | The official site lists more extensions and presets |
| Requirements change often and you want to edit specs and plans at any time | OpenSpec | Artifacts have no strict phases, so you can go back and edit |

## Decision guidance

1. **Look at your stack and habits before features.** The two overlap heavily in capability, and the friction of a mismatched environment usually matters more.
2. **Run each on the same small feature.** Pick a requirement that takes half a day and walk the full flow with each. That is more reliable than reading ten comparison articles.
3. **Do not install both in one project.** Both tools generate commands and directories in the project, and mixing them clutters your assistant's command list.
4. **Judge on three things:** whether writing the spec actually reduced rework, whether your AI assistant is officially supported, and whether the team is willing to maintain these Markdown files.

## Recommended path

- **To try one quickly:** pick the one that matches your stack, install it, and walk only the shortest path on a small feature.
- **To compare properly:** follow point 2 above with both, then decide on "amount of rework" and "team acceptance".
- **To go deeper:** read [Install Spec Kit](/en-US/related-software-installation/spec-kit/installation) and the [Introduction to OpenSpec](/en-US/related-software-installation/openspec/intro-openspec).
