## Overview

MonoSpecs is the multi-repository management approach provided by HagiCode. It tracks and manages multiple sub-repositories through `.hagicode/monospecs.yaml`. Any project that needs to manage several independent repositories in one place can use it.

> **Migration notice**: `monospecs.yaml` has moved from the project root to `.hagicode/monospecs.yaml`. A `monospecs.yaml` in the root directory is no longer detected and there is no compatibility fallback. Existing projects need to create the `.hagicode/` directory and move the file manually.

> 💡 **Quick start**: See the [monospecs-demo](https://github.com/HagiCode-org/monospecs-demo) repository for a complete MonoSpecs project structure, including the configuration file, pull scripts, and README documentation.

### Core concepts

**Configuration file**

`.hagicode/monospecs.yaml` is the core of the whole management approach. The file defines:

- The list and locations of the sub-repositories
- The Git URL of each repository
- Display names and icons
- How it integrates with OpenSpec

**How OpenSpec usage differs from a regular repository**

Both MonoSpecs-managed projects and regular single repositories can use HagiCode's OpenSpec workflow for change management. The differences are:

| Feature | Regular repository | MonoSpecs-managed project |
|------|---------|---------------------|
| **OpenSpec location** | `openspec/` in the repository root | `openspec/` in the main repository root |
| **Change scope** | Limited to the current repository | Can involve multiple sub-repositories |
| **Sub-repository cleanliness** | Specs are mixed with code | Specs live in the main repository, so sub-repositories stay cleaner |
| **Automatic commit on archive** | Specs changes must be committed manually | `commit_when_archive` automatically commits specs to the main repository |

In short, the MonoSpecs approach separates specs from sub-repository code to keep the sub-repositories clean, and it simplifies specs management through automatic commits.

### Why use MonoSpecs

- **Unified management**: Track all sub-repositories in one configuration file
- **Automation support**: Provide repository metadata for scripts and tools
- **AI-friendly**: Structured configuration helps AI Agents understand how the repositories relate
- **OpenSpec integration**: Integrates seamlessly with the change management workflow

### When to use MonoSpecs

Consider MonoSpecs first in these scenarios:

**1. Multi-repository collaborative development**

When a project is split into several independent repositories and needs unified management:
- The frontend app, backend service, and desktop app are developed separately
- Supporting projects such as documentation, the official website, and build tools
- The repositories depend on each other, so versions and changes need to be coordinated

**2. Cross-repository feature development**

When you use OpenSpec for change management:
- One feature change may involve multiple repositories
- You need to track which repositories a change is implemented in
- Changes are committed automatically to the correct target repository

**3. AI-assisted development**

Give AI Agents information about the project structure:
- Describe each repository's tech stack and conventions in `AGENTS.md`
- AI can understand how the repositories relate based on the configuration
- Supports cross-repository code generation and refactoring

**4. Continuous integration and deployment**

CI/CD pipelines need to:
- Process multiple repositories in batches
- Build and deploy automatically based on the configuration
- Track the versions and dependencies of each repository

### How MonoSpecs differs from regular repositories

| Feature | Regular multi-repository project | MonoSpecs-managed project |
|------|---------------|---------------------|
| **Repository discovery** | Look up and record repositories by hand | Read automatically from `.hagicode/monospecs.yaml` |
| **Batch operations** | Scripts must be written by hand | Unified, configuration-driven scripts |
| **AI support** | Relies on written documentation | Structured configuration plus `AGENTS.md` |
| **Repository metadata** | Scattered in different places | Managed centrally (icon, name, URL) |
| **Onboarding** | Requires reading several documents | Run a single script |

### Project structure

A MonoSpecs setup needs a main repository to manage the configuration. The main repository is itself a Git repository, and it is used to:

- Store the `.hagicode/monospecs.yaml` configuration file
- Manage cross-repository configuration and scripts
- Track the metadata relationships between sub-repositories

Taking the HagiCode Mono project as an example, a typical MonoSpecs project looks like this:

<FileTree>
- your-project/         # Main repository (Git repository)
  - .git/              # Git history of the main repository
  - .gitignore         # Excludes the repos/ directory
  - .hagicode/         # HagiCode project data directory
    - monospecs.yaml   # Repository configuration file
  - openspec/          # OpenSpec change directory (optional)
  - repos/             # Sub-repository directory (not in Git)
    - frontend/        # Sub-repository (independent Git repository)
    - backend/         # Sub-repository (independent Git repository)
    - ...              # Other sub-repositories
</FileTree>

All sub-repositories should live under the `repos/` directory, and that directory **must be excluded from the main repository's Git version control**. You can do this by adding the following to the main repository's `.gitignore` file:

```plaintext
# 排除所有子仓库
repos/
```

This prevents the main repository from tracking the contents of the sub-repositories, so each sub-repository manages its own version control independently.

## Quick start

This section walks you through the initial MonoSpecs setup so you can start using multi-repository management right away.

### Initialization

Follow these steps to complete the MonoSpecs initialization:

#### 1. Create an empty git folder

Create an empty `git` folder in your main repository (note: this is `git`, not `repos`; it is a MonoSpecs convention):

```bash
mkdir git
cd git
git init
cd ..
```

#### 2. Configure the monospecs file

Create the `.hagicode/monospecs.yaml` configuration file in the root of the main repository and add the sub-repositories you want to manage:

```bash
mkdir -p .hagicode
```

```yaml
version: "1.0"
commit_when_archive: true

repositories:
  - path: "repos/frontend"
    url: "https://github.com/your-org/frontend.git"
    displayName: "前端应用"
    icon: "🌐"
  - path: "repos/backend"
    url: "https://github.com/your-org/backend.git"
    displayName: "后端服务"
    icon: "⚙️"
```

#### 3. Add the .gitignore entry

Add the following to the `.gitignore` file of the main repository to exclude the sub-repository directory:

```plaintext
# 排除所有子仓库
repos/
```

#### 4. Pull all sub-repositories (repo)

Use the clone script to pull the configured sub-repositories.

This clones all sub-repositories into the `repos/` directory according to the configuration in `.hagicode/monospecs.yaml`.

#### 5. Add the parent repository to HagiCode

If you use the HagiCode desktop app, open it and add the main repository as a project through the interface. Click the "Add project" or "+" button and select your main repository folder.

If everything is configured correctly, you will see the list of all sub-repositories and their status.

## .hagicode/monospecs.yaml configuration

### Configuration file location

The configuration file lives in the project root:

<FileTree>
  - your-project/
    - .hagicode/
      - monospecs.yaml
</FileTree>

### Configuration options

```yaml
# 版本号
version: "1.0"

# 归档时自动提交（OpenSpec 使用）
commit_when_archive: true

# 仓库列表
repositories:
  # 仓库路径（相对于项目根目录）
  - path: "repos/frontend"
    # Git 仓库 URL
    url: "https://github.com/your-org/frontend.git"
    # 显示名称
    displayName: "前端应用"
    # 图标（emoji）
    icon: "🌐"
```

| Option | Type | Required | Description |
|--------|------|------|------|
| `version` | string | Yes | Configuration file version |
| `commit_when_archive` | boolean | No | Whether to automatically commit specs to the main repository on archive (sub-repository code is not committed) |
| `repositories` | array | Yes | List of repository configurations |
| `repositories[].path` | string | Yes | Relative path of the repository |
| `repositories[].url` | string | Yes | Git repository URL |
| `repositories[].displayName` | string | Yes | Repository display name |
| `repositories[].icon` | string | No | Repository icon (emoji) |

## Repository management operations

### Add a new repository

Add a new entry to the `repositories` array in `.hagicode/monospecs.yaml`:

```yaml
repositories:
  # ... 现有仓库
  - path: "repos/new-service"
    url: "https://github.com/HagiCode-org/new-service.git"
    displayName: "新服务"
    icon: "🆕"
```

### Update repository configuration

When a repository URL or its metadata changes:

1. Edit `.hagicode/monospecs.yaml` and update the corresponding entry
2. Verify that the YAML syntax is correct
3. If you need to sync the change, update the local repository configuration manually

## Integration with OpenSpec

Both MonoSpecs-managed projects and regular repositories can use HagiCode's OpenSpec workflow. The main differences are where the OpenSpec folder lives and how changes are distributed.

### OpenSpec folder location

**Regular repository**:
```
my-repo/
  - openspec/          # OpenSpec 变更目录（与代码混在一起）
  - src/
```

**MonoSpecs-managed project**:
```
your-project/          # 主仓库
  - openspec/          # OpenSpec 变更目录（独立管理）
  - .hagicode/
    - monospecs.yaml
  - repos/
    - frontend/        # 子仓库（更干净，无 openspec/）
    - backend/         # 子仓库（更干净，无 openspec/）
```

**Advantage**: Keeping specs in the main repository leaves the sub-repositories clean, containing only real code with no specification documents mixed in.

### How changes are distributed

**Regular repository**:
- Changes only affect the current repository
- Specs and code are in the same repository
- Specs-related changes must be committed manually after archiving

**MonoSpecs-managed project**:
- OpenSpec reads `.hagicode/monospecs.yaml` to identify the repository scope
- The target repository is matched automatically from the paths of the changed files
- With `commit_when_archive: true`, archiving commits specs to the main repository automatically, with no manual steps
- Actual code changes in sub-repositories must be committed manually

### About commit_when_archive

When `commit_when_archive: true` is set:

```yaml
version: "1.0"
commit_when_archive: true  # 归档时自动提交 specs 到主仓库
```

**Behavior on archive**:
- OpenSpec automatically commits the specs changes (proposal, design, tasks, and so on) to the main repository
- The actual code changes in the sub-repositories are not committed (code must be committed manually)
- You no longer have to manage the version control of specs by hand

**Example flow**:
1. Create the change `openspec/changes/add-user-auth/`
2. Finish the design and tasks, and implement the code
3. Run the archive operation
4. OpenSpec automatically commits the specs to the main repository
5. Manually commit the code changes in the sub-repositories

### Example

Create a change in a MonoSpecs-managed project:

```
openspec/changes/add-user-auth/
  - proposal.md
  - design.md
  - tasks.md
```

When this change involves modifying `repos/frontend/src/components/Login.tsx`:

1. OpenSpec reads `.hagicode/monospecs.yaml`
2. It identifies the repository configuration that corresponds to `repos/frontend`
3. The developer implements the code changes
4. On archive, OpenSpec automatically commits the specs to the main repository
5. The developer manually commits the code changes in the frontend sub-repository

### AI Agent configuration support

Projects that use MonoSpecs can give AI Agents project-specific guidance through `AGENTS.md`:

<FileTree>
- your-project/
  - AGENTS.md           # Agent configuration at the main repository level
  - repos/
    - frontend/
      - AGENTS.md       # Repository-specific Agent configuration (inherits the main configuration)
    - backend/
      - AGENTS.md       # Agent configuration for the backend repository
</FileTree>

Each repository's `AGENTS.md` can include:

- **Tech stack notes**: frameworks, build tools, state management, and so on
- **Code conventions**: naming conventions, file structure, best practices
- **Project-specific behavior**: extensions of, or differences from, the main repository configuration
- **OpenSpec integration**: how to take part in the change management workflow

This layered configuration lets AI Agents:
1. Understand the global conventions of the main repository
2. Recognize the special requirements of each repository
3. Stay consistent when operating across repositories

## Best practices

### Naming conventions

- **Repository path**: Use the `repos/` prefix to stay consistent
- **Repository name**: Use kebab-case (lowercase letters and hyphens)
- **Display name**: Use concise Chinese names
- **Icon choice**: Use an emoji related to the repository's function

### Configuration maintenance

1. **Keep the configuration in sync with the actual repository state**: Regularly make sure `.hagicode/monospecs.yaml` reflects the real repository structure

## Migrating from the root monospecs.yaml

If your project still uses a `monospecs.yaml` in the root directory, migrate it manually to the new HagiCode project data directory:

```bash
mkdir -p .hagicode
mv monospecs.yaml .hagicode/monospecs.yaml
git add .hagicode/monospecs.yaml
git rm monospecs.yaml
git commit -m "Move MonoSpecs config to .hagicode"
```

After migration, HagiCode only reads `.hagicode/monospecs.yaml`. If only the root `monospecs.yaml` is kept, the project is treated as having no MonoSpecs configured, and the related scripts will not read it as a compatibility path.
2. **Version control**: Commit every configuration change to version control
3. **Documentation updates**: Update the related documentation when you add or remove a repository
