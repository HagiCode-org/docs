A **project** is a folder that HagiCode works in. Sessions, Git state, standard words, and MonoSpecs settings all belong to a project, so the project rail on the left edge of the workbench is where most work starts.

## The project rail

By default the rail is collapsed to one round icon per project. Click the small arrow at the top of the rail to expand it.

![Expanded project rail listing All Sessions and the orbit-notes project, with a plus button to add a project](../../img/user-guide/workbench/02-project-rail.png)

- **All Sessions** shows sessions from every project on one board.
- Click a project to filter the board to that project and show it in the project panel.
- The green **+** button creates a project. The arrow next to it collapses the rail again.

:::tip[Which projects feed the "All Sessions" board?]
In **Settings → Sessions and conversation → Session List** you can switch the scope from *All Projects* to a *Custom Selection* of projects. See [Settings](/en-US/user-guide/settings).
:::

## Create a project

Click **+** in the project rail. The **New Project** dialog offers three ways to add projects.

### Single Project

Use this when you already have a folder on disk.

![New Project dialog on the Single Project tab with a name, folder path, and description filled in](../../img/user-guide/projects/01-create-project.png)

| Field | Notes |
| --- | --- |
| **Project Name** | Required, up to 200 characters. |
| **Folder Path** | Required, up to 1000 characters. Enter the absolute path of the folder, for example `/home/user/projects/orbit-notes`. |
| **Project Description** | Optional, up to 1000 characters. |

When the path contains `.hagicode/monospecs.yaml`, the dialog detects it and shows MonoSpecs guidance for that project. See [MonoSpecs](/en-US/guides/monospecs).

### Batch Create

Use this when you keep many repositories under one parent folder.

![New Project dialog on the Batch Create tab asking for a folder to scan](../../img/user-guide/projects/02-create-project-batch.png)

Enter the full path of the parent folder. HagiCode scans up to three directory levels for Git repositories and registers each one it finds as a project.

### Demo Project

Use this to explore HagiCode before you connect your own code.

![New Project dialog on the Demo Project tab showing the MonoSpecs Demo repository and its target path](../../img/user-guide/projects/03-create-project-demo.png)

HagiCode clones the official MonoSpecs Demo repository (`https://github.com/HagiCode-org/monospecs-demo`) and registers it. This needs Git on your machine. The path shown is the default; the real folder follows your runtime data directory.

## The project panel

Select a project and the right side of the board shows its project panel.

![Project panel with Quick actions and Repository status for the orbit-notes project](../../img/user-guide/workbench/06-project-panel.png)

**Quick actions**

| Button | What it does |
| --- | --- |
| **Auto Super Commit** | Starts an AI-assisted commit for the project. See [Super Commit](/en-US/guides/ai-compose-commit). |
| **Open Code Server** | Opens the project in the browser-based code editor. |
| **Open Git Management** | Opens the Git tab of the project details drawer. |
| **View Project Details** | Opens the project details drawer. |

**Repository status** lists each repository of the project with its current branch. The colored dot shows the working tree state; in the screenshot the dot is red because `src/server.js` has an uncommitted change. Use the refresh button to re-read the state.

The **Recent changes** menu in the board toolbar lists recently changed repositories. It shows "No recent changes yet" until a repository changes.

## Project Details

Click **View Project Details** to open the drawer. It has four tabs.

### Details

![Project Details drawer on the Details tab showing name, path, description, and icon settings](../../img/user-guide/projects/04-project-details.png)

- **Name**, **Path**, and **Description** of the project.
- **Icon Settings** choose between a *Game Icon* and a *Text Abbreviation* for the project avatar. **Change Icon** opens the icon picker.
- **Manage DESIGN.md** manages the project's `DESIGN.md` file.
- **Delete Project** removes the project after you type its name to confirm. The confirmation dialog lists what is permanently deleted: all sessions in the project and all messages in those sessions. This cannot be undone.

### MonoSpecs

![MonoSpecs tab offering to initialize MonoSpecs for the project](../../img/user-guide/projects/05-project-monospecs.png)

MonoSpecs turns a project into a workspace that coordinates specs and several repositories. On a project that is not yet a MonoSpecs workspace, **Initialize MonoSpecs** creates only what is needed. No repositories are cloned automatically:

- `.hagicode/monospecs.yaml`
- a `repos/` folder for child repositories
- `openspec/changes/archive/` and `openspec/specs/`
- a `.gitignore` update so the `repos/` folder stays untracked

Read the [MonoSpecs guide](/en-US/guides/monospecs) before you initialize.

### Standard Words

![Standard Words tab with an empty list of groups and an Add group button](../../img/user-guide/projects/06-project-standard-words.png)

Standard words are shared terminology for the project, stored in `.hagicode/standard_words.yaml`. The tab shows group, phrase, and tag counts, lets you search, **Add group**, **Refresh** from disk, and **Save changes**.

### Git

![Git tab showing the repository list on the left and a repository brief with Push, Pull, and Super Commit actions on the right](../../img/user-guide/projects/07-git-management.png)

The Git tab is the project's Git cockpit.

- **Repository list** (left) shows the monitored repositories; the counter (for example `1 / 15`) compares them with the monitoring limit from **Settings → Integration → Git**. Use **Select Changed**, **Select All**, and **Clear Selection** for batch work, or search by name. **Manage Super Commit All exclusions** controls which files the quick commit skips.
- **Repository brief** (right) shows the branch, sync status, whether there are uncommitted changes, the remote, and the repository path.
- Actions for the focused repository: **Super Commit**, **Push**, **Pull**, **Rebase Upstream**, **Open Remote Repository**, **Open Code Server**, and **Manage DESIGN.md**.

The brief replaces a diff preview on purpose. For deeper Git work, use **Open Code Server**.

Git behavior such as profiles, status monitoring, and the default Super Commit action is configured in **Settings → Integration → Git**.

## `.hagicode` data files

A project keeps its own data files in the `.hagicode/` folder at the project root, where they can be committed with Git. The folder currently holds:

- `.hagicode/monospecs.yaml`: MonoSpecs configuration. See **MonoSpecs** above.
- `.hagicode/standard_words.yaml`: standard words. See **Standard Words** above.
- `.hagicode/plans/`: scheduled plan definitions. See below.

### Scheduled plans (.hagicode/plans/)

Each scheduled plan of a project is one file in `.hagicode/plans/`. The plan's configuration lives in the file, so you can review, roll back, and share it like any other project file. The plan's run state is not stored in the file; see **What the plan file does not hold** below.

**File forms**

| File name | Scope | Description |
| --- | --- | --- |
| `<name>.yaml` | Team (`team`) | A team plan. Commit it with the project so the team shares it. |
| `<name>.user.yaml` | Personal (`personal`) | A personal plan that belongs only to you. |

The scope comes from the file name suffix, not from the file content. HagiCode reads only the files directly inside this folder. Sub-folders and other files, such as `.yml`, `.yaml.bak`, and `.md`, are ignored. If the folder does not exist, the project has no plans. Reading plans never creates the folder; the folder is created when you save the first plan.

**File name rules**

- The name part (the file name without `.yaml` or `.user.yaml`) may use only English letters, digits, and hyphens, for example `weekly-release-check`. A name that contains a space, an underscore, a dot, or a path separator, or that starts with a dot, is not read as a plan.
- If a `.yaml` file and a `.user.yaml` file in the same folder have the same name part (letter case is ignored), neither is read as a plan, and HagiCode reports the conflict. Rename one of the two files.
- Renaming a file creates a new plan. The original plan no longer exists.

**Ignore personal plans**

Personal plans usually should not be committed. Add this line to the project's `.gitignore` to exclude every personal plan and leave team plans alone:

```gitignore
.hagicode/plans/*.user.yaml
```

HagiCode does not edit `.gitignore`, so add this line yourself.

**Fields**

| Field | Required | Description |
| --- | --- | --- |
| `schemaVersion` | No | File format version. Write `"1.0"`. HagiCode does not check it when it reads the file. |
| `type` | Yes | `proposal` (a proposal plan) or `hagitask` (a HagiTask plan). |
| `name` | Yes | Plan name. It cannot be blank and can be at most 200 characters. |
| `enabled` | No | `true` or `false`. Defaults to `true`. A plan set to `false` does not run automatically. |
| `payload` | Yes | Task inputs. Field names match the matching creation request, in camelCase. A proposal plan uses `title` and `chiefComplaint`; a HagiTask plan uses `presetTaskId` and other fields. `title` is required. Plans cannot carry images, so `draftImageRefs` must be omitted or an empty list. |
| `schedule` | Yes | When the plan runs. See the table below. |
| `agentPool` | Required for HagiTask plans | Agent pool. `strategy` must be `random`. `agents` must contain exactly one agent, written with its `heroId`. A proposal plan can omit it. |
| `exceptions` | No | A list that HagiCode writes when you change or delete a single occurrence. You can omit it when you write the file by hand. |

`payload.projectId` can be omitted; when it is omitted, the plan belongs to the project that holds the file. If you write it, it must equal that project's ID, otherwise the file is skipped and reported. The folder decides which project a plan belongs to, so a file cannot bind a plan to another project.

**Schedule**

| Form | Description |
| --- | --- |
| `mode: once` | A one-time plan. `runAt` is required. Prefer a time with a UTC offset, for example `2026-11-02T09:00:00+08:00`. Without an offset, the time is read in the local time zone of the machine that runs the backend. When you create or edit the plan in the app, `runAt` must be later than the current time. |
| `mode: recurring` | A recurring plan. Requires `timeZone` (an IANA time zone, for example `Asia/Shanghai`), `startDate` and `endDate` (`yyyy-MM-dd`, both inclusive; `endDate` cannot be earlier than `startDate`), `timeOfDay` (`HH:mm`), and `repeat`. |
| `repeat.rule` | `daily` or `weekly`. |
| `repeat.weekdays` | Required for `weekly`. At least one day, written as an English weekday name from `monday` to `sunday`. |

**What the plan file does not hold**

The plan file holds configuration only. The plan's state and next run time are recorded on this machine, not in the file, so a run never changes the file's content. The plan's creation and update times are not stored separately; they come from the file's modification time.

**Create a plan by hand**

1. Create the `.hagicode/plans/` folder at the project root, if it does not exist.
2. Create a file and name it by the rules above, for example `weekly-release-check.yaml` for a team plan, or `weekly-release-check.user.yaml` for a personal plan.
3. Copy the example below into the file, edit it as needed, and save it as UTF-8 text.
4. After you save, HagiCode finds the file, and the plan appears in the project's plan list.

```yaml
schemaVersion: "1.0"
type: proposal
name: Weekly release check
enabled: true
payload:
  title: Weekly release check
  chiefComplaint: Check this week's pending changes and list the release notes that still need writing.
schedule:
  mode: recurring
  timeZone: Asia/Shanghai
  startDate: 2026-11-02
  endDate: 2026-12-31
  timeOfDay: "09:00"
  repeat:
    rule: weekly
    weekdays:
      - monday
```

**Malformed files**

A file that cannot be parsed or does not follow these rules is skipped. HagiCode reports its path in the problem list, and the other plans keep being read and run. HagiCode never rewrites, renames, or deletes a skipped file. After you fix the file, HagiCode reads it again.

**The old global plans file**

Earlier versions stored all plans in one global `scheduled-plans.json` file. HagiCode does not read, convert, or delete that file, and the plans in it are not shown or run. To keep one of those plans, create it again in the project's `.hagicode/plans/` folder.
