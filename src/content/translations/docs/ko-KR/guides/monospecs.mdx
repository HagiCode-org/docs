## 개요

MonoSpecs는 HagiCode가 제공하는 다중 저장소 관리 방식으로, `.hagicode/monospecs.yaml`을 통해 여러 하위 저장소를 추적하고 관리합니다. 여러 독립 저장소를 통합 관리해야 하는 프로젝트라면 어디에서든 사용할 수 있습니다.

> **마이그레이션 안내**: `monospecs.yaml`은 프로젝트 루트 디렉터리에서 `.hagicode/monospecs.yaml`로 옮겨졌습니다. 루트 디렉터리의 `monospecs.yaml`은 더 이상 감지되지 않으며 호환용 대체 경로로도 사용되지 않습니다. 기존 프로젝트는 `.hagicode/` 디렉터리를 직접 만들고 파일을 옮겨야 합니다.

> 💡 **빠른 시작**: 설정 파일, 가져오기 스크립트, README 문서를 포함한 MonoSpecs 프로젝트의 전체 구조는 [monospecs-demo](https://github.com/HagiCode-org/monospecs-demo) 저장소를 참고하십시오.

### 핵심 개념

**설정 파일**

`.hagicode/monospecs.yaml`은 전체 관리 방식의 핵심이며, 이 파일은 다음을 정의합니다.

- 하위 저장소의 목록과 위치
- 각 저장소의 Git URL
- 표시 이름과 아이콘
- OpenSpec과의 통합 동작

**일반 저장소와 OpenSpec 사용 방식의 차이**

MonoSpecs로 관리하는 프로젝트든 일반 단일 저장소든 HagiCode의 OpenSpec 흐름으로 변경을 관리할 수 있습니다. 둘의 차이는 다음과 같습니다.

| 특성 | 일반 저장소 | MonoSpecs로 관리하는 프로젝트 |
|------|---------|---------------------|
| **OpenSpec 위치** | 저장소 루트 디렉터리의 `openspec/` | 메인 저장소 루트 디렉터리의 `openspec/` |
| **변경 범위** | 현재 저장소로 한정 | 여러 하위 저장소에 걸칠 수 있음 |
| **하위 저장소 깔끔함** | specs와 코드가 섞여 있음 | specs가 메인 저장소에 독립되어 하위 저장소가 더 깔끔함 |
| **아카이브 자동 커밋** | specs 변경을 수동으로 커밋해야 함 | `commit_when_archive`가 specs를 메인 저장소에 자동 커밋 |

요컨대 MonoSpecs 방식은 specs와 하위 저장소 코드를 분리하여 하위 저장소를 깔끔하게 유지하고, 자동 커밋으로 specs 관리 절차를 단순화합니다.

### MonoSpecs를 사용하는 이유

- **통합 관리**: 하나의 설정 파일에서 모든 하위 저장소를 추적합니다
- **자동화 지원**: 스크립트와 도구에 저장소 메타데이터를 제공합니다
- **AI 친화적**: 구조화된 설정으로 AI Agent가 저장소 간 관계를 이해하기 쉽습니다
- **OpenSpec 통합**: 변경 관리 워크플로와 매끄럽게 통합됩니다

### MonoSpecs가 필요한 경우

다음과 같은 상황에서는 MonoSpecs를 우선 고려할 수 있습니다.

**1. 다중 저장소 협업 개발**

하나의 프로젝트가 여러 독립 저장소로 나뉘어 있어 통합 관리가 필요할 때:
- 프런트엔드 애플리케이션, 백엔드 서비스, 데스크톱 클라이언트를 각각 독립적으로 개발함
- 문서, 공식 웹사이트, 빌드 도구 같은 보조 프로젝트
- 저장소 간에 의존 관계가 있어 버전과 변경을 조율해야 함

**2. 저장소를 넘나드는 기능 개발**

OpenSpec으로 변경을 관리할 때:
- 하나의 기능 변경이 여러 저장소에 걸칠 수 있음
- 변경이 어느 저장소에서 구현되는지 추적해야 함
- 변경을 올바른 대상 저장소에 자동으로 커밋함

**3. AI 보조 개발**

AI Agent에 프로젝트 구조 정보를 제공할 때:
- `AGENTS.md`를 통해 각 저장소의 기술 스택과 규칙을 설명함
- AI가 설정을 바탕으로 저장소 간 관계를 이해할 수 있음
- 저장소를 넘나드는 코드 생성과 리팩터링을 지원함

**4. 지속적 통합/배포**

CI/CD 파이프라인에는 다음이 필요합니다.
- 여러 저장소를 일괄 처리
- 설정에 따라 자동으로 빌드하고 배포
- 각 저장소의 버전과 의존 관계 추적

### MonoSpecs와 일반 저장소의 차이

| 특성 | 일반 다중 저장소 프로젝트 | MonoSpecs로 관리하는 프로젝트 |
|------|---------------|---------------------|
| **저장소 탐색** | 수동으로 찾고 기록 | `.hagicode/monospecs.yaml`에서 자동으로 읽음 |
| **일괄 작업** | 스크립트를 직접 작성해야 함 | 통합된 설정 기반 스크립트 |
| **AI 지원** | 문서 설명에 의존 | 구조화된 설정 + `AGENTS.md` |
| **저장소 메타데이터** | 여기저기 흩어져 있음 | 중앙에서 관리(아이콘, 이름, URL) |
| **신규 인력 온보딩** | 여러 문서를 읽어야 함 | 스크립트 하나만 실행하면 됨 |

### 프로젝트 구조 설명

MonoSpecs 방식을 사용할 때는 설정을 관리할 메인 저장소가 필요합니다. 메인 저장소 자체도 하나의 Git 저장소이며 다음 용도로 쓰입니다.

- `.hagicode/monospecs.yaml` 설정 파일 저장
- 저장소 간 공통 설정과 스크립트 관리
- 하위 저장소의 메타데이터 관계 추적

HagiCode Mono 프로젝트를 예로 들면, 전형적인 MonoSpecs 프로젝트 구조는 다음과 같습니다.

<FileTree>
- your-project/         # 메인 저장소(Git 저장소)
  - .git/              # 메인 저장소의 Git 히스토리
  - .gitignore         # repos/ 디렉터리 제외
  - .hagicode/         # HagiCode 프로젝트 데이터 디렉터리
    - monospecs.yaml   # 저장소 설정 파일
  - openspec/          # OpenSpec 변경 디렉터리(선택 사항)
  - repos/             # 하위 저장소 디렉터리(Git에 포함되지 않음)
    - frontend/        # 하위 저장소(독립 Git 저장소)
    - backend/         # 하위 저장소(독립 Git 저장소)
    - ...              # 그 밖의 하위 저장소
</FileTree>

모든 하위 저장소는 `repos/` 디렉터리 아래에 두어야 하며, 이 디렉터리는 **반드시 메인 저장소의 Git 버전 관리에서 제외해야 합니다**. 메인 저장소의 `.gitignore` 파일에 다음 내용을 추가하면 됩니다.

```plaintext
# 排除所有子仓库
repos/
```

이렇게 하면 메인 저장소가 하위 저장소의 내용을 추적하는 일을 피할 수 있고, 각 하위 저장소는 자체 버전 관리를 독립적으로 운영합니다.

## 빠른 시작

이 절에서는 MonoSpecs 초기 설정을 단계별로 안내하여 다중 저장소 관리 기능을 빠르게 사용할 수 있게 합니다.

### 초기화

다음 단계에 따라 MonoSpecs 초기 설정을 완료합니다.

#### 1. 빈 git 폴더 만들기

메인 저장소에 빈 `git` 폴더를 만듭니다(주의: `repos`가 아니라 `git`이며, 이는 MonoSpecs의 규칙입니다).

```bash
mkdir git
cd git
git init
cd ..
```

#### 2. MonoSpecs 파일 설정

메인 저장소 루트 디렉터리에 `.hagicode/monospecs.yaml` 설정 파일을 만들고, 관리하려는 하위 저장소를 추가합니다.

```bash
mkdir -p .hagicode
```

```yaml
version: "1.0"
commit_when_archive: true

repositories:
  - path: "repos/frontend"
    url: "https://github.com/your-org/frontend.git"
    displayName: "前端应用"
    icon: "🌐"
  - path: "repos/backend"
    url: "https://github.com/your-org/backend.git"
    displayName: "后端服务"
    icon: "⚙️"
```

#### 3. .gitignore 설정 추가

메인 저장소의 `.gitignore` 파일에 다음 내용을 추가하여 하위 저장소 디렉터리를 제외합니다.

```plaintext
# 排除所有子仓库
repos/
```

#### 4. 모든 하위 저장소(repo) 가져오기

clone 스크립트를 사용하여 설정된 하위 저장소를 가져옵니다.

이렇게 하면 `.hagicode/monospecs.yaml`의 설정에 따라 모든 하위 저장소가 `repos/` 디렉터리로 클론됩니다.

#### 5. 메인 저장소를 HagiCode에 추가하기

HagiCode 데스크톱 애플리케이션을 사용한다면 앱을 연 뒤 화면에서 메인 저장소를 프로젝트로 추가합니다. "프로젝트 추가" 또는 "+" 버튼을 클릭하고 메인 저장소 폴더를 선택하면 됩니다.

모든 설정이 올바르다면 모든 하위 저장소의 목록과 상태 정보가 표시됩니다.

## .hagicode/monospecs.yaml 설정

### 설정 파일 위치

설정 파일은 프로젝트 루트 디렉터리에 있습니다.

<FileTree>
  - your-project/
    - .hagicode/
      - monospecs.yaml
</FileTree>

### 설정 항목 설명

```yaml
# 版本号
version: "1.0"

# 归档时自动提交（OpenSpec 使用）
commit_when_archive: true

# 仓库列表
repositories:
  # 仓库路径（相对于项目根目录）
  - path: "repos/frontend"
    # Git 仓库 URL
    url: "https://github.com/your-org/frontend.git"
    # 显示名称
    displayName: "前端应用"
    # 图标（emoji）
    icon: "🌐"
```

| 설정 항목 | 타입 | 필수 | 설명 |
|--------|------|------|------|
| `version` | string | 예 | 설정 파일 버전 |
| `commit_when_archive` | boolean | 아니요 | 아카이브할 때 specs를 메인 저장소에 자동 커밋할지 여부(하위 저장소 코드는 커밋하지 않음) |
| `repositories` | array | 예 | 저장소 설정 목록 |
| `repositories[].path` | string | 예 | 저장소 상대 경로 |
| `repositories[].url` | string | 예 | Git 저장소 URL |
| `repositories[].displayName` | string | 예 | 저장소 표시 이름 |
| `repositories[].icon` | string | 아니요 | 저장소 아이콘(emoji) |

## 저장소 관리 작업

### 새 저장소 추가

`.hagicode/monospecs.yaml`의 `repositories` 배열에 새 항목을 추가합니다.

```yaml
repositories:
  # ... 现有仓库
  - path: "repos/new-service"
    url: "https://github.com/HagiCode-org/new-service.git"
    displayName: "新服务"
    icon: "🆕"
```

### 저장소 설정 업데이트

저장소 URL이나 메타데이터가 바뀌었을 때:

1. `.hagicode/monospecs.yaml`을 편집하여 해당 항목을 업데이트합니다
2. YAML 문법이 올바른지 확인합니다
3. 변경 사항을 동기화해야 한다면 로컬 저장소 설정을 수동으로 업데이트합니다

## 핵심 기능

이 절에서는 MonoSpecs와 OpenSpec을 통합했을 때의 핵심 시각화 기능을 소개하여, 이 기능들을 더 직관적으로 이해하고 사용할 수 있도록 돕습니다.

> **주의**: 아래 스크린샷은 MonoSpecs를 활성화한 후의 모습입니다.

### 하위 저장소 선택

새 제안을 만들 때 참조하고 편집할 대상 하위 저장소를 선택할 수 있습니다. 시스템이 사용 가능한 하위 저장소 목록을 자동으로 감지하여 보여 줍니다.

![새 제안 생성 시 하위 저장소 선택](../../img/screenshots/product/create-proposal/original.png)

변경을 만들 때 OpenSpec은 `.hagicode/monospecs.yaml` 설정을 읽고 선택할 수 있는 모든 하위 저장소를 나열합니다. 수정해야 하는 하위 저장소를 선택하면 시스템이 변경이 미치는 범위를 자동으로 추적합니다.

### 저장소 상세 미리보기

프로젝트 패널에서 마우스를 특정 저장소 위에 올리면 해당 저장소의 상세 정보와 빠른 작업이 팝업으로 나타납니다.

![마우스를 올려 저장소 상세 정보 보기](../../img/screenshots/guides/repository-hover-actions/original.png)

이런 대화형 미리보기 방식으로 다음을 빠르게 파악할 수 있습니다.
- 저장소 이름, 경로, 현재 브랜치
- 저장소의 현재 상태(커밋되지 않은 변경 사항이 있는지, 원격보다 앞서거나 뒤처진 커밋 수)
- 해당 저장소에 대한 빠른 작업: Code Server 열기, Git 관리 열기, Super Commit, DESIGN.md 관리, 저장소로 이동

### Super Commit 하위 저장소 선택

Super Commit으로 변경을 커밋할 때 지정한 하위 저장소를 대상으로 선택할 수 있습니다.

![Super Commit 시 하위 저장소 선택](../../img/screenshots/product/git-super-commit/original.png)

Super Commit 기능은 다음과 같이 동작합니다.
1. `.hagicode/monospecs.yaml` 설정을 읽습니다
2. 변경 내용을 분석합니다
3. 어느 하위 저장소에 커밋해야 하는지 제안합니다
4. 제안을 수락하거나 대상 저장소를 직접 지정할 수 있습니다

## OpenSpec 통합

MonoSpecs로 관리하는 프로젝트든 일반 저장소든 HagiCode의 OpenSpec 흐름을 사용할 수 있습니다. 주된 차이는 OpenSpec 폴더의 위치와 변경이 분배되는 방식입니다.

### OpenSpec 폴더 위치

**일반 저장소**:
```
my-repo/
  - openspec/          # OpenSpec 变更目录（与代码混在一起）
  - src/
```

**MonoSpecs로 관리하는 프로젝트**:
```
your-project/          # 主仓库
  - openspec/          # OpenSpec 变更目录（独立管理）
  - .hagicode/
    - monospecs.yaml
  - repos/
    - frontend/        # 子仓库（更干净，无 openspec/）
    - backend/         # 子仓库（更干净，无 openspec/）
```

**장점**: specs를 메인 저장소에 독립시켜 하위 저장소는 순수하게 유지됩니다. 하위 저장소에는 실제 코드만 있고 규칙 문서가 섞이지 않습니다.

### 변경 분배 메커니즘

**일반 저장소**:
- 변경은 현재 저장소에만 적용됩니다
- specs와 코드가 같은 저장소에 있습니다
- 아카이브 후 specs 관련 변경을 수동으로 커밋해야 합니다

**MonoSpecs로 관리하는 프로젝트**:
- OpenSpec이 `.hagicode/monospecs.yaml`을 읽어 저장소 범위를 식별합니다
- 변경 파일의 경로에 따라 대상 저장소를 자동으로 매칭합니다
- `commit_when_archive: true`이면 아카이브할 때 specs가 메인 저장소에 자동 커밋되므로 수동 작업이 필요 없습니다
- 하위 저장소의 실제 코드 변경은 수동으로 커밋해야 합니다

### commit_when_archive 설명

`commit_when_archive: true`로 설정하면 다음과 같이 동작합니다.

```yaml
version: "1.0"
commit_when_archive: true  # 归档时自动提交 specs 到主仓库
```

**아카이브할 때의 동작**:
- OpenSpec이 specs의 변경(proposal, design, tasks 등)을 메인 저장소에 자동으로 커밋합니다
- 하위 저장소의 실제 코드 변경은 커밋하지 않습니다(코드는 수동으로 커밋해야 함)
- specs 버전 관리를 직접 챙기는 번거로움이 사라집니다

**예시 흐름**:
1. 변경 `openspec/changes/add-user-auth/`를 만듭니다
2. 설계와 작업을 마치고 코드 기능을 구현합니다
3. 아카이브 작업을 실행합니다
4. OpenSpec이 specs를 메인 저장소에 자동 커밋합니다
5. 하위 저장소의 코드 변경을 수동으로 커밋합니다

### 예시

MonoSpecs로 관리하는 프로젝트에서 변경을 하나 만듭니다.

```
openspec/changes/add-user-auth/
  - proposal.md
  - design.md
  - tasks.md
```

이 변경이 `repos/frontend/src/components/Login.tsx` 수정을 포함할 때:

1. OpenSpec이 `.hagicode/monospecs.yaml`을 읽습니다
2. `repos/frontend`에 해당하는 저장소 설정을 식별합니다
3. 개발자가 코드 변경을 구현합니다
4. 아카이브할 때 OpenSpec이 specs를 메인 저장소에 자동 커밋합니다
5. 개발자가 frontend 하위 저장소의 코드 변경을 수동으로 커밋합니다

### AI Agent 설정 지원

MonoSpecs 방식을 사용하는 프로젝트는 `AGENTS.md`를 통해 AI Agent에 프로젝트별 지침을 제공할 수 있습니다.

<FileTree>
- your-project/
  - AGENTS.md           # 메인 저장소 수준의 Agent 설정
  - repos/
    - frontend/
      - AGENTS.md       # 저장소별 Agent 설정(메인 설정을 상속)
    - backend/
      - AGENTS.md       # 백엔드 저장소의 Agent 설정
</FileTree>

각 저장소의 `AGENTS.md`에는 다음을 담을 수 있습니다.

- **기술 스택 설명**: 프레임워크, 빌드 도구, 상태 관리 등
- **코드 규칙**: 명명 규칙, 파일 구조, 모범 사례
- **프로젝트별 동작**: 메인 저장소 설정의 확장 또는 차이
- **OpenSpec 통합**: 변경 관리 워크플로에 참여하는 방법

이러한 계층적 설정으로 AI Agent는 다음을 할 수 있습니다.
1. 메인 저장소의 전역 규칙을 이해합니다
2. 각 저장소의 특수 요구 사항을 식별합니다
3. 저장소를 넘나드는 작업에서도 일관성을 유지합니다

## 모범 사례

### 명명 규칙

- **저장소 경로**: `repos/` 접두사를 사용하여 일관성을 유지합니다
- **저장소 이름**: kebab-case(소문자와 하이픈)를 사용합니다
- **표시 이름**: 간결한 중국어 이름을 사용합니다
- **아이콘 선택**: 저장소 기능과 관련된 emoji를 사용합니다

### 설정 유지 관리

1. **설정과 실제 상태 동기화**: `.hagicode/monospecs.yaml`이 실제 저장소 구조를 반영하는지 주기적으로 확인합니다

## 루트 디렉터리 monospecs.yaml에서 마이그레이션

프로젝트가 아직 루트 디렉터리의 `monospecs.yaml`을 사용하고 있다면, 새 HagiCode 프로젝트 데이터 디렉터리로 수동 마이그레이션하십시오.

```bash
mkdir -p .hagicode
mv monospecs.yaml .hagicode/monospecs.yaml
git add .hagicode/monospecs.yaml
git rm monospecs.yaml
git commit -m "Move MonoSpecs config to .hagicode"
```

마이그레이션 후 HagiCode는 `.hagicode/monospecs.yaml`만 읽습니다. 루트 디렉터리의 `monospecs.yaml`만 남겨 두면 프로젝트는 MonoSpecs가 설정되지 않은 것으로 간주되며, 관련 스크립트도 이를 호환 경로로 읽지 않습니다.
2. **버전 관리**: 모든 설정 변경은 버전 관리에 커밋해야 합니다
3. **문서 업데이트**: 저장소를 추가하거나 제거할 때 관련 문서를 업데이트합니다

### 검증 방법

- 저장소 경로에 특수 문자가 포함되어 있지 않은지 확인합니다
- YAML 문법이 올바른지 검증합니다
